“回复不对”还不是足够具体的故障描述。登录返回 401 时，可能是请求没有进入 Python，也可能是分类错了、专业角色冷却、工具参数错了，或者模型拿到正确资料后仍写了错误正文。排查的第一步是找到**最后一个正确的中间值**，再看紧接着的函数。

## 1. 先选好环境，再让编号指向同一次执行

### 调试现有线上请求，还是研究受控测试

如果第 02 章的后端已经启动，先用原入口检查健康状态，确认你连接的是当前 Python 实例。本教程直接请求 8000 的 `/chat`。断点只有在**收到请求的那个 Python 进程**里才会命中。

Dockerfile 会把源码复制到镜像，当前 Compose 没有把整个业务代码目录实时挂载进容器。宿主机编辑器中打开一个文件并打断点，不能自动调试已启动容器里的副本。本章在线断点示例使用宿主机 Python 3.12，按第 02 章进入 `.venv`、安装 `requirements-dev.txt`，先确保 Redis 和 ChromaDB 可达，然后把后端本机解释器作为调试进程运行。

准备时逐项确认：工作目录是项目根目录；解释器是本项目 `.venv`；本机 Redis 用映射端口 6379；本机 ChromaDB 用 8001，不是容器内部 8000；模型配置已准备；8000 没有被旧应用占用。依赖容器可继续运行，旧 `echomind` 应用需先停止以释放端口。

只研究第 4、5 节的受控测试，则不需要另外启动监听 8000 的后端，也不需要真实模型 Key。它们直接创建对象或用 ASGITransport 进入 FastAPI，存储和模型由测试控制。开发依赖未安装时，先完成第 6 节环境准备。

### 四个编号分别用来找什么

主线用户发“登录返回 HTTP 401，怎么处理？”，沿用 reader_01、demo-login，并为这次新调试消息使用 `msg-debug-001`：

```json
{
  "message": "登录返回 HTTP 401，怎么处理？",
  "user_id": "reader_01",
  "conv_id": "demo-login",
  "client_request_id": "msg-debug-001"
}
```

| 值 | 谁生成/提供 | 排查用途 |
| --- | --- | --- |
| `reader_01` | 请求或鉴权身份 | 找用户；启用鉴权后以后端 Token 绑定身份为准 |
| `demo-login` | 客户端会话编号 | 区分这个用户的不同对话 |
| `msg-debug-001` | 客户端消息编号 | 判断重复消息和复用回执 |
| response 的 `request_id` | 内部 Request 生成 | 找这一轮 Agent/工具轨迹，简称 R1 |

R1 只是教程简称，轨迹 URL 必须填响应中实际的 UUID。拿 `msg-debug-001` 查轨迹，通常找不到，因为它是另一个用途的编号。

如果第 02 章已经成功处理过 `msg-001`，原样重发会在回执检查处提前返回，分类和工具断点不会再执行。要查旧轨迹就使用旧 response.request_id；要看新执行就换新的 client_request_id；还想从空会话观察，再换 conv_id 为 `demo-login-debug`。不要用相同消息 ID 发不同正文，入口会返回 409。

先保存完整 HTTP 状态码、响应头和 JSON。`status=failed` 的 ChatResponse 通常以 HTTP 503 返回；未就绪、锁占用等 503 可能只有 `detail`；504 是 50 秒总预算到期。HTTP 401 表示访问鉴权被拒绝，而问题正文里“登录 HTTP 401”只是用户描述业务错误，两者不能混为一谈。

## 2. 从 chat() 入口设置断点，逐步看请求变成什么

### 编辑器怎样启动收到请求的进程

以支持 Python 调试的编辑器为例，选择本项目 `.venv` 解释器，启动方式设为运行模块 `uvicorn`，参数为 `api.main:app --host 127.0.0.1 --port 8000`，工作目录为项目根目录。初次研究时先不启用 reload，避免把断点设在父进程，而请求进入另一个重载子进程。

VS Code 的一份可参考配置如下。它是供读者保存到本机的示例，本章没有改项目配置文件。Redis URL 中的密码仅为 Compose 默认示例，若实际配置不同需同步替换；不要把真实凭据提交到仓库：

```json
{
  "version": "0.2.0",
  "configurations": [{
    "name": "EchoMind Python API",
    "type": "debugpy",
    "request": "launch",
    "module": "uvicorn",
    "args": ["api.main:app", "--host", "127.0.0.1", "--port", "8000"],
    "cwd": "${workspaceFolder}",
    "envFile": "${workspaceFolder}/.env",
    "env": {
      "REDIS_URL": "redis://:echomind123@127.0.0.1:6379/0",
      "CHROMA_HOST": "127.0.0.1",
      "CHROMA_PORT": "8001",
      "CHROMA_PERSIST_DIRECTORY": "./data/chroma",
      "EVAL_BASELINE_PATH": "./data/eval/baseline.json",
      "PROMETHEUS_PORT": "0"
    }
  }]
}
```

启动后看到服务完成初始化再发请求。编辑器断点停在一行时，这行通常**尚未执行**；跨过该行后才看赋值结果。不要看到 `intent_result` 还不存在，就认为分类没有返回。

### 第一轮建议放这几处断点

表中的语句是用于定位源码的片段；省略号不是可复制执行的 Python 表达式。

| 位置 | 要停在哪句附近 | 执行后观察什么 |
| --- | --- | --- |
| [api/main.py](../../api/main.py) · `chat` | `receipt = await _memory.get_turn_receipt(...)` | receipt 是否存在；新消息通常为 None |
| 同文件 · `chat` | `mem_ctx = await _memory.get_context(...)` | recent_messages、summary、state 是否来自正确会话 |
| 同文件 · `chat` | `intent_result = await _orchestrator.recognize_intent(...)` | message/history、intent、confidence、entities、source_scores |
| 同文件 · `chat` | `orch_req = OrcReq(...)` | 当前消息、实体、旧状态、内部 request_id |
| [agents/agent_orchestrator.py](../../agents/agent_orchestrator.py) · `run` | `req.conversation_state = merge_state(...)` | 合并前旧 state 与合并后实体、来源编号 |
| 同文件 · `run` | `decision = self._route_decision(req)` | primary_agent、supporting_agents、reason |
| 同文件 · `_call_llm` | `tool_uses = [...]` | resp.content 是正文块还是工具请求块 |
| 同文件 · `_call_llm` | `result = spec.handler(req, args)` | 工具名、schema、实际 args 与返回字典 |
| [api/main.py](../../api/main.py) · `chat` | `await _memory.commit_turn(...)` | 最终 response 与 conversation_state；提交是否正常完成 |

不要一开始每行都停。先在 intent_result、decision 和 commit_turn 三处确认输入分类、角色选择、最终结果；有异常再加中间断点。异步代码等待模型时单步可能要等网络返回；`await` 表示等待结果，不表示该行自己在无限重复。

### 正常登录例子应怎样观察

下面都是健康依赖下的教学预期，实际分类置信度和模型是否选工具要看本轮结果：

1. `receipt` 为 None，说明不是在复用旧回执。
2. 如果用了新的 demo-login-debug 会话，recent_messages 为空、summary 没有旧摘要、state 为空；如果沿用 demo-login，有历史是正常的。
3. `intent_result.intent.value` 预期是 technical_login，`entities["error_code"]` 包含字符串 401。同时读 `source_scores`，确认不是仅凭最终标签推测三路识别细节。
4. `orch_req` 应保留这句 message、实际 user_id/conv_id 和内部编号 R1。进入 `run()` 后，merge_state 输出技术领域 state，把 401 标记为来自 R1。
5. 健康技术实例存在时 `decision.primary_agent.value` 预期为 technical；若 reason 含 monitor_fallback，则进入第 10 章检查实例可用性。
6. 模型若选择 lookup_error_code，工具块 input 应是 `{"error_code":"401"}`。执行后工具应给出认证失败解释，并说明没有检查服务端日志。
7. 继续到下次模型调用，messages 末尾应带 tool_result；最终正文应基于结果给建议，不能宣称已经修复账号。
8. `response.entities` 来自合并后的 Request；提交完成后 state 和问答进入同一会话，下一轮才有东西可读。

这条链在“401 提取正确”以后仍有几个独立边界：工具被选中、参数通过校验、handler 正常完成、模型忠实使用结果。只确认一个字段不能推断后面全正确。

### 长时间暂停会影响超时

HTTP 内部的 `asyncio.timeout(50)` 和 Redis 租约仍依赖经过时间。调试器暂停不能让这些截止点自动延后；Redis 是独立进程，也不会因为 Python 断点暂停。停留过久再继续，可能立即触发超时或失去锁。在线请求适合短暂停下来观察；逐句长时间研究工具循环，改用第 4 节受控测试，既没有真实模型等待，也便于重复。

## 3. 用实际 request_id 查轨迹，再区分调用成功和业务成功

不打开调试器也可以查这次执行。先从 `/chat` 的 JSON 保存 response.request_id，再替换下面 URL 的占位文字；开启鉴权时使用管理员 Token：

```bash
curl --noproxy '*' -H "Authorization: Bearer ${ECHOMIND_TUTORIAL_TOKEN:-}" \
  http://localhost:8000/trace/tool/替换为实际request_id
```

接口实际实现为：

```python
@app.get("/trace/tool/{request_id}", response_model=ToolTraceResponse)
async def get_tool_trace(request_id: str):
    if _orchestrator is None:
        raise HTTPException(503, "服务未就绪")
    trace = await _memory.get_trace(request_id) if _memory else None
    trace = trace or _orchestrator.get_tool_trace(request_id)
    return ToolTraceResponse(
        request_id=request_id,
        found=trace is not None,
        trace=trace or {},
    )
```

先检查服务是否就绪；有 MemoryManager 时先读取 Redis 的 `trace:实际request_id`；没有结果时 `trace or ...` 取编排器近期内存轨迹。`found` 表示是否找到，不能把 `trace={}` 当成已经执行过某个工具。

HTTP 200 且 `found=false` 表示当前两处存储没找到，而不是该 UUID 的调用必然没发生。要查是否用错消息 ID、是否重启丢了内存记录、是否尚未完成 Redis 提交、持久化轨迹是否过期。正常 commit_turn 保存轨迹 7 天；内存近期记录默认最多 200 条，可由 `ECHOMIND_TOOL_TRACE_MAX` 调整。

一份完整外层结构的教学响应如下，内部编号只是占位：

```json
{
  "request_id": "替换为实际UUID",
  "found": true,
  "trace": {
    "request_id": "替换为实际UUID",
    "tool_calls": [{
      "agent_type": "technical",
      "tool_name": "lookup_error_code",
      "tool_use_id": "toolu_demo_401",
      "input": {"error_code": "401"},
      "success": true,
      "result_success": null,
      "latency_ms": 0.2,
      "cached": false,
      "reranked": false,
      "error": "",
      "source": "local",
      "mcp_server": null,
      "mcp_tool": null,
      "retry_safe": true
    }]
  }
}
```

这份展示只保留轨迹容器关键字段，单次工具条目的字段与当前实现一致；`0.2ms` 是教学数字。定位第一条实际调用用 `response["trace"]["tool_calls"][0]`，不要从最外层找 tool_name。

| 字段 | 正确解释 |
| --- | --- |
| `success=true` | 工具名在白名单、参数校验通过、handler 没抛异常 |
| `result_success=null` | 工具返回字典没有独立 success 字段；不是失败 |
| `result_success=false` | 有独立业务 success 字段且结果为 false，比如检索降级 |
| `source=local` | 当前来自本地工具，不是外部 MCP 服务器 |
| `retry_safe=true` | 工具规格允许安全重试，不表示整体 HTTP 请求必然重试 |
| `cached`、`reranked` | 结果字典中的缓存/重排标记，不能只按工具名字猜 |

lookup_error_code 只解释错误码，没有返回顶层 success，因而 result_success 为 null。知识库包装工具有业务 success 字段，才可进一步区分“调用代码正常”与“检索真的成功”。如果 success=false，先读 error 与 input，再查 schema/handler；如果工具正常、正文却编造日志，问题在结果使用而非工具连接。

轨迹来自程序实际执行，能区分模型在正文中自称“已查询”和程序真实调用。持久化轨迹经过敏感字段脱敏，但没有保存全部工具正文；核验回答是否忠实仍要结合可重现工具结果和实际回答。

## 4. 把模型换成一个有顺序的替身，为什么能验证两次调用

网络模型带来不确定性：这次它可能直接解释 401，下次可能选工具。要验证“收到 tool_use 后程序执行白名单工具，再把 tool_result 送回模型”，先固定模型输出，才能让每次运行覆盖同一路径。

这里的替身只替换外部 `messages.create()`，没有替换 `TechnicalAgent.handle()`、工具白名单、参数校验或工具循环。因此我们能检查真实程序如何处理已知模型响应。

[test_agent_orchestrator.py](../../tests/test_agent_orchestrator.py) 中的 `make_request()` 提供一个内部请求。完整辅助函数如下：

```python
def make_request(**kwargs):
    values = {
        "message": "登录时报 401，同时这笔订单被重复扣款",
        "user_id": "u1",
        "conv_id": "c1",
        "intent": IntentCategory.TECHNICAL_LOGIN,
        "intent_group": "technical",
        "urgency": UrgencyLevel.HIGH,
        "intent_confidence": 0.92,
        "entities": {"error_code": ["401"], "amount": ["99 元"]},
    }
    values.update(kwargs)
    return Request(**values)

```

`kwargs` 是可选覆盖字段；`values.update(kwargs)` 可让别的测试改其中一项。当前默认 message 同时含技术和账单信号，但本测试**直接**创建 TechnicalAgent，没有进入分类/路由，因此不证明 Billing 参与。若想从技术主线理解，关注实体里的 401 和技术角色工具即可。

下面是仓库现有工具往返测试的完整核心函数。所需 `asyncio`、`TechnicalAgent` 与上面的 Request/枚举已经在测试文件导入，读者运行原测试文件即可：

```python
def test_tool_use_round_trip_executes_only_whitelisted_tool():
    class ToolUseBlock:
        type = "tool_use"
        id = "toolu_1"
        name = "lookup_error_code"
        input = {"error_code": "401"}

    class TextBlock:
        type = "text"
        text = "已根据 401 错误码给出排查建议。"

    class ToolClient:
        def __init__(self):
            self.calls = []
            self.responses = [
                type("Response", (), {"content": [ToolUseBlock()]})(),
                type("Response", (), {"content": [TextBlock()]})(),
            ]

        class Messages:
            def __init__(self, owner):
                self.owner = owner

            async def create(self, **kwargs):
                self.owner.calls.append(kwargs)
                return self.owner.responses.pop(0)

        @property
        def messages(self):
            return self.Messages(self)

    client = ToolClient()
    agent = TechnicalAgent(client, "test-model")
    response = asyncio.run(agent.handle(make_request()))

    assert response.success is True
    assert response.tools_used == ["lookup_error_code"]
    assert len(response.tool_traces) == 1
    assert response.tool_traces[0]["tool_name"] == "lookup_error_code"
    assert response.tool_traces[0]["input"] == {"error_code": "401"}
    assert response.tool_traces[0]["success"] is True
    assert len(client.calls) == 2
    assert {tool["name"] for tool in client.calls[0]["tools"]} == {
        "lookup_error_code",
        "build_diagnostic_plan",
    }
    assert "tool_result" in str(client.calls[1]["messages"])

```

### 先理解替身中几句 Python

`ToolUseBlock` 和 `TextBlock` 是带固定字段的小对象。第一个告诉程序调用 lookup_error_code、参数 401；第二个给最终文字。它们模仿 SDK 的响应块字段，只保留这个测试用到的内容。

`type("Response", (), {"content": [...]})()` 创建一个临时类并立刻实例化，得到有 `.content` 的对象；你可以把它理解成一个装着响应块的盒子。`responses` 是两个盒子组成的队列，`pop(0)` 每次取走最前面的一个。

`Messages` 保存外层 ToolClient 的引用 `owner`。`create(self, **kwargs)` 中的 kwargs 收集这次模型请求的命名参数，如 model、messages、tools；先放进 `calls`，再取下一份固定响应。`@property messages` 使 `client.messages` 看起来与 SDK 一样，代码不需要改自己的调用入口。

`asyncio.run(agent.handle(...))` 在同步测试函数里运行异步 handle，直到完成返回 response。`assert` 检查条件，False 就让测试在这一行失败；它不生成正确结果，只验证程序已经生成的值。

### 两次调用之间，真正发生的五步

```text
handle(make_request)
  1. _call_llm 第一次 messages.create → 替身返回 ToolUseBlock
  2. 真实工具循环查白名单、验证参数、执行 lookup_error_code
  3. 把 assistant 的 tool_use 和 user 的 tool_result 追加到 messages
  4. _call_llm 第二次 messages.create → 替身返回 TextBlock
  5. 没有新 tool_use，提取正文 → handle 返回 AgentResponse
```

第一次请求的 `tools` 必须只有该测试配置下的两个本地工具：lookup_error_code、build_diagnostic_plan。真实工具返回认证失败资料后，模型第二轮输入包含类似下面的块。这是字段形状示意，content 的资料仅为示范，不是源码全部返回字典：

```json
{
  "type": "tool_result",
  "tool_use_id": "toolu_1",
  "content": "{\"meaning\": \"认证失败\", \"server_log_checked\": false}",
  "is_error": false
}
```

`tool_use_id` 把结果对应回第一次请求的工具块。`content` 是 JSON **字符串**，所以外层 JSON 中引号有反斜杠转义；它与 Python 的返回字典不是同一个层级。

还要留意这份替身的记录方式：`calls.append(kwargs)` 没有深拷贝里面的 messages 列表，而真实循环会继续往同一列表追加内容。因此运行结束后查看 `calls[0]["messages"]`，也可能看见后来追加的块；不要把它当作第一次调用当时的完整快照。想观察第一次与第二次的时间差异，在 `create()` 内或循环调用前放断点。当前断言核对调用次数、白名单和结果连接，不能由此推出消息快照已逐字段比对。

最终几个断言各自承担不同职责：`tools_used` 与 trace input 证明走过指定工具和参数；trace success 证明调用没有抛错；第一次 tools 检查白名单；`len(client.calls)==2` 检查循环确实两次调用；第二次 messages 包含 tool_result 检查结果被接回模型输入。只断言最终有文字无法证明这套连接。

也要读懂断言强度：当前测试用字符串包含检查验证第二次输入里有 tool_result，并未逐字段比对整个工具结果，也没有测试真实模型是否忠实依据资料写作。固定返回的文字不会自己核验工具内容。程序连接由这项测试验证，真实模型选择与回答质量分别用在线轨迹和第 11 章评测观察。

## 5. HTTP 多轮测试：夹具替换依赖，真实主流程仍然执行

仅直接测试 Agent 看不到记忆读取、状态提交和下一轮继承。接着看 [test_chat_reliability.py](../../tests/test_chat_reliability.py) 的多轮退款测试。这里暂时换成退款场景，因为订单、金额和日期更容易观察“继承”和“换订单清理”。

### services 不是隐藏服务，是测试开始前的准备函数

`@pytest_asyncio.fixture` 声明一个异步测试夹具。测试函数的参数叫 `services` 时，pytest 先运行同名夹具到 `yield`，把 yield 的对象交给测试；测试结束再继续 yield 后的清理。

当前夹具完整函数如下，它引用的类和 `text_response()` 已在同一个测试文件定义或导入：

```python
@pytest_asyncio.fixture
async def services(monkeypatch):
    monkeypatch.setenv("ECHOMIND_ENV", "development")
    monkeypatch.delenv("ECHOMIND_API_TOKENS", raising=False)
    memory = MemoryManager.__new__(MemoryManager)
    memory._redis = fakeredis.aioredis.FakeRedis(decode_responses=True)
    memory._request_locks = KeyedLocks()
    memory._query_episodic = AsyncMock(return_value={})
    memory._get_profile = AsyncMock(return_value={})
    client = SimpleNamespace(messages=SimpleNamespace(create=AsyncMock(return_value=text_response())))
    orch = AgentOrchestrator.__new__(AgentOrchestrator)
    orch._pool = {
        kind: [cls(client, "test-model")]
        for kind, cls in [(AgentType.GENERAL, GeneralAgent), (AgentType.BILLING, BillingAgent),
                          (AgentType.TECHNICAL, TechnicalAgent)]
    }
    orch._composer = ResponseComposer(client, "test-model")
    orch._recent_tool_traces = deque(maxlen=200)
    recognizer = IntentRecognizer.__new__(IntentRecognizer)

    async def recognize(message, history=None):
        return IntentResult(IntentCategory.REFUND, .95, UrgencyLevel.LOW, "billing",
                            recognizer._extract_entities(message), "test", 0)

    orch.recognize_intent = AsyncMock(side_effect=recognize)
    monkeypatch.setattr(api, "_memory", memory)
    monkeypatch.setattr(api, "_orchestrator", orch)
    monkeypatch.setattr(api, "_profile_updater", None)
    monkeypatch.setattr(api, "_monitor", None)
    async with httpx.AsyncClient(transport=httpx.ASGITransport(app=api.app), base_url="http://test") as http:
        yield memory, orch, client, http
    await memory._redis.aclose()

```

别急着记住所有类名，按它们替换的外部边界来看：

1. `monkeypatch` 临时设置 development 并移除鉴权变量，让这一组默认测试不依赖本机已有 Token；测试结束自动还原设置。鉴权专项由同文件其他测试或真实存储脚本单独验证。
2. `MemoryManager.__new__(MemoryManager)` 分配对象，跳过会连接真实依赖的 `__init__()`。随后显式设置 `_redis`、锁及本测试需要的其他成员，真实 get_context/commit_turn 逻辑仍可执行。
3. `FakeRedis(decode_responses=True)` 在进程内模拟 Redis 命令，返回文本。`KeyedLocks()` 保留当前会话的本机锁实现。
4. `_query_episodic` 和 `_get_profile` 用 `AsyncMock` 返回空字典，跳过 Chroma 查询；近期记忆和 state 仍通过 FakeRedis 读写。
5. `SimpleNamespace` 是简单属性容器，使 client.messages.create 与 SDK 形状相同。`AsyncMock(return_value=text_response())` 每次被 await 就返回固定“回复完成”，还可以记录调用次数或临时设为抛异常。
6. 编排器也用 `__new__` 跳过初始化，但放入真实 General/Billing/Technical 实例，并保留真实 run、状态合并与路由逻辑。
7. `recognize()` 固定意图为 REFUND、置信度 0.95、领域 billing，但实体仍调用真实 `_extract_entities(message)`，所以订单、金额、日期来自每轮输入的实际提取。此测试不是在验证分类是否识别退款。
8. `monkeypatch.setattr(api, ...)` 把 HTTP 路由实际读取的模块全局服务替换为这组对象，关闭无关的画像后台和 Monitor。
9. `ASGITransport(app=api.app)` 直接把请求交给 FastAPI 应用，中间件、请求校验、`/chat` 路由仍执行，只是没有打开真实 TCP 监听端口。
10. `yield memory, orch, client, http` 给测试四个对象；结束后关闭 FakeRedis。每个测试建立自己的对象，避免上一测试残留会话污染下一测试。

因此 `http.post("/chat", ...)` 经过真实 HTTP 入口逻辑，不是直接给 merge_state 函数塞一个期望答案；模型和存储协议的外部依赖受控，函数连接仍是真实的。

### 四轮请求和断言完整接起来

请求辅助函数把 user 固定为 u，会话默认为 c，每条消息 ID 由调用者传入：

```python
def body(message="退款规则", request_id="one", conv_id="c"):
    return {"message": message, "user_id": "u", "conv_id": conv_id,
            "client_request_id": request_id}
```

`@pytest.mark.asyncio` 告诉 pytest 用异步方式运行这个测试，才能在函数里 await HTTP 请求。现有测试如下：

```python
@pytest.mark.asyncio
async def test_slots_survive_turns_but_reset_for_another_order_or_conversation(services):
    memory, orch, model, http = services
    await http.post("/chat", json=body("订单号 #12345，昨天支付99元", "first"))
    second = await http.post("/chat", json=body("退款多久到？", "second"))
    assert second.json()["entities"]["order_id"] == ["12345"]
    assert second.json()["entities"]["amount"] == ["99元"]
    assert second.json()["entities"]["date"] == ["昨天"]
    third = await http.post("/chat", json=body("另一笔订单 #67890", "third"))
    assert third.json()["entities"]["order_id"] == ["67890"]
    assert not third.json()["entities"]["amount"] and not third.json()["entities"]["date"]
    other = await http.post("/chat", json=body("退款多久到？", "fourth", "other"))
    assert not other.json()["entities"]["order_id"]
    state = json.loads(await memory._redis.get(memory._state_key("u", "c")))
    assert state["sources"]["order_id"] == third.json()["request_id"]

```

第一行把夹具返回的四个对象依次取出。`await http.post()` 必须等这一轮完成，下一句才能读到本轮提交的状态；`response.json()` 把 HTTP JSON 转成 Python 字典。

| 轮次 | 用户消息/会话 | 预期 state 的关键变化 | 对应断言在检查什么 |
| --- | --- | --- | --- |
| first · c | 订单 #12345、昨天、99元 | 写入订单、日期、金额 | 第一轮为后续继承准备真实提交 |
| second · c | 退款多久到？ | 没换任务，继承三个旧字段 | response.entities 仍有 12345、99元、昨天 |
| third · c | 另一笔订单 #67890 | 新任务/换订单，清理旧日期金额 | 订单变成67890，amount/date为空 |
| fourth · other | 退款多久到？ | 独立会话，从空状态开始 | 不应继承 c 中的订单 |

第三轮的 `assert not ...` 是 Python 的真假检查，空列表 `[]` 为假，因此表示该列表应为空。最后两行进一步直接读 FakeRedis 的 state JSON，检查订单来源等于第三轮**内部** request_id：这不是只把字段临时放到 response 后就结束，它必须正确提交来源状态。

完整连接是：HTTP body → `/chat` 读取 FakeRedis 历史和 state → 固定退款意图、真实实体提取 → 编排器 merge_state → 真实角色在固定模型下返回正文 → response.entities → commit_turn 写回 FakeRedis → 下一轮再次读出。

如果 second 的 order_id 断言失败，有三处值得逐一查看：上一轮是否提交、第二轮是否读到正确 state、合并是否保留旧字段。它不先依赖模型正文质量，所以可以精确定位程序行为。FakeRedis 仍不代替真实 Redis 的网络、租约时序和服务重启；那部分用本章后面的 verify 脚本检查。

## 6. 怎样运行现有测试，失败输出应该从哪里读

在项目根目录、已经进入本项目 Python 3.12 虚拟环境后运行。若开发依赖未装，第一条完成安装；本章解释的是读者操作步骤，本轮文档维护的实际执行情况见文末完善说明：

```bash
python -m pip install -r requirements-dev.txt
INTENT_EMBEDDING_PROVIDER=local python -m pytest -q \
  tests/test_agent_orchestrator.py::test_tool_use_round_trip_executes_only_whitelisted_tool \
  tests/test_chat_reliability.py::test_slots_survive_turns_but_reset_for_another_order_or_conversation
```

`python -m pytest` 使用当前解释器执行测试，减少终端 pytest 与编辑器 Python 不属于同一环境的误会。`-q` 减少例行输出，`文件::函数名` 只选这个测试。前置 `INTENT_EMBEDDING_PROVIDER=local` 让涉及意图向量的代码走本地提供器，不是配置真实模型。

两条测试都通过时通常看到 `2 passed`；这是成功输出形状说明，不是本次已运行结果。不同环境还可能显示耗时或 warnings。若 collection 阶段就提示 `ModuleNotFoundError: fakeredis`，根本还没到任何 assert，先确认 requirements-dev 安装到当前解释器，而不是改业务逻辑。

想看失败位置和具体变量，重跑选定测试并增加详细参数，例如：

```bash
INTENT_EMBEDDING_PROVIDER=local python -m pytest -vv --tb=short --maxfail=1   tests/test_chat_reliability.py::test_slots_survive_turns_but_reset_for_another_order_or_conversation
```

教学失败输出可能像这样，不代表当前代码确实失败：

```text
FAILED tests/test_chat_reliability.py::test_slots_survive_turns_but_reset_for_another_order_or_conversation
E   AssertionError: assert [] == ['12345']
```

从下往上找到失败 assert 所在源码行。这个例子说明“期待第二轮保留 12345，实际拿到空列表”，还没有说明是读取还是合并错误。再看测试输入的 user/conv 和每轮 state，把最早不正确的变量找出来。若报 `KeyError: 'entities'`，先打印/查看 `second.status_code` 与 `second.json()`；它可能拿到错误 detail，而不是正常 ChatResponse。

Agent 往返测试若 `len(client.calls)` 不是 2，查看是第一次就返回正文、工具循环提前异常，还是第二次之后还继续发工具请求；若 tools_used 空而 trace 中 success=false，先查白名单与 schema；若调用两次但第二次缺 tool_result，查 messages 追加的位置。不同 assert 指向不同连接，不能把所有失败统一归为“模型不稳定”。

受控测试可以在编辑器以 pytest 调试方式运行，在测试函数和 `_call_llm()` 放断点。第一次模型调用立即返回固定 tool_use，第二次立即返回固定正文，适合慢慢研究 messages 如何变化；不需要为逐句调试去放大线上超时预算。

## 7. 三个完整定位案例：从现象走到第一个错误变量

### 案例 A：登录 401 被 General 回答

先保留本轮 JSON 的 intent、agent_type、primary_agent、routing_reason 和 request_id。若实际 HTTP 是 401 且只有鉴权 detail，请求还没有进入角色，先修正访问身份。

HTTP 正常且 `intent=technical_login` 时，分类已经给出技术意图。再看 reason：含 `monitor_fallback=[technical]`，就查 `/monitor` 中 technical 实例的 recent_total、monitor_penalty、recovery_state，对照第 10 章检查是否冷却或探测占用；有技术分类并不保证每次技术实例都可用。

如果 primary_agent=technical 但实际 agent_type=general，还可能是本轮 Technical 执行失败后的 `_execute()` 即时兜底。用 request_id 读轨迹，查是否有 `agent_fallback` 事件，再读模型错误日志。不要只根据最终 agent_type 断定 `_route_decision()` 分类错了。

若 intent 本身已经是 other，往前看识别器收到的 message 和 history，再看三路分数与融合理由。断点确认实际数据以后，再决定改规则、向量样例还是上下文处理。

### 案例 B：回答说“检查过日志”，工具却只给错误解释

先看 `/trace/tool/{request_id}` 的 found 和 tool_calls。没找到轨迹时先排除编号错误、尚未提交和过期；找到后确认 tool_name=lookup_error_code、input.error_code 是字符串 401。

success=false 时查看 error，可能白名单、schema 或 handler 执行异常；success=true、result_success=null 对这个本地工具是正常的。再在 handler 返回后观察 `server_log_checked=false`，然后看第二次模型请求是否带相同结果的 tool_result。

如果结果正确传入，最终正文仍写“已检查日志”，最后一个正确变量就是 tool_result，紧接着的正文生成错误。此时重点检查角色提示词、模型对资料边界的使用，用第 11 章 evidence 评测重复核验；调整 Redis 键或增加 Monitor 成功率不会纠正这句事实。

### 案例 C：第二轮“还是报错”丢了 401

先确认两轮最终实际 user_id 与 conv_id 相同，client_request_id 不同。启用鉴权时 user_id 应核对 Token 绑定身份；请求 body 写 reader_01 并不能覆盖绑定身份。若 conv 不同，它本来就是新会话。

再看第一轮响应是否 failed，failed 回执不会把问答和 state 写成一轮正常历史；有正文却返回前提交失败，也可能尚未留下可读状态。检查第一轮 commit_turn 是否完成、Redis state 是否含 error_code。

第二轮停在 get_context 后，若 mem_ctx.state 已丢字段，问题在身份/会话、提交或读取；若 state 正确但 merge_state 后消失，检查当前 intent_group 是否改变领域、是否有新任务信号；若合并正确且字段进入角色契约，模型仍重复问错误码，问题才在模型使用上下文。

退款测试的 second/third/other 分支提供了同一种定位练习，只是换成更容易断言的订单字段。用它检查读取→合并→提交的连接，再用登录真实请求检查实际分类与回答。

### 入口和评测也用同一个顺序

页面可用但 `/health` 失败，先查后端进程、容器健康、依赖与代理，尚未到 Agent。评测任务 completed 却没有基线，先查 report.status、suite_id 和 baseline 路径，任务完成和测量完整是不同条件。

每次排查写下三样东西就够用：这次请求编号、最后正确的变量、下一步产生错误的函数。它能把“整个项目回复不对”变成一个固定输入可复现的局部问题，再选择下面相应的测试。

| `verify_memory_keys.py` | Redis 键隔离、旧键原子迁移、TTL 与歧义旧身份 |
| `verify_memory_concurrency.py` | 真实 Redis 快照压缩、保留并发新增消息、摘要失败不删原文 |
| `verify_request_concurrency.py` | Redis 租约与完整聊天串行化、Chroma 同用户跨会话检索与不同用户隔离 |

这里的“完整聊天串行化”指脚本直接调用 `api.chat()`，让第一条生成等待、第二条排队，并检查后者读到了前者的回复。它没有通过HTTP客户端或ASGITransport发送请求，因此不覆盖FastAPI网络输入校验、中间件鉴权或真实TCP连接。前面 `test_chat_reliability.py` 的受控HTTP测试与这个真实存储脚本各检查一段不同的连接，不能把它们当作同一个测试。

脚本会创建测试数据，按随机测试身份清理自己的记录；模型结果使用替身。应对开发环境运行，知道目标 Redis/Chroma 地址再执行。使用哪套配置就带哪套命令前缀；修改过脚本但镜像没有更新时先重建应用，否则跑到的是镜像里的旧版本。

每段脚本打印 `PASS:` 才表示它已经到达相应断言之后；没有异常结束再读最后的成功行。`AssertionError` 要回到 traceback 的断言查看实际与期望，Redis 的连接/鉴权错误则先修复依赖地址与密码，Chroma 连接错误先确认宿主机 8001 或容器内 chromadb:8000。不要把进程成功启动当成所有验证已经完成。

宿主机可以按以下形状调用一个脚本，前提仍是当前虚拟环境已装项目依赖、存储可达。示例 Redis 密码是 Compose 默认值，配置不同要替换：

```bash
REDIS_URL='redis://:echomind123@127.0.0.1:6379/0' \
PYTHONPATH=. python tests/verify_chat_atomic.py
```

这些脚本各自在随机测试身份下创建数据，并在 finally 清理；异常也会进入清理，但进程被直接杀死可能留下数据，需要根据该脚本的随机键范围核对。它们验证的是测试创建的记录，不能直接推断现有生产会话内容已无问题。

宿主机执行脚本时设置第 02 章的本机存储地址，并加 `PYTHONPATH=.`；这几个脚本最终通过 `os.environ["REDIS_URL"]` 取地址，显式导出最容易确认目标；`verify_memory_keys.py` 自己不调用 load_dotenv，而 `verify_chat_atomic.py` 导入 api.main 时会间接加载配置，行为并不完全相同。`verify_request_concurrency.py` 还需要可达的 ChromaDB。

## 最后一次核对：每层测试能证明什么

| 检查 | 可以证明 | 仍需另外验证 |
| --- | --- | --- |
| 工具/状态的纯函数实验 | 固定输入对应的规则行为 | 函数是否被 HTTP 流程正确调用 |
| Agent / HTTP 受控测试 | 往返、回执、状态、失败分支的程序行为 | 真实存储、网络与模型兼容性 |
| 真实存储脚本 | 当前依赖下的锁、事务与数据隔离 | 真实模型分类和正文质量 |
| 第 11 章 Judge 评测 | 固定用例的执行条件和回答质量 | HTTP 鉴权、回执和部署可用性 |

本轮教程维护的验证范围和环境限制见[完善说明](完善说明.md)。阅读测试时看输入替身和断言，不能只凭“测试通过”推断全部能力已经覆盖。

## 文档改完以后，怎样检查它仍然能照着操作

先在项目根目录运行配套的[文档检查脚本](scripts/check_docs.py)。它只需要 Python 3.12 与 Bash，不需要启动服务：

```bash
python3.12 wiki/教程/scripts/check_docs.py --run-offline \
  --report data/tutorial/docs-check.json
```

脚本检查本地链接和章节锚点、Shell 代码块语法、完整 Python 命令的语法、JSON 格式，以及文中点名的测试函数是否存在。`--run-offline` 只运行第 01、05、07 章已有的三个离线实验；其他聊天、知识写入、监控配置和评测命令不会自动执行。只想检查语法时，去掉这个选项。

输出 `status=passed` 表示上述检查通过。记录还包含 Python 版本、Git HEAD，以及当前源码和教程的内容摘要。内容摘要是一串用文件内容算出的标识：文件改变，标识通常也会改变。因为工作区可能有未提交修改，单记 Git HEAD 不够，这两串摘要可以帮助区分两次检查是否针对同一份内容。脚本不读取 `.env`，也不把模型 Key 写进报告。

### 静态检查通过后，还要分层验收

检查脚本能发现“链接坏了、命令语法错了”，不能证明 Docker、网络和模型都能正常工作。按下面的顺序验证，更容易知道失败发生在哪一层：

| 层级 | 使用已有的哪一步 | 成功时留下什么记录 |
| --- | --- | --- |
| 文档与离线函数 | 上面的检查脚本 | `docs-check.json`，状态 passed，三个离线实验通过 |
| Python 程序分支 | 本章 `python -m pytest -q tests` | 实际通过/失败数量；不要只记录进程启动了 |
| 部署配置 | `docker compose config --quiet`，或带对应练习/监控配置 | 命令退出码为 0；它仍不代表容器能启动 |
| 应用启动与聊天 | 第 02 章健康检查、首次聊天、追问 | HTTP 状态、业务 status、服务端 request_id |
| 回执和真实存储 | 第 04 章重试实验、本章 verify 脚本 | 回执复用结果、各脚本实际 PASS 输出 |
| 知识与协议 | 第 08 章已有导入、搜索、本地 MCP 调用 | 命中教程文档的 ID/版本、MCP 结果；不只看数组非空 |
| 监控 | 第 10 章 `/monitor`、指标采集 | 实际角色统计；使用 Prometheus 时确认目标 UP |
| 模型评测 | 第 11 章一条用例到终态 | 保存完整任务 JSON，分别记录执行、评分和通过情况 |

前两层不需要真实模型。后面的 HTTP 实验需要运行中的应用；聊天、检索改写和 Judge 会按章节说明调用模型。不要把“这次没有运行”写成“通过”，也不要把模型没选择某个工具一律解释成程序故障。

复现时至少保留：检查日期、操作系统、Python/Docker/Compose 版本、模型 ID、是否启用鉴权、使用的 Compose 文件、上表各项结果。记录配置项时只写模型名、地址和开关，不抄 Key 或 Token。
