## 从变量名找到类型和产生它的函数

| 走读中的变量 | 实际类型 | 产生位置 | 返回后怎么使用 |
| --- | --- | --- | --- |
| req（chat 中） | ChatRequest | FastAPI 按 Pydantic 解析 | 身份、回执和上下文读取 |
| mem_ctx | MemoryContext | MemoryManager.get_context | 裁短历史、组织背景、取得旧状态 |
| intent_result | IntentResult | IntentRecognizer.recognize | 构造编排请求 |
| orch_req / req（run 中） | Request | chat 的 OrcReq(...) | 状态合并、路由、角色和工具 |
| decision | RoutingDecision | _route_decision | 单角色执行或并行分派 |
| call_result | AgentCallResult | BaseAgent._call_llm | handle 补角色、耗时与统计 |
| response（handle/_execute 路径） | AgentResponse | BaseAgent.handle | run 整理为编排结果 |
| result（chat 中） | OrchestratorResult | AgentOrchestrator.run | 映射为 ChatResponse |
| response（chat 中） | ChatResponse | chat | 保存回执、返回 HTTP JSON |

同名变量可能位于不同函数：工具循环中的 result 是 handler 返回的内容，chat 中的 result 则是整轮 OrchestratorResult。先看当前函数和赋值来源，再判断其字段，能避免把“工具返回成功”与“整轮处理成功”混在一起。

## 聊天字段与单位

请求message为1至12000字符，client_request_id可选、1至128字符。user_id开发默认anonymous；认证后以Token身份为准。conv_id用于继续会话。

| 响应字段 | 含义或单位 |
| --- | --- |
| request_id | 执行轨迹身份，区别于客户端消息ID |
| intent、intent_group | 标签与领域组 |
| entities | 字段名到字符串列表，可能已多轮合并 |
| primary_agent、supporting_agents | 路由计划 |
| agent_type、agent_types | 单角色时前者来自执行响应；并行时前者仍为计划主角色，后者结合成功响应和轨迹阅读 |
| routing_confidence | 领域路由信号，非分类准确率 |
| intent_confidence、intent_source_scores | 融合与来源信号，非经过标定概率 |
| status | success / partial / failed |
| retryable、error_code | 安全重试与故障类别 |
| latency_ms | 毫秒，到回复生成结束 |
| knowledge_used | 轨迹中知识库工具结果成功 |
| escalated | 交接或升级标记，不证明真实队列接收 |

Server-Timing响应头含主请求存储提交。工具轨迹含调用名、输入、来源、执行与业务成功、耗时等，结果正文不是完整审计存档。

## HTTP 错误与业务状态的对应关系

| 返回 | 常见触发位置 | 后续如何理解 |
| --- | --- | --- |
| 200 + success | chat 正常执行并提交 | 可以继续会话，仍要看正文是否有待核验事项 |
| 200 + partial | 有可用但不完整的回复 | 同一客户端 ID 会复用该部分结果 |
| 401 | access_control 未找到有效身份 | 检查应用访问 Token |
| 403 | 普通用户访问管理接口 | 使用具备管理权限的身份 |
| 409 | 同一客户端消息 ID 对应不同文本 | 修正新消息编号 |
| 422 | Pydantic 请求校验 | 核对类型、长度和字段位置 |
| 503 | 未就绪、锁异常或处理失败 | 查看 detail 或 ChatResponse 中的错误码 |
| 504 | chat 的 50 秒总预算超时 | 原消息复用原客户端 ID，让回执先判断 |
| 202 | 评测任务提交成功 | 用 job_id 查询进度与报告 |
| 429 | 评测待处理容量已满 | 等已有任务完成，避免继续堆积 |

同一个 HTTP 503 可能来自不同阶段，所以返回体不一定都是 ChatResponse。前端应兼容 `detail` 类型的 HTTPException 响应，不应把任何错误 JSON 都当成有 response 字段的客服回答。

<a id="section-06"></a>

## 各阶段的默认预算怎样叠加

| 阶段 | 当前默认限制 | 范围 |
| --- | --- | --- |
| HTTP 聊天 | 50 秒 | 会话等待、读取、分类、执行和提交所在的整体处理 |
| 获取 Redis 租约 | 最多等待 30 秒 | 跨进程锁等待，仍受外层聊天预算约束 |
| 意图 LLM | 每次 8 秒、256 输出 token | 分类分支 |
| 意图在线向量 | 整次匹配 8 秒 | 模板初始化及当前查询，失败转本地 |
| 普通 Agent | 每次模型请求 15 秒，最多 3 轮 | 不代表工具和其他阶段可额外无限等待 |
| 检索查询改写 | 10 秒 | 失败保留原查询 |
| 检索模型重排 | 30 秒 | 失败使用原候选顺序 |
| 回复合成 | 8 秒 | 失败尝试确定性拼接 |
| 后台压缩 | maintain 中 30 秒 | 超过则结束本次维护分支 |
| 画像模型提炼 | 15 秒 | 后台执行 |
| Judge | 每次 45 秒，最多 2 次 | 独立评测，不受 chat 的 50 秒 HTTP 预算包裹 |
| 整个评测任务 | 1800 秒 | 取得任务锁后执行 runner 的上限 |

这些不是可以简单相加的服务承诺。聊天外层 50 秒可以先于某个内层预算耗尽；识别分支、主辅 Agent 又可能并行。排队中的评测等待也不属于取得锁后那段 runner 的 1800 秒计时。

## Redis键与生命周期

| 数据 | 当前键形式 | 典型TTL或上限 |
| --- | --- | --- |
| 工作消息 | wm_v2:<会话身份哈希> | 24小时 |
| 当前摘要 | summary_v2:<会话身份哈希> | 24小时 |
| 业务状态 | state_v1:<会话身份哈希> | 24小时 |
| 消息回执 | turn_receipt:<会话哈希>:<消息ID哈希> | 24小时 |
| 轨迹 | trace:<request_id> | 7天 |
| 最近轨迹 | trace:recent | 最近200条索引 |
| 会话锁 | lock:conversation:<协调身份哈希> | 租约默认120秒，续租 |
| 用户画像锁 | lock:profile:<用户身份哈希> | 租约保护 |

聊天协调锁和数据键的哈希构造由代码负责，不要手工假设二者完全相同。旧明文键只在归属可确认时迁移，带冒号的旧身份不自动猜测归属。

## 只读检查一个会话

下面以教程的 reader_01 / demo-login 为例，容器中使用实际 Redis 连接变量；查看其他会话时替换这两个值：

```bash
docker compose exec -T echomind python - <<'PYCODE'
import asyncio
import os
import redis.asyncio as redis
from memory.conversation_memory import MemoryManager

async def main():
    client = redis.from_url(os.environ["REDIS_URL"], decode_responses=True)
    user_id, conv_id = "reader_01", "demo-login"
    key = MemoryManager._wm_key(user_id, conv_id)
    print("messages:", await client.lrange(key, 0, 19))
    print("ttl:", await client.ttl(key))
    print("summary:", await client.get(MemoryManager._summary_key(user_id, conv_id)))
    print("state:", await client.get(MemoryManager._state_key(user_id, conv_id)))
    client_request_id = "msg-001"  # 换成当时发送的客户端消息ID
    receipt_key = MemoryManager.receipt_key(user_id, conv_id, client_request_id)
    print("receipt:", await client.get(receipt_key))
    print("receipt_ttl:", await client.ttl(receipt_key))
    await client.aclose()

asyncio.run(main())
PYCODE
```

列表最新在前。TTL=-2表示键不存在，-1表示没有设置过期。回执里包含原问题和原响应，需用客户端消息 ID 查询；不是用响应中的服务端 UUID。有叠加配置时带齐对应 -f。独立练习环境将命令开头换为 `docker compose -p echomind-tutorial -f wiki/教程/examples/compose.tutorial.yml exec -T echomind python -`，后面的 Python 程序保持不变。脚本不修改数据，但输出可能包含会话内容，分享时先脱敏。

## ChromaDB与文档版本

knowledge_base保存资料，episodic保存情景摘要，user_profile保存用户画像。文档结果含title、content、document_id、version和片段位置等。document_id和version可为哈希，不能只看标题判断是否同一来源。

开发可能本地降级，生产远端失败中止；确认实际连接后再检查collection。示例政策不是真实企业政策，生产空库需要导入有效文档。

## 评测字段与默认数量

默认11条意图样本、5组对话含7轮，报告1条分类汇总+7条对话结果=8；进度1组分类+5组对话=6。

| 字段 | 用途 |
| --- | --- |
| job.status | queued/running/completed/failed/cancelled |
| job.completed、total | 按组的任务进度 |
| job.result.status | complete/partial/failed/empty |
| result.valid_total、evaluation_errors | 有效结果与评分执行失败 |
| result.pass_rate | 有效结果中的通过比例，四舍五入4位 |
| result.avg_scores | 有效均分，不替代所有业务证据 |
| metadata.agent_status、deterministic_checks | 生成状态与明确要求 |
| metadata.judge_failed、judge_error_type、judge_attempts、judge_stop_reason | 评分失败定位 |
| metadata.judge_few_shot_version/count | 校准例子版本与数量 |
| suite_id、regression_note | 比较条件与跳过原因 |

Few-shot在evaluation/few_shot.py，默认5个；修改后重建代码镜像。队列最多8个未完成任务、最近50个任务、单任务1800秒，重启丢失任务状态。

## 数据保存位置与恢复边界

根目录Compose的Redis、ChromaDB和Prometheus使用命名卷。Skills、评测基线和日志等使用项目挂载目录。

普通down保留卷，down -v删除卷。进程内评测任务与缓存不因为数据卷存在就持久化；本地ChromaDB降级数据不自动合并回远端。恢复前先确认当前部署方式和数据源。

## 使用独立练习环境：不把教程数据混进已有服务

第 08 章会写入知识资料，第 11 章可能更新评测基线。已有数据需要保留时，可以用[独立 Compose 文件](examples/compose.tutorial.yml)单独运行 Python、Redis 和 ChromaDB。它仍使用当前源码和 `.env` 中的模型配置，所以真实聊天与评分仍会产生模型调用。

它只启动本教程需要的 Python 应用与两种存储。文件单独使用，不与根目录的 Compose 叠加。

### 1. 先确认隔离了什么

| 项目 | 练习环境的做法 |
| --- | --- |
| 服务身份 | 固定使用 `-p echomind-tutorial`，与原项目分开 |
| Redis、ChromaDB | 使用该项目独立命名卷，不连接原服务的数据卷；不向宿主机开放数据库端口 |
| 聊天入口 | 仍为本机 `http://localhost:8000`，现有 curl 和 Python 实验无需改地址 |
| 基线文件 | 保存到练习应用容器的 `/tmp/echomind-tutorial/eval/baseline.json` |
| 模型配置 | 读取根目录 `.env`；真实模型仍需可用 Key |
| 鉴权与外部 MCP | 本机练习默认关闭；意图向量固定为 local；不自动导入演示政策 |
| Skills | 只读挂载当前 `skills/`；需要改规则时回到普通开发环境 |

练习基线不挂到宿主机：普通 `restart` 保留它，删除或重新创建应用容器会丢失它。要比较两次评测，可以在同一个容器内连续执行；要保留报告，按下面的导出步骤保存。

### 2. 启动前，先腾出 8000 端口

先完成第 02 章的 `.env` 配置并启动 Docker 引擎。如果原来的根目录应用正占用 8000，可执行：

```bash
docker compose stop echomind
```

这只停止原 Python 容器，不删除数据。原来使用叠加文件时，带齐原来的 `-f`；若运行的是宿主机 Uvicorn，则在那个终端按 Ctrl+C。不要同时让两套 Python 应用占用 8000。

在项目根目录执行：

```bash
docker compose -p echomind-tutorial -f wiki/教程/examples/compose.tutorial.yml config --quiet
docker compose -p echomind-tutorial -f wiki/教程/examples/compose.tutorial.yml up -d --build
docker compose -p echomind-tutorial -f wiki/教程/examples/compose.tutorial.yml ps
docker compose -p echomind-tutorial -f wiki/教程/examples/compose.tutorial.yml logs --tail=100 echomind
curl --noproxy '*' http://localhost:8000/health
```

健康检查通过后，继续第 08、11 章原有的 HTTP 命令即可。需要进入容器查记录时，使用同一个 `-p` 和 `-f` 前缀；根目录的 `docker compose exec` 会进入另一套服务。

第一次启动的知识库应为 0 个片段。第 08 章原样导入短规范后应为 1，重复导入相同 ID 和正文仍为 1。如果这里不是预期值，先检查是否复用了以前的练习卷，不要立即修改检索代码。

### 3. 导出要保留的结果

评测完成后，可将它的完整结果保存到项目已忽略的 `data/tutorial/`。把下方占位文字换成实际 job_id：

```bash
mkdir -p data/tutorial
curl --noproxy '*' --fail --show-error \
  http://localhost:8000/eval/jobs/替换为实际job_id \
  -o data/tutorial/eval-job.json
```

如果需要保存练习基线，先完成至少一次允许保存基线的评测，再执行：

```bash
docker compose -p echomind-tutorial -f wiki/教程/examples/compose.tutorial.yml \
  cp echomind:/tmp/echomind-tutorial/eval/baseline.json data/tutorial/baseline.json
```

文件不存在时，先看报告是否完整、是否发生回归和保存日志；不是每次评测都会写基线。下载任务结果也不会取消正在执行的任务，应等任务终态后再清理环境。

### 4. 停止、清空练习数据与恢复原服务

只是暂时停下、以后继续练习：

```bash
docker compose -p echomind-tutorial -f wiki/教程/examples/compose.tutorial.yml stop
```

下次用同一前缀执行 `start`。要从空白环境重新做一遍，确认报告已导出后，执行下面的清理命令。**它会删除这套练习的容器、Redis 卷和 ChromaDB 卷，练习中的所有聊天与知识资料都会清空。**

```bash
docker compose -p echomind-tutorial -f wiki/教程/examples/compose.tutorial.yml down -v
```

这里的项目名和配置文件不能省略。它不删除原项目的数据卷，也不删除已导出的 `data/tutorial/` 文件。需要恢复之前停下的根目录 Python 服务时，使用原来的配置执行 `docker compose start echomind`；有叠加配置时仍带齐原来的 `-f`。

本机调试时也可以仅把 Redis URL 改为另一个数据库编号、把基线路径改为练习路径，但这**不会隔离远端 ChromaDB 的知识集合**。要一起隔离聊天、资料和基线，使用上面这套独立环境更容易核对。
