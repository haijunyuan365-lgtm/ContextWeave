## 1. 先把 JSON 变成一个经过校验的请求对象

客户端发送的正文如下。JSON 是一种传递数据的文本格式：花括号包住一组键值，冒号左边是字段名，右边是值。

```json
{
  "message": "登录返回 HTTP 401，怎么处理？",
  "user_id": "reader_01",
  "conv_id": "demo-login",
  "client_request_id": "msg-001"
}
```

[ChatRequest](../../api/main.py) 定义了聊天接口接收的字段：

```python
class ChatRequest(BaseModel):
    message: str = Field(min_length=1, max_length=12000)
    client_request_id: Optional[str] = Field(default=None, min_length=1, max_length=128)
    user_id: str = "anonymous"
    conv_id: Optional[str] = None
```

把代码与 JSON 对照着看：

1. `message: str` 表示这里需要字符串；`Field(...)` 继续限制长度为 1—12000。没有传 `message`，或者传了空字符串，通常得到 422 参数校验错误。
2. `client_request_id` 可以是字符串，也可以缺省为 `None`。如果显式给字符串，长度需要是 1—128；`""` 不会被当成正常编号接受。
3. `user_id` 没传时用 `"anonymous"`。这只是默认开发标识，不等于已经验证了匿名用户身份。
4. `conv_id` 没传时是 `None`，进入 `chat()` 后再决定实际会话编号。

`Optional[str]` 可以理解为“字符串或没有值”；`None` 是 Python 表示“没有值”的专门对象，不是字符串 `"None"`。这段代码没有给 `conv_id` 增加非空长度限制，所以 `""` 会在后面的 `or` 表达式中按缺省处理。

FastAPI 根据这个模型校验正文，通过后才调用：

```python
async def chat(req: ChatRequest, http_request: HTTPRequest):
    if _orchestrator is None or _memory is None:
        raise HTTPException(503, "服务未就绪")
```

`req` 是已解析的业务正文，`http_request` 则提供 HTTP 头、中间件设置的身份等信息。`_orchestrator` 负责后续分类与角色执行，`_memory` 负责记忆；它们尚未初始化时返回 503，不继续处理消息。

还有一个小边界：`" "` 这个只有空格的字符串长度是 1，当前长度规则会放过它。不要把“有长度校验”理解成“已经排除了所有空白文本”。

## 2. 四个编号解决四个不同问题

许多重试问题来自把几个 ID 当成同一回事。先用主线请求逐个对应：

| 名称 | 主线示例 | 它回答的问题 | 由谁提供 |
| --- | --- | --- | --- |
| `user_id` | `reader_01` | 这份记忆属于谁？ | 开发请求正文，或服务端 Token 映射 |
| `conv_id` | `demo-login` | 属于这个用户的哪段连续对话？ | 客户端，未提供时服务端生成 |
| `client_request_id` | `msg-001` | 这是哪一条用户消息？ | 建议客户端在发送前生成 |
| `request_id` | 每次新执行生成的 UUID | 后端这次执行怎样查轨迹？ | 内部 `Request` 自动生成 |

UUID 是一种适合生成唯一编号的格式。教程里的 `demo-login`、`msg-001` 是为了好读；代码不要求这两个客户端字段必须采用 UUID 格式。

### 2.1 首次提问、重试、追问分别怎样填

| 操作 | `user_id` | `conv_id` | `client_request_id` | 正文 |
| --- | --- | --- | --- | --- |
| 第一次发送 | `reader_01` | `demo-login` | `msg-001` | 登录返回 HTTP 401，怎么处理？ |
| 第一次响应丢失，重发原消息 | `reader_01` | `demo-login` | **仍为 `msg-001`** | 必须仍是原正文 |
| 用户接着说“重登过了，还是不行” | `reader_01` | **仍为 `demo-login`** | **换为 `msg-002`** | 新正文 |
| 用户开始全新的对话 | `reader_01` | 换一个会话编号 | 换一个消息编号 | 新正文 |

同一消息重试要保留原编号，新的消息要生成新编号。否则服务端没有办法区分“网络重试”和“用户真的又问了一遍”。

内部 `request_id` 与客户端消息编号也不同：真正重新执行时创建新的内部请求；直接复用回执时不会创建新执行，返回的是原来的 `request_id`。后面查工具轨迹用内部编号，重试用户消息用客户端编号。

### 2.2 省略编号时，源码到底生成什么

入口在确定用户身份后执行：

```python
client_id = req.client_request_id or str(uuid.uuid4())
conv_id = req.conv_id or str(
    uuid.uuid5(uuid.NAMESPACE_URL, req.user_id + ":" + client_id)
)
```

这里 `a or b` 的意思是：`a` 有有效内容就用 `a`，否则用 `b`。

- 主线两个编号都已提供，因此 `client_id="msg-001"`、`conv_id="demo-login"`。
- 未提供客户端消息编号时，`uuid4()` 随机生成一个。下次再省略，会生成另一个，因此通常会被当作新消息。
- 未提供会话编号时，`uuid5()` 根据“最终用户 ID + 冒号 + 客户端消息 ID”生成确定性编号。同样的输入会得到同样的输出。

例如只给 `user_id="reader_01"`、`client_request_id="msg-001"`，第一次响应丢失后仍用这两个值重试，服务端会再次算出相同的会话编号。随后真正发 `msg-002` 时，应保存并传入首次响应的 `conv_id`；如果继续省略，新的客户端消息 ID 会算出另一个会话，追问就不再属于同一段对话。

`ChatResponse` 会返回 `conv_id` 和内部 `request_id`，没有单独返回自动生成的 `client_id`。所以需要可靠重试的客户端应在发送前自己生成并保存 `client_request_id`，不能拿响应里的内部 `request_id` 替代它。

## 3. Token 怎样把“我填写是谁”变成“服务端认定是谁”

只允许客户端写 `user_id`，并不能证明消息确实来自这个用户。开发时可以用它方便实验；启用鉴权后，真正的身份来自服务端配置的 Token 映射。

Token 可以理解成客户端随请求携带的一把钥匙。Bearer 是 HTTP 头的格式：

```text
Authorization: Bearer <该用户对应的Token>
```

服务端在 `ECHOMIND_API_TOKENS` 中配置“Token → 账户”。账户形状是 `{"user_id": "reader_01", "role": "user"}`，其中角色只支持 `user` 和 `admin`。Token 至少 24 个字符。可用配置示例见[附录的鉴权配置](附录-接口配置与数据字典.md#section-08)，第 02 章说明怎样把头加入请求。

### 3.1 `identity()` 有三种返回结果

[core/access.py](../../core/access.py) 的关键分支如下：

```python
raw = os.getenv("ECHOMIND_API_TOKENS", "").strip()
if not raw:
    if os.getenv("ECHOMIND_ENV", "development") == "production":
        raise ValueError("production 模式必须设置 ECHOMIND_API_TOKENS")
    return None

# 解析并校验映射之后
supplied = authorization[7:] if authorization.startswith("Bearer ") else ""
# 比较 supplied 与各个已配置 Token
# 匹配时 return account
return {}
```

三个结果的含义不能混淆：

| 返回值 | 为什么出现 | 意味着什么 |
| --- | --- | --- |
| `None` | development 且没有 Token 映射 | 没启用这套访问鉴权 |
| `{}`，空字典 | 有映射，但请求 Token 缺失或无效 | 鉴权启用了，这次身份不成立 |
| 非空账户字典 | Token 匹配成功 | 身份和角色已经由服务端映射确定 |

Python 的字典保存键值，例如 `account["user_id"]` 读取用户编号。`None` 和 `{}` 在 `if account:` 中都会表现为假，但 `account is not None` 可以把“鉴权没开启”和“已开启但认证失败”分开。这正是中间件先写后一个条件的原因。

代码用 SHA-256 摘要和 `hmac.compare_digest()` 比较 Token。摘要是把输入转成固定长度的结果，比较函数用于比较两份摘要；这段代码没有创建登录会话、刷新 Token 或管理过期时间，它只是检查请求携带的 Token 是否出现在配置映射中。

### 3.2 中间件先拦截，再把账户放入请求

`access_control()` 是 HTTP 中间件，可以理解成路由函数前的一道处理步骤：

```python
account = identity(request.headers.get("authorization", ""))
request.state.account = account
if account is not None and request.url.path != "/health" and request.method != "OPTIONS":
    if not account:
        return JSONResponse({"detail": "需要有效 Bearer Token"}, status_code=401)
    reader = request.url.path in {
        "/chat", "/search", "/knowledge/stats", "/skills", "/mcp", "/mcp/"
    }
    if not reader and account["role"] != "admin":
        return JSONResponse({"detail": "该接口需要管理员权限"}, status_code=403)
```

把三种账户结果代进去：

1. `account=None`：第一个条件不成立，不做这套访问拦截。
2. `account={}`：除了 `/health` 和 OPTIONS，返回 401，`chat()` 不会执行。
3. `account={"user_id":"reader_01","role":"user"}`：`/chat` 是白名单路径，允许进入；访问管理接口则返回 403。
4. `role="admin"`：通过身份校验后，也可以访问管理路径。

白名单按**完整路径相等**检查，`/mcp`、`/mcp/` 两项不意味着放行所有 `/mcp/...` 路径。知识写入、评测、轨迹、监控、集成调试、Swagger 文档等需要 admin。

配置本身不合法时，中间件返回 503；程序启动时也会调用 `identity("")` 校验配置。因此 production 缺少映射，或者映射无效，会使启动校验失败。`/health` 的豁免针对缺失/错误请求 Token，不能绕过无效的服务端配置。

### 3.3 `chat()` 覆盖正文中的用户编号

```python
account = getattr(http_request.state, "account", None)
if account:
    req.user_id = account["user_id"]
```

`getattr(..., None)` 表示“读取 account 属性，没有这个属性就用 None”。主线 Token 若映射到 `reader_01`，即使 JSON 里写 `"user_id":"someone_else"`，最终 `req.user_id` 也会被覆盖为 `reader_01`。

覆盖在生成缺省会话编号、查记忆、加锁之前完成。因此后面用的都是最终身份。这个顺序使有效 Token 用户不能靠修改 JSON 中的用户编号，直接切换到别人的记忆。

## 4. 两层锁：让同一会话一轮一轮处理

先设想没有锁：同一会话几乎同时收到 `msg-001` 和 `msg-002`。两次请求都读到空历史，分别调用模型，再分别保存。即使最终两条都写入，第二条回答时也不知道第一条说过什么。对于同一消息的两次重试，还可能重复调用模型或工具。

入口因此把“检查回执—读取—分类—执行—提交”放在同一会话锁范围内：

```python
async with asyncio.timeout(50), _memory.conversation(req.user_id, conv_id):
    receipt = await _memory.get_turn_receipt(req.user_id, conv_id, client_id)
    # 之后才读记忆、识别、执行、提交
```

`async def` 定义一个可以等待的函数；`await` 表示等待某个异步操作结束。等待 Redis 或模型网络响应时，事件循环可以推进其他请求。它不会让同一请求自动跳过等待，也不会自动解决两次请求同时改数据的问题。

`async with` 表示进入一个管理范围，退出时做清理；这里会在进入时加锁、退出时释放。`asyncio.timeout(50)` 给这个范围一个**总共 50 秒**的预算，包含排队、记忆读取、分类、角色执行与提交，不是每个阶段分别获得 50 秒。

### 4.1 第一层：同一 Python 进程内排队

`MemoryManager.conversation()` 先根据用户和会话计算摘要，再进入 `KeyedLocks`：

```python
digest = hashlib.sha256(
    json.dumps([self._safe_text(user_id), self._safe_text(conv_id)]).encode()
).hexdigest()
async with self._request_locks.hold(digest):
    async with redis_lease(self._redis, f"lock:conversation:{digest}"):
        await self._migrate_legacy_keys(user_id, conv_id)
        yield
```

主线中的两个值先变成列表 `["reader_01", "demo-login"]`，再编码并哈希。同一对值算出同一个锁键；不同用户或不同会话得到不同键。使用列表编码也避免简单拼接中分隔符造成歧义。

`conversation()` 由 `@asynccontextmanager` 包装，才能供外层 `async with` 使用。读到 `yield` 时，两层锁都已取得，开始运行外层 `with` 中的回执检查和聊天处理；外层处理结束后回到这里退出两层锁。所以 `yield` 不是释放锁，而是把执行位置暂时交给受锁保护的正文。

`KeyedLocks.hold()` 为同一个键提供 `asyncio.Lock()`：持有者执行，其余等待。等待者按锁的顺序排队，最后一个使用者退出后回收这个键的锁对象。它只在当前 Python 进程内有效。

### 4.2 第二层：多个后端进程共享 Redis 租约

如果有两个后端进程，进程 A 内的锁对象不会自动影响进程 B。Redis 租约用所有进程共享的键协调它们：

```python
lock = client.lock(key, timeout=120, blocking_timeout=30, thread_local=False)
if not await lock.acquire():
    raise ConversationBusyError("当前会话正在处理请求，请稍后重试")
```

租约可以理解成“带到期时间的锁”：默认最多等待 30 秒获取它，获得后有效期为 120 秒。后台续租任务每 `120 / 3 = 40` 秒延长一次；续租失败会取消持有任务并转成 `LeaseLostError`，防止已经失去锁的请求继续写入。

正常退出、异常或超时后都会尝试释放 Redis 锁，再释放进程内锁。释放异常会记录日志，不表示可以让其他请求忽略锁。

### 4.3 两次相同消息同时到达会怎样

```text
请求 A：获得两层锁 → 没查到回执 → 执行 → 提交回执 → 释放锁
请求 B：等待 A       → 获得两层锁 → 查到 A 的回执 → 直接返回原响应
```

锁本身只负责顺序，并不记住“这条消息已经处理过”；回执负责记住结果。先加锁再查回执，才能避免两个并发重试同时查到“没有回执”。不同会话的锁不同，可以同时推进。

若 A 占用时间很长，B 可能达到 Redis 获取等待上限或外层 50 秒预算。此时 B 得到 503/504，并不意味着 A 的执行一定失败。客户端仍应按原消息编号重试，由服务端检查已保存的结果。

## 5. 回执：保存“这条消息的原响应”

回执不是聊天摘要，也不是模型分类缓存。它按 `user_id + conv_id + client_request_id` 查找，记录原正文和完整响应。

`get_turn_receipt()` 的核心只有两步：

```python
raw = await self._redis.get(self.receipt_key(user_id, conv_id, request_id))
return json.loads(raw) if raw else None
```

这里形参名 `request_id` 指的是调用方传入的**客户端消息编号**。主线调用传的是 `msg-001`，不是内部 UUID。Redis 返回的是 JSON 文本，`json.loads()` 把它恢复成字典；没有数据时返回 `None`。

回执键使用用户/会话的摘要与消息编号摘要；示意内容如下。以下内部编号和耗时只是形状示例：

```json
{
  "message": "登录返回 HTTP 401，怎么处理？",
  "response": {
    "conv_id": "demo-login",
    "request_id": "本次执行的UUID",
    "response": "这里是原来生成的回答",
    "status": "success",
    "retryable": false,
    "latency_ms": 1200.0
  }
}
```

实际回执中还包括意图、角色、工具、实体等全部 `ChatResponse` 字段。`commit_turn()` 使用 `SETEX` 保存，默认到期时间为 86400 秒，即 24 小时。这是有期限的请求回执，不是永久业务去重台账。

### 5.1 逐句读入口的判断

```python
if receipt:
    if receipt["message"] != req.message:
        raise HTTPException(409, "同一 client_request_id 不能用于不同消息")
    previous = ChatResponse(**receipt["response"])
    if previous.status != "failed" or not previous.retryable:
        return render(previous)
```

按主线重试代入：

1. 查到字典，`if receipt` 成立。
2. 比较保存的正文与本次正文。比较的是完整字符串；改标点、加空格等也可能使它们不同。不同就返回 409，不尝试猜测“是不是同一个意思”。
3. `**receipt["response"]` 把字典的字段展开成 `ChatResponse` 的参数，恢复原响应对象。
4. 非 failed 的结果直接返回；failed 但不允许重试也直接返回。
5. 只有 `failed` **且** `retryable=True` 才继续往下重新读取、分类与执行。

用表格检查每一种情况：

| 回执情况 | 本次动作 | 是否新建后续执行 |
| --- | --- | --- |
| 没有回执 | 继续处理 | 是 |
| 同编号但不同正文 | HTTP 409 | 否 |
| 同正文，`success` | 返回原结果 | 否 |
| 同正文，`partial` | 返回原部分结果 | 否 |
| 同正文，`failed`、`retryable=False` | 返回原失败结果，HTTP 503 | 否 |
| 同正文，`failed`、`retryable=True` | 继续重新处理 | 是 |

`partial` 说明已有部分回答，当前实现仍把它当成该消息的结果保存和复用。同 ID 重发不会自动要求模型补全；要按实际业务情况发起新的消息。

### 5.2 复用时，哪几个值会保持原样

返回原响应意味着正文、内部 `request_id`、原 `latency_ms`、意图等均不重新计算。HTTP 中间件会重新给本次调用添加 `Server-Timing` 头，它测量本次 HTTP 处理耗时。

因此“JSON 内耗时仍为 1200 毫秒，但 Server-Timing 很短”可以是正常的回执复用。不要把原执行耗时当成本次查 Redis 的耗时。分类缓存只复用识别结果；回执则复用整轮最终响应，两者的作用范围不同。

## 7. 先看 HTTP 状态，再看业务状态

HTTP 状态告诉你这次接口调用怎样结束；`ChatResponse.status` 告诉你业务执行有没有完整结果。两者需要一起读。

```python
def render(reply):
    if reply.status == "failed":
        return JSONResponse(reply.model_dump(), status_code=503)
    return reply
```

这段代码决定：`success` 和 `partial` 通常以 HTTP 200 返回；`failed` 以 HTTP 503 返回，但正文仍是完整的 `ChatResponse`。

| 看到的结果 | 怎样理解 | 重试时注意什么 |
| --- | --- | --- |
| 422 + 参数错误 | 正文未通过模型校验 | 修正字段，未进入正常聊天处理 |
| 401 + `detail` | EchoMind 请求 Token 缺失/错误 | 先修正请求头；与用户正文的登录 401 区分 |
| 403 + `detail` | 当前角色不允许访问该接口 | 检查需要的角色 |
| 409 + `detail` | 同客户端编号对应了不同正文 | 新消息用新编号；原消息重试保持原文 |
| 200 + `status=success` | 得到完整业务结果 | 相同 ID 会复用 |
| 200 + `status=partial` | 已有部分结果，例如模型输出被截断 | 相同 ID 仍复用该结果 |
| 503 + `status=failed` | 编排得到失败响应 | 继续看 `retryable` 与 `error_code` |
| 503 + `detail` | 未就绪、会话繁忙或锁失效等入口问题 | 没有完整业务响应可供解释 |
| 504 + `detail` | 本轮总预算超时 | 原消息沿用原客户端编号重试 |

当前单角色失败的 `retryable` 会根据 `req.tool_attempts` 中的工具是否都标记为 `retry_safe` 判断。如果尚未尝试任何工具，`all([])` 在 Python 中为真；如果尝试过不安全工具，则不会允许简单重放。这里的“安全”专指重试安全属性，不代表模型回答经过业务核验。

客户端断线或 504 不能证明模型、工具或者提交从未发生。保留原消息编号，让下次请求先查回执，才能处理“服务端完成了，客户端还不知道”的情况。

## 8. 有副作用的工具，为什么要先写一张失败回执

副作用是“调用后改变外部状态”，例如提交退款、修改地址。当前主线错误码查询是只读工具，不触发这一保护。这里解释扩展到写工具时已有的机制。

入口定义了 `before_unsafe_tool()` 回调。回调不是当场调用，而是先挂在内部请求上，等工具执行器准备执行不安全工具时调用：

```python
async def before_unsafe_tool(name):
    marker = ChatResponse(
        conv_id=conv_id, request_id=orch_req.request_id,
        response="该请求涉及可能修改数据的工具，请先核验执行结果再发起新的请求。",
        intent=intent_result.intent.value, agent_type="unknown",
        escalated=False, latency_ms=(time.monotonic() - started) * 1000,
        status="failed", retryable=False, error_code="tool_outcome_unknown",
    )
    await _memory.commit_turn(
        req.user_id, conv_id, client_id, req.message, marker.model_dump()
    )
orch_req.before_unsafe_tool = before_unsafe_tool
```

调用顺序在 [BaseAgent._call_llm](../../agents/agent_orchestrator.py) 中：校验工具参数 → 记录工具尝试 → `await req.before_unsafe_tool(name)` → 调用实际处理函数。

具体设想：

```text
先保存“结果未知，不允许自动重试”的回执
  → 调用外部写工具
  → 正常得到最终结果并提交时，正式回执覆盖标记
```

如果进程在工具产生改变后崩溃，或者处理超时、尚未提交最终响应，标记仍在。下次同 ID 重试读取它，得到 `failed + retryable=False + tool_outcome_unknown`，不会直接再次执行该工具。

标记不能证明工具成功，也不能证明工具失败；它专门表达“无法从这次请求记录确认最终结果”。在标记后、实际工具调用前崩溃也会留下它，这是为避免盲目重放而选择的保守边界。

此机制还需要外部业务系统配合：写操作使用自己的幂等编号，并提供结果查询。换一个客户端消息编号虽能形成新请求，却不能代替核对上次写操作结果。更完整的工具执行顺序见[第 07 章](07-Agent路由Skills与工具执行.md)。

## 实验：相同消息重试与编号冲突

先按第 02 章启动后端。下面的 Python 程序在项目根目录执行，使用标准库发送三次请求；**首次会使用真实模型**，后两次只有在首次形成可复用回执后才会直接返回。程序创建随机会话，不覆盖上面的 `demo-login` 会话。

```bash
python3.12 - <<'PYCODE'
import json
import os
import urllib.error
import urllib.request
import uuid

payload = {"message": "登录返回 HTTP 401，怎么处理？",
           "user_id": "reader_retry", "conv_id": "retry-" + uuid.uuid4().hex,
           "client_request_id": "same-message"}
headers = {"Content-Type": "application/json"}
if os.getenv("ECHOMIND_TUTORIAL_TOKEN"):
    headers["Authorization"] = "Bearer " + os.environ["ECHOMIND_TUTORIAL_TOKEN"]
opener = urllib.request.build_opener(urllib.request.ProxyHandler({}))

def send(body):
    request = urllib.request.Request("http://localhost:8000/chat",
        data=json.dumps(body).encode(), headers=headers, method="POST")
    try:
        with opener.open(request, timeout=65) as response:
            return response.status, json.load(response)
    except urllib.error.HTTPError as error:
        return error.code, json.load(error)

code, first = send(payload)
assert code == 200, (code, first)
assert first["status"] in {"success", "partial"}, first
code, repeated = send(payload)
assert code == 200 and repeated == first, (code, repeated)
code, conflict = send({**payload, "message": "换一个问题"})
assert code == 409, (code, conflict)
print("PASS：响应回执复用；同编号换消息返回409")
print("request_id:", first["request_id"])
PYCODE
```

程序的三次请求分别验证：

1. 原消息正常处理并形成可复用回执；HTTP 200 且业务状态是 success/partial。
2. 原编号、原正文再次发送；完整 JSON 应与首次相等，包括 `request_id`、回答和原 `latency_ms`。
3. 原编号改成新正文；应返回 409，不能把新问题当成旧结果返回。

预期末尾输出 `PASS：响应回执复用；同编号换消息返回409`。`assert` 是 Python 的检查语句，条件不成立时停止并显示信息；不是服务端功能。

第一条若得到 401，检查教程 Token；若得到 503/504，按[第 12 章](12-测试与故障排查.md)检查服务与模型，不能把“允许重试的失败又执行了一次”当成成功的回执复用。HTTP 超时设为 65 秒，是为了让客户端有机会读到后端的 50 秒预算错误。

完成后试着回答：追问更换的是哪个编号？failed 且 retryable 为 true 会提前返回吗？答案是更换 `client_request_id`，保持同一 `conv_id`；允许重试的失败会继续重新处理。下一章就从这里的 `get_context()` 开始，看看后端具体读回了什么。
