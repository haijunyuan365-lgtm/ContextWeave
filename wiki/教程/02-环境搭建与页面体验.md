## 先选最短路径，再展开配置

首次体验用 Docker，研究源码时再切到宿主机 Python。先按这个顺序完成：

```text
确认Docker引擎运行
  → 复制并填写.env中的模型配置
  → docker compose up -d --build
  → GET /health
  → POST /chat
  → 沿用conv_id、换消息ID发追问
```

健康接口只证明启动完成；第一次聊天才检验模型调用。使用 curl 就能走通 Python 链路，也可通过 FastAPI 的接口文档页面提交请求。

## 启动前先完成这三项检查

```bash
docker --version
docker compose version
docker info > /dev/null
```

前两条确认命令可用，第三条确认 Docker 引擎正在运行。若提示无法连接 `docker.sock`，先启动 Docker Desktop；这时还没有进入项目代码。

| 要体验什么 | 需要准备什么 | 成功时检查哪里 |
| --- | --- | --- |
| 只学当前 Python 后端 | 当前仓库、Docker、有效模型配置 | `8000/health` 与 `8000/chat` |
| 在编辑器里调试 Python | Python 3.12、开发依赖、可达的 Redis/ChromaDB | 第 8 节的宿主机启动方式 |

如果已有需要保留的数据，使用[附录的独立练习环境](附录-接口配置与数据字典.md#tutorial-environment)。它仍运行本项目的 Python 后端，只把练习数据分开放。

### 先弄清 Docker 在这里做什么

Docker把程序及依赖装成“镜像”，再用镜像启动一个正在运行的“容器”。你可以把镜像理解为运行材料，容器理解为一次真正运行起来的程序环境。修改源码后旧镜像不会自动改变，所以后面需要重新构建。

Compose读取 `docker-compose.yml`，按其中的“服务”定义一起启动容器、连接网络、挂载数据。服务名是命令里使用的名字，例如 `echomind`；当前对应的容器名是 `echomind-app`。执行 `docker compose logs echomind` 时用前者，不能随意把二者混用。

“卷”和目录挂载让数据保存在容器之外。重建应用容器不等于重新建立一个空数据库。因而重复运行相同的教程消息，仍可能读到以前的历史和回执。

## 模型配置怎样被 Python 读到

首次创建配置文件时使用：

```bash
cp -n .env.example .env
```

`-n` 表示已有 `.env` 时不覆盖。编辑其中的模型配置，使用你自己的凭据和可调用模型：

```dotenv
ANTHROPIC_API_KEY=填写模型服务的Key
ANTHROPIC_BASE_URL=https://api.deepseek.com/anthropic
ANTHROPIC_MODEL=填写账号当前可调用的模型ID
ECHOMIND_ENV=development
CHROMA_HOST=chromadb
CHROMA_PORT=8000
```

这不是一段要直接粘贴进终端运行的Python代码，而是要写入 `.env` 的配置示例。“填写...”是占位说明，必须换成实际值，不能原样作为Key或模型名使用。

`.env` 是文本配置文件；后面的 `.venv` 是本机Python虚拟环境目录。这两个名字相近，但用途完全不同。修改前者改变应用配置，激活后者改变终端使用的Python解释器。

这里使用 Anthropic Messages 兼容协议。变量名虽然以 ANTHROPIC 开头，但服务地址可以指向兼容该协议的提供方。模型 Key 只交给后端，不放到网页源码里。

API_KEY是模型服务验证调用资格的凭据，BASE_URL是要把模型请求发到哪个服务地址，MODEL是让该服务使用哪个模型。三者应匹配：只换模型名，却仍指向不支持它的服务地址，聊天也可能失败。

项目使用Anthropic Python SDK作为请求客户端。SDK是帮助Python发送和解析请求的库，不是把模型权重下载到本机的模型程序。`/chat`处理过程里真正生成答案的步骤仍需要访问配置的模型服务。

配置进入 Python 的位置是 [api/main.py](../../api/main.py) 的 `_anthropic_cfg()`：

```python
def _anthropic_cfg() -> Dict[str, Any]:
    key = os.getenv("ANTHROPIC_API_KEY", "")
    if not key:
        raise RuntimeError("未设置 ANTHROPIC_API_KEY")
    cfg: Dict[str, Any] = {
        "api_key":  key,
        "model":    os.getenv("ANTHROPIC_MODEL", "claude-3-5-sonnet-20241022").strip(),
    }
    base_url = os.getenv("ANTHROPIC_BASE_URL", "").strip()
    if base_url:
        cfg["base_url"] = base_url
    return cfg
```

`os.getenv()` 从进程环境读取配置。没有 Key 就在启动时失败；有 Key 则把它和模型名放进 `cfg`。如果配置了 base URL，也加入字典；没有时使用 SDK 的默认地址。

调用链可以具体读成：启动时 `load_dotenv()` 把 `.env` 中配置补入进程环境，`_anthropic_cfg()` 从环境取出值，`lifespan()` 再把这份cfg传给识别器、编排器和评测器。宿主机启动命令已经设置的环境值通常优先于文件，因为 `load_dotenv()` 默认不会覆盖已有环境。

这段函数只检查有没有配置，不会提前发一条模型请求。因此配置文件存在、程序启动正常，仍不能保证模型 Key 的权限或额度有效。要真正经过模型调用，需要发送一条聊天。

### 两个环境开关，分别控制什么

`.env.example` 同时存在 `APP_ENV` 和 `ECHOMIND_ENV`。鉴权是否强制、ChromaDB 断连是否允许本地降级、是否导入演示政策，读取的是 **`ECHOMIND_ENV`**；`APP_ENV` 在 `python api/main.py` 入口控制开发 reload，不能代替前者。Docker 的默认启动命令是 Uvicorn，不会因为 `APP_ENV=development` 自动开启 reload。

首次只体验本地流程，可以在 `.env` 设置 `MCP_EXTERNAL_ENABLED=false` 和 `INTENT_EMBEDDING_PROVIDER=local`，减少外部依赖；模型回复仍需要有效的 `ANTHROPIC_API_KEY`。前者仅关闭外部 MCP 客户端连接，不关闭本地知识库或 `/mcp/` 服务。向量配置详见第 06 章。

如果已有服务开启了应用 Token，命令行实验使用以下变量传递访问身份：

```bash
export ECHOMIND_TUTORIAL_TOKEN='替换为已配置的应用访问Token'
```

这是教程命令使用的客户端变量，服务不会读取它作为鉴权配置。服务端映射由 `ECHOMIND_API_TOKENS` 配置；它与模型 Key 分开。聊天可以使用 user 身份，导入知识、评测和轨迹查询需要 admin 身份。未启用应用鉴权的本机环境不用设置该变量。

## 启动 Python 后端

仅运行当前 Python 项目：

```bash
docker compose config --quiet
docker compose up -d --build
docker compose ps
docker compose logs --tail=100 echomind
```

`config --quiet` 先校验 Compose 配置且不输出展开后的凭据。`--build` 构建镜像，`-d` 在后台运行，`ps` 显示服务状态，`logs` 显示 Python 服务最近日志。第一次构建可能需要下载依赖和向量模型。

这四条命令不是四种不同启动方法：第一条检查配置；第二条实际构建和启动；第三条检查结果；第四条查看后端发生了什么。若第二条已经报错，先读错误，不要把后面健康接口不通当作新的业务故障。

`docker compose ps` 中服务可能经历starting，再进入healthy。healthy表示配置的健康检查通过，不是说每个模型问题都能回答。日志里可以检查应用是否出现“EchoMind 已就绪”；若持续退出或unhealthy，再看最早的初始化错误。

当前根目录配置把 Python API 绑定到本机 8000，ChromaDB 绑定到 8001。Docker 容器之间使用服务名访问，宿主机通过端口映射访问。附录的独立练习配置只开放 Python 8000，不开放数据库端口。

### 为什么同一个数据库有两个地址

```text
Python容器 → chromadb:8000 → ChromaDB容器
宿主机Python → 127.0.0.1:8001 → Docker端口映射 → ChromaDB容器的8000
```

`localhost`指“当前程序自己所在的环境”。在Python容器里，它指Python容器，不是Redis容器；在本机浏览器里，它指宿主机。容器网络提供redis、chromadb等服务名，本机进程则通过已映射端口访问。

因此不能将Docker内部的 `CHROMA_HOST=chromadb` 原样拿到宿主机调试。第8部分会明确覆盖本机地址。Redis同理，只是本机与容器的映射端口都恰好是6379，名字仍不能混用。

## 确认 Python 接口可访问

先发一条不请求模型的健康检查：

```bash
curl --noproxy '*' -i http://localhost:8000/health
```

`--noproxy '*'` 让这一条本地请求绕过系统代理；`-i` 让你同时看到 HTTP 状态码。成功时应看到 HTTP 200，JSON 中有 `"status":"ok"`。开启应用鉴权时，健康检查也允许不带 Token。

- 连接被拒绝：通常还没有进程监听 8000，先看 `docker compose ps` 和应用日志。
- 返回 503：先看启动是否完成、依赖是否连接成功。
- 返回 200：说明应用就绪，下一步发聊天，验证模型凭据和实际处理。

浏览器打开 [Python 接口文档](http://localhost:8000/docs) 可以查看参数。未启用鉴权时，还能展开 `POST /chat`，点 **Try it out**，填写下一节的 JSON，再点 **Execute**。启用鉴权后文档页面本身需要管理员身份，优先用下一节的 curl。

本教程都直连 8000，请求路径写 `/chat`，不添加网页代理前缀。

## 发出后面所有代码讲解使用的请求

下面的 curl 直接调用 Python，可复制执行。未启用应用 Token 时无需设置客户端变量；已启用时先设置有效的 `ECHOMIND_TUTORIAL_TOKEN`，命令会通过 `Authorization` 请求头发送它。

```bash
curl --noproxy '*' -i -H "Authorization: Bearer ${ECHOMIND_TUTORIAL_TOKEN:-}" http://localhost:8000/chat \
  -H 'Content-Type: application/json' \
  --data-binary @- <<'JSON'
{
  "message": "登录返回 HTTP 401，怎么处理？",
  "user_id": "reader_01",
  "conv_id": "demo-login",
  "client_request_id": "msg-001"
}
JSON
```

`Content-Type` 告诉 FastAPI 按 JSON 解析正文。`--data-binary @-` 从后面的文本读取请求体，curl 因带了正文而使用 POST。`-i` 额外显示状态码和响应头，便于看 `Server-Timing`。

`<<'JSON'` 到下一行独立的 `JSON` 之间，是终端传给curl的完整正文，最后的标记不是请求数据。这个写法可以保留中文与引号，避免复杂JSON在单行shell字符串中难以阅读。复制时应连同结束标记一起复制。

`Authorization`里的 `${ECHOMIND_TUTORIAL_TOKEN:-}` 是shell取变量值的写法；没有设置时为空。未启用应用鉴权的本机环境仍可访问，启用后则必须事先放入有效访问Token。它不会从模型Key自动生成。

执行后先看最前面的HTTP状态，再看JSON字段。200表示拿到了正常接口结果，但status仍可能是partial；503可能是结构化失败，也可能只有detail。不要只凭终端显示了一段中文就判断所有步骤成功。

未启用应用鉴权时，也可以在 [Python 接口文档](http://localhost:8000/docs) 的 POST `/chat` 中提交同一份 JSON。启用鉴权后，文档页面自身也要求 admin 身份；当前应用没有给 Swagger 配置 Bearer 的 Authorize 流程，优先使用带请求头的 curl。

不要把教程里的编号用于每条新消息。下面章节为了方便逐段对照，重复引用的是这同一条请求。

## 先读懂最关键的返回字段

模型生成的正文、置信度和工具选择会变化。下面只是说明返回形状，省略其他字段，`执行时生成的UUID` 不是固定返回值：

```json
{
  "conv_id": "demo-login",
  "request_id": "执行时生成的UUID",
  "response": "401通常与认证有关，可以先检查登录状态及令牌有效期。",
  "intent": "technical_login",
  "agent_type": "technical",
  "tools_used": ["lookup_error_code"],
  "status": "success",
  "retryable": false
}
```

先看 `status` 与正文，再看处理路径。`intent` 是识别出的诉求类别，`agent_type` 是这一单角色路径的处理角色，`tools_used` 表示执行返回的工具名。当前这条路径没有查知识库，所以本地错误码查询不能被解释为知识库检索。

`request_id` 用于查这次内部执行的轨迹，和客户端发来的 `msg-001` 不是同一个编号。`conv_id` 用于继续这段对话。接口还有 partial 和 failed 状态，具体保存与重试规则在第 04、09 章解释。

如果客户端只是断线后重发同一条消息，继续使用 `msg-001`。如果要追问“重登过了，还是不行”，使用新的消息编号：

```json
{
  "message": "重登过了，还是不行",
  "user_id": "reader_01",
  "conv_id": "demo-login",
  "client_request_id": "msg-002"
}
```

这样后端才知道：这仍是同一段对话，但需要处理一个新的问题。教程中的空会话条件只适用于首次使用这组用户与会话；重复运行可能已经有历史或回执。

上面的JSON仍要通过POST发送，单独复制JSON到终端不会调用后端。可直接执行下面这一条，与第一次请求相比保留用户和会话，修改正文与客户端消息ID：

```bash
curl --noproxy '*' -i -H "Authorization: Bearer ${ECHOMIND_TUTORIAL_TOKEN:-}" \
  -H 'Content-Type: application/json' http://localhost:8000/chat \
  --data-binary @- <<'JSON'
{
  "message": "重登过了，还是不行",
  "user_id": "reader_01",
  "conv_id": "demo-login",
  "client_request_id": "msg-002"
}
JSON
```

若收到409，先确认你是否以前用msg-002发过另一句正文；不要只改提示词重试。为了反复体验，可以改用尚未使用的消息ID，或者新建会话从头开始。第03章讲首次请求的代码回放，第05章解释这类追问如何得到前文。

## 改了代码或配置，为什么运行结果没变化

先确认当前使用的启动配置。下文短命令针对根目录 Compose；使用监控鉴权叠加文件时，要继续带齐原来的 `-f`。使用附录的独立练习环境时，改用附录里的项目名和配置文件。

当前 Dockerfile 会把 Python 代码复制进镜像。因此修改源码后，需要构建并创建新应用容器：

```bash
docker compose up -d --build --no-deps echomind
```

只改环境变量时，重新创建即可读取新配置：

```bash
docker compose up -d --force-recreate --no-deps echomind
```

`restart` 只是重新启动已有容器，通常仍使用创建时的环境与代码。使用叠加配置时，继续带齐原来的 `-f` 参数。

Skill 正文采用目录挂载，但进程保存着已解析对象，修改后需要 POST `/skills/reload`。知识文档则已经导入数据库，修改本地 Markdown 不会自动更新库，需要重新走导入接口。这些生效方式的差异来自数据实际存放的位置。

## 本地调试与停止服务

若想在编辑器里给 Python 函数打断点，可以使用宿主机 Python 3.12，与项目 Dockerfile 的版本一致。在项目根目录创建并进入虚拟环境：

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-dev.txt
```

第一条创建隔离的Python环境，不启动EchoMind。第二条改变当前终端的PATH，让python/pip指向这份环境。第三条用同一解释器安装开发依赖；requirements-dev会继续包含运行依赖，还加上pytest等测试工具。

安装以后可以用 `python -V` 和 `python -m pip --version` 核对解释器与pip。看到No module named某个包时，先确认当前解释器和依赖是否匹配，不要首先修改模型Key。Docker容器的Python环境和这份本机虚拟环境是分开的，容器安装过不代表本机已安装。

进入虚拟环境后，`python` 指向其中的解释器。若本机还没有 `python3.12`，需要先安装这个版本；前面的 Docker 启动方式不依赖本机 Python。

宿主机进程要通过已映射的端口访问依赖，不能直接使用容器内部的 `redis`、`chromadb` 服务名。若从头开始调试，可先运行 `docker compose up -d redis chromadb`，只启动依赖。若之前启动过完整后端，运行 `docker compose stop echomind` 释放 8000 端口，然后在宿主机启动。下面假设 Redis 和 ChromaDB 容器已运行，并使用 Compose 示例中的 Redis 默认密码 `echomind123`；改过 `REDIS_PASSWORD` 时，把 URL 中的密码同步换成实际值。先确保 8000 端口未被另一个 Python 实例占用，再启动：

```bash
REDIS_URL='redis://:echomind123@127.0.0.1:6379/0' \
CHROMA_HOST=127.0.0.1 \
CHROMA_PORT=8001 \
CHROMA_PERSIST_DIRECTORY=./data/chroma \
EVAL_BASELINE_PATH=./data/eval/baseline.json \
PROMETHEUS_PORT=0 \
python -m uvicorn api.main:app --host 127.0.0.1 --port 8000
```

这些变量只覆盖当前启动命令的环境，不会改写 `.env`。项目调用 `load_dotenv()` 时保留已存在的环境值，模型配置仍可从 `.env` 读取。相对数据路径以项目根目录为起点；`PROMETHEUS_PORT=0` 避免本地调试时另开一个指标监听端口。

在编辑器中调试时，选择 `.venv` 解释器，运行模块设为 `uvicorn`，参数设为 `api.main:app --host 127.0.0.1 --port 8000`，并把上面六个环境变量填到调试配置的环境字段。

Uvicorn是接收HTTP请求并运行FastAPI应用的服务程序。`api.main:app`表示导入api/main.py中的app对象；这与直接打开文档或运行一个普通工具函数不同。终端出现服务监听地址后才去调用/chat，停止本机进程可在该终端按Ctrl+C。

停止 Compose 环境使用 `docker compose down`；如果用了叠加配置，也带齐相应 `-f`。普通 down 保留命名数据卷；加 `-v` 会删除卷数据。评测任务记录属于进程内状态，并不因数据卷保留就自动恢复。

下一章带着这份 JSON 看一轮请求的时序和中间对象；第 04—09 章再分别展开入口、上下文、执行与提交的代码。

## 本章检查点

完成启动后，至少确认以下三件事再进入源码：

1. `/health` 返回 `status=ok`。这证明启动完成，不证明模型凭据有效。
2. 第一条 `/chat` 返回正文，查看 HTTP 状态和 `status`，保存 `conv_id`、`request_id`。
3. 用同一 `conv_id`、新的 `client_request_id` 发追问；若要重新观察空会话，用新的用户和会话编号，避免已有画像、历史或回执影响结果。

默认 Compose 还有本机 Nginx 入口 `http://localhost` 和 Prometheus `http://localhost:9090`。80 端口由 Nginx 代理 Python API；教程聊天仍直连 8000，Prometheus 页面用于观察指标。
