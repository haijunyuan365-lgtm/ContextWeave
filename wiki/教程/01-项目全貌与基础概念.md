## 1. 用户只问了一句话，后端为什么还有这么多工作

假设用户在聊天页面输入：

> 登录返回 HTTP 401，怎么处理？

用户希望得到的是明确的含义和下一步，例如“401 与认证失败有关，先检查登录状态与凭据有效期”。如果还缺少运行环境，系统应继续问必要信息，而不是直接断定“你的 Token 已经过期”。

EchoMind 用这个客服场景演示一个 Agent 应用。它要完成的不只是写出一段文字，还要把问题交给合适的角色，取得可用依据，保存这轮对话，供下一次追问使用。

### 先解释 HTTP、接口和 JSON

**HTTP** 是浏览器与服务之间发送请求、接收响应的一种方式。**接口（API）** 是后端提供的一个处理入口，比如 EchoMind 的 `/chat`。客户端向这个入口发送问题，后端返回结果。

`POST /chat` 可以读成“用 POST 方法把一份内容交给聊天入口”。POST 是请求方法，`/chat` 是路径，两者合起来决定后端运行哪个处理函数。直接访问网页和提交聊天消息可以是不同请求。

**JSON** 是这份内容在网络上传输时使用的文本格式。后端接收的不是页面里那个聊天气泡，而是类似下面的请求体：

```json
{
  "message": "登录返回 HTTP 401，怎么处理？",
  "user_id": "reader_01",
  "conv_id": "demo-login",
  "client_request_id": "msg-001"
}
```

逐项代入这个例子：

- `message` 是这一次具体说了什么。
- `user_id` 区分说话的人，示例是 `reader_01`。启用应用鉴权时，后端会使用 Token 映射中的可信身份，客户端不能仅改这个字段就冒充别人。
- `conv_id` 区分这个人的不同对话。当前登录问题属于 `demo-login`，后面的追问通常继续沿用它。
- `client_request_id` 区分一条消息。网络断线重发这条消息时仍用 `msg-001`，新说一句话时换成新的编号。

这里的编号用于解释过程，不是必须使用的固定值。真正操作时，你可以使用自己的用户、会话和消息编号。

### 为什么这里有两个“401”场景

用户原文中的 HTTP 401，指的是他自己的登录问题；如果调用 EchoMind 的 `/chat` 也返回 HTTP 401，那是本应用访问身份没有通过。这两个401可能出现在不同系统中，排查位置也不同。

后续教程会用返回状态、响应体和工具轨迹区分它们。先记住：用户说“遇到了401”和“EchoMind接口返回401”不是同一条错误记录。

## 2. 模型、Agent、工具：分别是谁在做什么

### 模型：根据收到的内容理解和生成

本项目通过 Python 客户端请求外部模型服务。程序把文字、处理规则和工具说明发送过去，模型返回分类、答复，或者想调用的工具。

模型看不到整个 Python 进程的所有变量。它不知道 Redis 中刚保存了哪些消息，也不会因为仓库中有一个函数就自动执行它。程序必须把需要的信息明确放入模型请求。

当模型返回“我想查询401”，这仍是它生成的一段结构化请求，查询尚未发生。

### Agent：准备输入并组织执行的 Python 对象

当前项目中的 Agent 可以先理解为一个负责某种工作的 Python 对象。比如 `TechnicalAgent` 负责技术支持：准备技术角色规则，带上当前问题和可用工具，请求模型，接住工具请求，再把真实结果交回模型。

“对象”指的是按某个类创建出来的一份可操作实例。类 `TechnicalAgent` 规定它具备什么行为；创建的实例持有本次应用所用的模型客户端、规则和统计。后续 `agent.handle(req)` 就是在让这个实例处理内部请求。

不同角色可以使用同一个外部模型，但输入规范和工具范围不同。它们没有因为类名不同就各自训练出一个新模型。

### 工具：程序真的能执行的函数

工具是登记给 Agent 的具体能力。当前 `lookup_error_code` 根据错误码查一张本地解释表，`compare_amounts` 做金额算术，知识搜索工具读取已导入的资料。

模型看到的是工具名称、用途和参数格式。Python 保存实际函数，并在检查工具名与参数以后执行。这就是工具调用与“模型在文字里声称做过什么”的区别。

### 把三者接成一次完整往返

为说明程序路径，我们假设模型确实选择了错误码工具：

```text
① TechnicalAgent：把问题和lookup_error_code的说明发给模型
② 模型：返回工具名lookup_error_code，参数error_code="401"
③ TechnicalAgent：检查名称与参数，调用对应Python函数
④ Python函数：返回“认证失败”、排查方向、未检查服务端日志
⑤ TechnicalAgent：把这个字典作为工具结果发回模型
⑥ 模型：结合原问题和实际结果，生成用户能读懂的建议
```

同一轮聊天里可能请求模型多次。第一次决定需要工具，第二次结合工具结果回答；它们仍然服务于最初那一条用户消息。

真实模型也可能直接回答，不调用工具。后续走读会明确指出固定的教学路径，不把它说成每次运行必然出现的结果。

## 3. 拆开一个完整的真实工具

下面是 [agents/tools.py](../../agents/tools.py) 中 `lookup_error_code()` 的完整函数。这里保留四种错误码和未知码分支，方便你看清同一段代码怎样处理不同输入；导入和工具登记在第 07 章展开。

```python
def lookup_error_code(req: Request, args: Dict[str, Any]) -> Dict[str, Any]:
    """技术工具：解释常见错误码的排查方向，不声称读取了服务端日志。"""
    code = str(args.get("error_code", "")).upper().strip()
    mapping = {
        "401": ("认证失败", ["确认 Token/API Key 是否过期", "确认请求时间戳和签名", "确认账号登录状态"]),
        "403": ("权限不足", ["确认账号或套餐权限", "确认资源权限和 IP 白名单"]),
        "404": ("资源或路径不存在", ["确认接口路径和环境", "确认资源标识是否正确"]),
        "500": ("服务端处理异常", ["记录 request_id 和发生时间", "检查依赖服务、参数格式和服务端日志"]),
    }
    meaning, steps = mapping.get(
        code,
        ("暂未识别的错误码", ["补充完整错误信息、发生时间和运行环境"]),
    )
    return {
        "error_code": code,
        "meaning": meaning,
        "next_steps": steps,
        "server_log_checked": False,
    }
```

### 第一步：函数接收两份信息

`req` 是程序整理好的本轮工作请求，里面有原问题、用户、背景和实体。`args` 是模型针对这次工具填写的参数，例如：

```python
args = {"error_code": "401"}
```

字典用“键→值”存数据。`"error_code"` 是键，`"401"` 是它的值；这里401是字符串，不是整数。实际 schema 要求字符串，参数不符合时会在函数调用前被拒绝。

这个函数的实现没有读取 req，主要使用 args。保留统一的两个参数，是为了让其他需要读取请求背景的工具也使用相同调用形式。

### 第二步：把输入整理成便于查表的形式

```python
code = str(args.get("error_code", "")).upper().strip()
```

`get()` 从字典取值，找不到键时取第二个参数的默认空字符串。`str()` 转成字符串，`upper()` 统一大小写，`strip()` 去掉两端空格。输入 `" 401 "` 时，最后的 code 是 `"401"`。

这些是格式整理，还没有识别真实故障原因，也没有访问外部日志。

### 第三步：查本地表，找不到时使用默认建议

mapping 的每个值包含两个元素：含义文字和步骤列表。比如401对应“认证失败”和三条检查方向。

```python
meaning, steps = mapping.get(
    code,
    ("暂未识别的错误码", ["补充完整错误信息、发生时间和运行环境"]),
)
```

这里保留了真实默认值。查到401时，把第一个元素放进 meaning，把第二个放进 steps；查不到时，用“暂未识别的错误码”和补充信息提示。这叫把一组返回值分别接住。

### 第四步：return 把结果交还调用方

代入固定参数 `{"error_code":"401"}`，完整返回字典为：

```json
{
  "error_code": "401",
  "meaning": "认证失败",
  "next_steps": [
    "确认 Token/API Key 是否过期",
    "确认请求时间戳和签名",
    "确认账号登录状态"
  ],
  "server_log_checked": false
}
```

`return` 结束这个函数并交回字典。它没有直接把字典显示到网页，也没有自动再调用模型；这些事情由外面的 Agent 循环继续完成。

`server_log_checked=false` 是一个明确事实：当前工具没检查用户系统的日志。模型收到它以后，应给排查方向，不能把“可能是凭据过期”升级为“已检查并确认凭据过期”。

## 4. 有了模型和工具，其他模块为什么还需要

### 第二轮追问，引出了记忆

第一轮回答后，用户说“重登过了，还是不行”。只把这句话单独发给模型，它不知道用户重登哪个系统、前面看到了什么错误。

所以应用在第一轮把问答保存下来，第二轮重新读取，组织成背景交给模型。**记忆**在这里是应用的读写过程，不是模型服务自动、永久记住了用户。

Redis 是快速键值存储，当前用于近期消息、业务状态和回执。ChromaDB 是向量存储，当前保存可按内容检索的历史摘要、用户画像和知识文档。两个存储怎样分工，在第 05、08、09 章逐步展开。

### 不同业务问题，引出了分类和路由

有人问登录故障，有人问退款和发票。先识别问题类型，再选择角色，能让每个角色带上更合适的规则和工具。

`IntentRecognizer` 返回“问题属于哪类”，这是**意图识别**。`AgentOrchestrator` 根据分类、关键词、字段和可用性选择“交给谁处理”，这是**编排与路由**。前者产生信息，后者组织执行。

### 公司自己的规范，引出了知识检索

模型可能知道401的一般含义，却不知道公司最新的内部处理规则。应用可以先查已导入文档，把相关段落交给模型再回答。这种做法叫 **RAG（检索后生成）**。

**Embedding（向量表示）**是把文字转换成一组数字，用于比较接近程度。你可以先理解为数据库有一种按内容找相近段落的方法；第 06、08 章再解释数字怎么比较，以及它的局限。

**MCP**是一种连接工具服务的协议。当前项目既能通过客户端接外部工具，也能把本地知识库提供给其他客户端。它解决“不同系统怎么对接工具”，RAG解决“怎样利用资料回答”，二者不是同一个概念。

### 重发、故障和修改，引出了可靠性与验证

页面断线重发时，回执帮助取回已完成响应；同会话消息同时到达时，会话锁让它们按顺序读取和提交。专业角色持续失败时，监控帮助暂时回退，并在之后探测恢复。

改了规则或提示词以后，评测用固定输入重新执行，再检查路径和回答质量。负责评分的模型对象叫 Judge；给它少量评分示例叫 Few-shot，不代表重新训练模型。

上面每个模块都从一个具体问题出现。首次阅读不必同时掌握全部实现，后面沿请求顺序一个个进入。

## 6. 看到“成功”，怎样知道实际完成了什么

本项目能运行分类、角色分工、工具调用、知识检索、记忆、监控和评测。错误码工具给建议，账单工具查字段和算金额；这些都是具体、可观察的程序能力。

但“完成了本轮建议生成”与“完成了用户账号修复”是不同结果。`status="success"` 描述本轮执行是否完整，真正做了什么还要看工具能力、真实返回与最终正文。生成交接文字也不代表人工已经接单。

还要分清两个名为Token的用法：访问Token/API Key是请求服务时使用的凭据；模型的token预算是文字输入输出的计量。配置访问凭据不会自动增加输出预算，增大max_tokens也不会改变用户权限。

如果这些区别能讲清，就可以进入第 02 章实际运行，再到第 03 章跟完整链路。下面的小实验不需要任何外部服务，可以先验证最简单的一项能力。

## 动手确认：错误码工具究竟查了什么

在项目根目录执行，使用 Python 3.12 即可；这一段只导入本地工具，不需要模型 Key、Redis 或 Docker：

```bash
python3.12 - <<'PYCODE'
import json
from agents.tools import lookup_error_code

result = lookup_error_code(None, {"error_code": "401"})
print(json.dumps(result, ensure_ascii=False, indent=2))
print(result["meaning"])
print(result["server_log_checked"])
assert result["meaning"] == "认证失败"
assert result["server_log_checked"] is False
PYCODE
```

应先打印前面解释过的完整结果JSON，再打印 `认证失败` 和 `False`。这里传 `None` 是因为该 handler 不读取请求对象，只用工具参数；正式 Agent 循环会传入内部 `Request`。`json.dumps`负责把字典显示成可阅读的JSON文本，`ensure_ascii=False`保持中文，`indent=2`使用两格缩进。

读完后，应能回答：把工具返回值交回模型的是谁？工具给了认证排查建议，能否证明真实账号已经恢复？前者是 Agent 的执行循环；后者需要真实业务结果，本工具没有提供。
