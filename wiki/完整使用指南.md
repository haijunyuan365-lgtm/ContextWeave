# EchoMind 完整使用指南

> trace 合并版说明：本页保留附件的讲解与示例；当前主链增加 Context Planner、记忆演化、经验记忆、混合检索和 OTel。运行流程、接口变化与迁移以 [合并版本使用指南](合并版本使用指南.md) 为准；文中的历史测试结果不是本次验收。

这份指南按当前 Python 仓库说明部署、接口调用、知识库维护、数据查看、监控评测和故障排查。所有终端命令默认在 EchoMind 项目根目录执行，适用于 macOS、Linux、WSL 的 Bash/Zsh；PowerShell 的变量和换行写法需要调整。

第一次使用，先读第 2—3 节启动后端，再按第 6—7 节完成聊天和检索。需要查看存储时读第 9—11 节，评测任务的提交与轮询在第 13 节。处理顺序与代码讲解见 [业务流程说明](业务流程说明.md)，逐步学习见 [源码教程](教程/README.md)。

## 1. 先确认本仓库负责什么

EchoMind 是面向客服场景的 Python 多 Agent 后端。它能提供通用咨询、技术排查建议、账单字段检查、金额比较和人工交接说明。真实订单查询、退款执行、工单创建仍需要接入对应业务系统。

本仓库可以独立运行，通过 Swagger 或 HTTP 客户端使用。根目录 Compose 启动 Python API、Redis、ChromaDB、Prometheus 和 Nginx，不包含 Web 前端；需要配套前端时使用第 3.3 节的叠加配置。

一条 HTTP 聊天请求主要经过：

```text
身份与会话锁 → 重试回执检查 → 读取上下文
→ 意图识别与业务字段合并 → 路由到单个或主辅 Agent
→ 模型按需调用知识库、角色工具或外部 MCP 工具
→ 生成回复及完成状态 → Redis 整轮提交
→ 返回响应，后台压缩历史并更新画像
```

意图识别用于分流，RAG 由 Agent 在执行时按需调用。评测通过独立任务运行，不是每次聊天都自动评分。

主要目录：

```text
api/main.py                    HTTP 接口、应用初始化与 CLI
agents/agent_orchestrator.py    角色、主辅路由、工具往返、回复汇总
agents/tools.py                各角色工具与共享 RAG 工具
core/intent_recognizer.py      三路意图融合与实体提取
core/intent_embedding.py       在线意图向量与本地降级
core/conversation_state.py     多轮业务字段继承与重置
core/concurrency.py            会话锁与后台维护队列
core/access.py                 Token 身份与角色校验
core/skill_loader.py           Skills 加载、匹配与提示词注入
memory/conversation_memory.py  Redis 消息、摘要、回执及 ChromaDB 记忆
tooling/tool_manager.py        工具参数、缓存、超时、熔断与检索改写重排
tooling/knowledge_base.py      知识导入、切片、版本更新与查询
tooling/mcp_client.py          标准 MCP 外部工具客户端
tooling/mcp_server.py          对外提供本地知识库的 MCP 服务端
evaluation/evaluator.py        意图与对话评测、Judge、回归比较
evaluation/jobs.py             异步评测任务
evaluation/few_shot.py         Judge 评分校准样例
monitor/performance_monitor.py 在线统计与 Prometheus 指标
config/                        MCP、Nginx、Prometheus 配置
skills/                        通用、技术、账单客服规则
requirements.txt               运行依赖
requirements-dev.txt           测试依赖
.env.example                   环境变量模板
```

本地工具实现目录现在是 `tooling/`。不要继续从旧的 `mcp/knowledge_base.py` 导入项目代码；`mcp` 包名留给官方协议 SDK。

## 2. 环境与配置

### 2.1 准备模型与运行环境

Docker 路线需要 Docker 和 Docker Compose v2。模型服务要支持 **Anthropic Messages 协议和工具调用**，需要提供对应的地址、模型 ID 和 Key。只有 OpenAI Chat Completions 接口的服务不能直接填入当前配置。

模型 ID 使用所选服务实际支持、当前账号可调用的值。首次构建需要拉取镜像、安装依赖并下载 ChromaDB 默认的本地向量模型。

### 2.2 从模板创建 `.env`

仓库已经有 [.env.example](../.env.example)。首次配置时执行下面的命令，已有文件则只编辑，不覆盖：

```bash
if [ ! -e .env ]; then
  cp .env.example .env
fi
```

至少核对这些配置：

```dotenv
ANTHROPIC_API_KEY=替换为模型服务的Key
ANTHROPIC_BASE_URL=替换为Anthropic兼容接口地址
ANTHROPIC_MODEL=替换为账号可调用的模型ID

ECHOMIND_ENV=development
REDIS_PASSWORD=echomind123
CHROMA_HOST=chromadb
CHROMA_PORT=8000

INTENT_EMBEDDING_PROVIDER=auto
SILICONFLOW_API_KEY=
MCP_EXTERNAL_ENABLED=true
```

使用 Anthropic 官方服务时可以留空 `ANTHROPIC_BASE_URL`；使用兼容服务时按其实际入口填写。模型凭据保存在服务端 `.env` 或环境变量中，不放进前端变量。

常用配置与作用：

| 配置 | 作用 |
| --- | --- |
| `ANTHROPIC_API_KEY / BASE_URL / MODEL` | 聊天、意图 LLM、摘要和默认 Judge 使用的模型服务 |
| `REDIS_PASSWORD` | 根目录 Compose 启动 Redis 的密码 |
| `REDIS_URL` | 原生 Python 使用的 Redis 地址；根目录 Compose 会覆盖为容器网络地址 |
| `CHROMA_HOST / CHROMA_PORT` | Docker 为 `chromadb:8000`，宿主机调试为 `localhost:8001` |
| `CHROMA_PERSIST_DIRECTORY` | development 连接远端 ChromaDB 失败时的本地降级目录 |
| `ECHOMIND_SEED_DEMO_DOCS` | development 空库是否导入演示资料，默认 true；production 禁止自动导入 |
| `ECHOMIND_SKILLS_DIR` | Skills 根目录，Compose 固定为 `/app/skills` |
| `ECHOMIND_SKILLS_MAX_PROMPT_CHARS` | 每次注入规则的总字符预算，默认 5000 |
| `ECHOMIND_INTENT_TIMEOUT_S` | 意图 LLM 单次超时，默认 8 秒 |
| `ECHOMIND_LLM_TIMEOUT_S` | 普通 Agent 单次模型请求超时，默认 15 秒 |
| `ECHOMIND_COMPOSER_TIMEOUT_S` | 多 Agent 汇总模型超时，默认 8 秒 |
| `MONITOR_INTERVAL` | 监控采样间隔，默认 10 秒 |
| `PROMETHEUS_PORT` | 可选独立指标端口，设为 0 关闭；HTTP `/metrics` 仍可用 |
| `EVAL_JUDGE_MODEL` | 可单独指定评分模型，仍使用同一服务地址和 Key |
| `EVAL_JUDGE_MAX_TOKENS / TIMEOUT_S` | Judge 默认输出预算 4096、单次超时 45 秒 |

`APP_ENV` 用于直接启动脚本时的开发热重载；`ECHOMIND_ENV` 用于访问控制和生产存储策略，两者用途不同。Docker 的监听地址由 Uvicorn 启动命令指定，修改 `API_PORT` 不会自动改变 Compose 端口。

原生 Python 启动时，进程中已存在的环境变量优先于 `.env`。如果改文件仍不生效，也检查终端是否导出了旧值。

### 2.3 可选：配置在线意图向量

默认没有硅基流动 Key 也可以运行，意图匹配使用本地字符 n-gram 哈希向量。需要在线向量时，在 `.env` 中填写：

```dotenv
INTENT_EMBEDDING_PROVIDER=auto
SILICONFLOW_API_KEY=替换为硅基流动Key
```

| 模式 | 行为 |
| --- | --- |
| `auto` | 有 Key 时尝试在线匹配，没有 Key 时用本地向量 |
| `local` | 只使用本地向量 |
| `siliconflow` | 指定在线服务；缺少 Key 或调用失败仍会本地降级 |

代码固定使用 `BAAI/bge-m3`，不会自动切换到 Pro 模型。账号权限、额度及限流以服务端实际返回为准。这个配置只影响意图识别，知识库和长期记忆仍使用 ChromaDB 默认模型，不需要因此重建知识库。

重建应用后，通过 `/integrations/embedding` 看配置和冷却状态，再从 `/chat` 的 `intent_embedding_source` 确认本次实际使用了 `siliconflow/BAAI/bge-m3` 还是 `local-ngram`。`online_configured=true` 只表示读取了在线配置，不能代替真实调用验证。

### 2.4 API 访问 Token 与模型 Key 分开配置

本机演示可以使用 `development` 且不配置 `ECHOMIND_API_TOKENS`。对外部署或需要访问身份时，配置独立随机 Token：

```dotenv
ECHOMIND_ENV=production
ECHOMIND_API_TOKENS='{"替换为至少24字符的随机用户Token":{"user_id":"guide_user","role":"user"},"替换为至少24字符的随机管理员Token":{"user_id":"guide_admin","role":"admin"}}'
```

示例字符串必须换成自己的随机值。在有 Python 的终端中可用 `python3 -c "import secrets; print(secrets.token_urlsafe(32))"` 生成；两个角色使用不同 Token。production 没有有效配置时应用启动失败。

调用终端设置用于本次操作的访问凭据：

```bash
export ECHOMIND_ACCESS_TOKEN='替换为本次操作所需的EchoMind访问Token'
```

后文 EchoMind API 示例使用 `Authorization: Bearer ${ECHOMIND_ACCESS_TOKEN:-}`。本机未启用鉴权时可以不设置此变量；启用后，管理操作使用 admin Token，聊天可使用 user Token。它与 `ANTHROPIC_API_KEY`、`SILICONFLOW_API_KEY` 是不同凭据。

启用鉴权后，聊天用户来自 Token 映射，JSON 里的 `user_id` 不再决定身份。后面的存储查询默认查 `guide_user`，如果用管理员身份聊天，应把查询用户改成对应 Token 的 `user_id`。

## 3. Docker Compose 部署

### 3.1 启动 Python 后端和依赖

```bash
docker compose up -d --build
docker compose ps
docker compose logs -f echomind
```

根目录服务与端口：

| 服务 | Compose 服务名 | 宿主机入口 | 容器内部入口 |
| --- | --- | --- | --- |
| Python API | `echomind` | `http://localhost:8000` | `echomind:8000` |
| Nginx | `nginx` | `http://localhost` | `nginx:80` |
| ChromaDB | `chromadb` | `http://localhost:8001` | `chromadb:8000` |
| Redis | `redis` | `localhost:6379` | `redis:6379` |
| Prometheus | `prometheus` | `http://localhost:9090` | `prometheus:9090` |

这些宿主机端口绑定 `127.0.0.1`。容器之间使用服务名，不能把容器里的 `localhost:8001` 当作 ChromaDB 地址。

查看健康检查：

```bash
curl -sS http://localhost:8000/health
```

未开启鉴权时，可打开 `http://localhost:8000/docs`，也可以经 Nginx 打开 `http://localhost/docs`。根目录部署的 Nginx 只代理 API，不会出现聊天 Web 页面。

`/health` 正常只说明应用完成初始化，不验证模型 Key、额度和模型 ID。再按第 6 节发一次聊天，确认模型能实际生成回复。

### 3.2 修改配置后怎样生效

只修改 `.env`：

```bash
docker compose up -d --force-recreate echomind
```

修改代码或运行依赖：

```bash
docker compose up -d --build echomind
```

修改 Redis 密码时同时更新 Redis 和应用：

```bash
docker compose up -d --force-recreate redis echomind
```

`restart` 只重启现有容器，不会重新读取 `.env` 中的新容器环境。修改 Skills 走热加载；修改 MCP 配置文件后重启应用重新读取配置。

### 3.3 可选：带上配套 Web 与 Java 后端

需要另有同级目录 `EchoMindFrontend`、`EchoMindJava`。根目录已有 Redis/ChromaDB 数据时，可叠加启动：

```bash
docker compose -f docker-compose.yml -f docker-compose.web.yml up -d --build
```

前端入口为 `http://localhost:5174` 或 `http://localhost`，Python 仍是 8000，Java 是 8080。Java 数据使用外部卷，默认名 `echomindjava_app-data`，可通过 `ECHOMIND_JAVA_DATA_VOLUME` 指定现有卷。全新环境没有该卷时先创建：

```bash
docker volume create echomindjava_app-data
```

此后管理这套部署时始终携带同样两个 `-f` 参数。若模型服务不是叠加配置中预设的兼容平台，先检查 Java 的模型配置，不能只凭 Python 配置推断 Java 也可用。

配套前端仓库还提供独立部署路线。两套部署端口和容器名有重叠，选择一套运行；其数据卷不自动互通。具体路径约定见 [README 的快速启动](../README.md#quickstart)。

## 4. CLI 与本地源码调试

### 4.1 在现有 Compose 环境运行 CLI

```bash
docker compose run --rm echomind python api/main.py --cli
```

输入 `quit`、`exit`、`退出` 或空行结束。CLI 会创建自己的 Agent、Skills、记忆、RAG 工具和外部 MCP 客户端，能够体验知识检索和工具调用。

CLI 没有启动 HTTP 鉴权、请求回执、整轮事务、结构化业务状态传递、Monitor 或后台画像维护。它分别写用户和助手消息，达到阈值时可同步压缩。因此，要验证 HTTP 重试、身份绑定、异步评测和后台记忆行为，使用 API。

命令使用已构建到镜像里的代码。修改 Python 后先 `docker compose build echomind`；Skills 在启动 CLI 时重新读取。

### 4.2 在宿主机调试 API

推荐 Python 3.12，与镜像一致：

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
docker compose up -d redis chromadb
```

Windows 的虚拟环境创建可用 `py -3.12 -m venv .venv`，在 PowerShell 中用 `.venv\Scripts\Activate.ps1` 激活。

宿主机进程在 `.env` 使用以下存储地址，密码与实际 Redis 保持一致：

```dotenv
REDIS_URL=redis://:echomind123@localhost:6379/0
CHROMA_HOST=localhost
CHROMA_PORT=8001
CHROMA_PERSIST_DIRECTORY=./data/chroma
EVAL_BASELINE_PATH=./data/eval/baseline.json
PROMETHEUS_PORT=0
```

关闭占用 8000 端口的旧应用后启动：

```bash
python -m uvicorn api.main:app --host 127.0.0.1 --port 8000 --reload
```

也可执行 `python api/main.py --cli`。切回 Docker 部署前，把 `.env` 的 ChromaDB 地址恢复为 `chromadb:8000`。development 才允许远端 ChromaDB 失败时回退本地目录，production 会中止启动；本地与远端数据不会自动合并。

## 5. Swagger、权限和接口总览

本地未启用鉴权时，在 `/docs` 点击 **Try it out → Execute** 即可调用。启用后，`/docs`、`/openapi.json` 也需要管理员认证头，普通浏览器直接打开可能返回 `401`；当前代码没有替 Swagger 声明完整的 Bearer 授权方案。可以改用带认证头的 HTTP 客户端，或直接使用下列 curl 示例。

### 5.1 接口和权限

下面的权限指启用 Token 后的规则。未启用鉴权的 development 环境不执行这些角色限制。

| 方法与路径 | 参数位置 | 用途 | 权限 |
| --- | --- | --- | --- |
| `GET /health` | 无 | 初始化状态，鉴权开启后隐藏 Agent 明细 | 公开 |
| `POST /chat` | JSON | 聊天、路由、工具和会话提交 | user / admin |
| `POST /search` | query、top_k 查询参数 | 独立知识检索 | user / admin |
| `GET /knowledge/stats` | 无 | 资料片段数 | user / admin |
| `GET /skills` | 无 | 规则加载结果 | user / admin |
| `POST /skills/reload` | 无 | 重新扫描规则文件 | admin |
| `POST /knowledge/add` | JSON | 文档导入或更新 | admin |
| `POST /knowledge/upload` | multipart 文件 | txt、md、json 导入 | admin |
| `GET /trace/tools` | limit 查询参数 | 最近持久化轨迹 | admin |
| `GET /trace/tool/{request_id}` | 路径 | 单次路由和工具明细 | admin |
| `GET /monitor`、`GET /metrics` | 无 | 在线统计与 Prometheus | admin |
| `POST /eval/run` | 可选 JSON | 提交评测任务，返回 202 | admin |
| `GET /eval/jobs/{job_id}` | 路径 | 任务进度和最终报告 | admin |
| `GET /integrations/embedding` | 无 | 意图向量配置与冷却状态 | admin |
| `GET /integrations/mcp` | 无 | 外部连接及工具发现 | admin |
| `POST /integrations/mcp/call` | JSON | 单独调试外部工具 | admin |
| `/mcp/` | 标准 MCP 协议 | 本地知识搜索及统计资源 | user / admin |

### 5.2 查看与热加载 Skills

```bash
curl -sS -H "Authorization: Bearer ${ECHOMIND_ACCESS_TOKEN:-}" http://localhost:8000/skills
curl -sS -H "Authorization: Bearer ${ECHOMIND_ACCESS_TOKEN:-}" -X POST http://localhost:8000/skills/reload
```

文件放在 `skills/`，可使用 `SKILL.md` 目录或 Markdown、TXT、JSON 文件。例如：

```markdown
---
name: 技术排查补充规则
description: 收集故障信息并说明下一步
keywords: 登录,报错,401
agents: technical
enabled: true
---

遇到登录错误时，先确认发生时间、客户端版本和错误码。
给出排查步骤前，说明需要这些信息的原因。
```

只有启用、角色匹配、关键词匹配的规则才注入；关键词为空则不限制消息，角色为空则不限制角色。重新加载成功不代表每个请求都会命中。当前内置通用、技术、账单三类规范，Escalation 的确定性回复不构建普通 Agent 提示词。

### 5.3 查看意图向量与外部 MCP 状态

```bash
curl -sS -H "Authorization: Bearer ${ECHOMIND_ACCESS_TOKEN:-}" http://localhost:8000/integrations/embedding
curl -sS -H "Authorization: Bearer ${ECHOMIND_ACCESS_TOKEN:-}" http://localhost:8000/integrations/mcp
```

标准 MCP 配置在 [config/mcp_servers.json](../config/mcp_servers.json)。默认服务为 Microsoft Learn，提供搜索和抓取，限定 General、Technical 使用。支持 Streamable HTTP 和 stdio；工具必须在白名单中，只读模式还要求远程工具明确声明只读且不具破坏性。

调用调试接口时，从状态接口复制实际工具别名，并按该工具参数 schema 填写。例如默认搜索工具可这样请求：

```bash
curl -sS -H "Authorization: Bearer ${ECHOMIND_ACCESS_TOKEN:-}" \
  -X POST http://localhost:8000/integrations/mcp/call \
  -H "Content-Type: application/json" \
  -d '{"name":"mcp_mslearn_microsoft_docs_search","arguments":{"query":"Azure App Service deployment"}}'
```

工具是否连通、远端参数格式和返回资料以实际服务为准。`404` 表示工具未连接或未在白名单中；HTTP 成功后仍要看响应的 `success/error`。配置更新后重启应用；stdio 工具要求可执行命令及依赖在应用容器内存在。

外部客户端访问 EchoMind 的 MCP 地址是 `http://localhost:8000/mcp/`。提供 `search_local_knowledge` 工具和 `echomind://knowledge/stats` 资源。用支持 MCP 的客户端连接，不能把普通 GET 当作完整协议测试。通过自定义域名访问时需配置 `MCP_ALLOWED_HOSTS`、`MCP_ALLOWED_ORIGINS`。

## 6. 聊天、追问和重试

### 6.1 发送第一条消息

```bash
curl -sS -H "Authorization: Bearer ${ECHOMIND_ACCESS_TOKEN:-}" \
  -X POST http://localhost:8000/chat \
  -H "Content-Type: application/json" \
  -d '{
    "message":"订单号 #12345，昨天支付99元，想问退款多久到账？",
    "user_id":"guide_user",
    "conv_id":"guide-refund",
    "client_request_id":"guide-refund-001"
  }'
```

消息长度 1～12000 字符。`user_id` 默认 `anonymous`；会话不传时根据用户与客户端消息 ID 生成 UUID。客户端 ID 不传时由服务端生成，但客户端不便复用，所以需要可靠重试时主动提供它。

下面是关键字段示意，省略部分响应字段，分数和回复不代表固定结果：

```json
{
  "conv_id":"guide-refund",
  "request_id":"服务端执行ID",
  "response":"还需要确认支付渠道；退款处理结果与到账情况需核验实际业务记录。",
  "intent":"refund",
  "intent_group":"billing",
  "primary_agent":"billing",
  "supporting_agents":[],
  "agent_type":"billing",
  "agent_types":["billing"],
  "tools_used":["check_billing_fields"],
  "knowledge_used":false,
  "intent_confidence":0.75,
  "intent_embedding_source":"local-ngram",
  "status":"success",
  "retryable":false,
  "error_code":null
}
```

常用字段：

| 字段 | 应怎样理解 |
| --- | --- |
| `request_id` | 服务端一次执行的 ID，用于查轨迹，不是客户端重试 ID |
| `intent / intent_group` | 细分诉求与业务大类 |
| `primary_agent / supporting_agents` | 路由计划；回退后可能与实际执行不同 |
| `agent_type / agent_types` | 返回角色信息；并行回退细节结合工具轨迹看 |
| `routing_reason / routing_confidence` | 规则打分和选择依据，分数不是统计准确率 |
| `tools_used` | handler 返回后加入的工具名，即使业务结果失败也可能出现 |
| `knowledge_used` | 共享知识库工具至少一次实际成功；外部文档工具不计入这个本地 RAG 标记 |
| `entities` | 本轮与当前任务合并后的订单、金额、日期、错误码等字段 |
| `intent_source_scores` | 意图各来源的原始分数及可能的细化标记 |
| `escalated` | 已产生升级交接或升级标记，不表示创建了工单 |
| `latency_ms` | 到组装回复时的处理耗时；不含随后的 Redis 提交，完整 HTTP 时间看 `Server-Timing` |
| `status / retryable / error_code` | 完成程度、失败是否可安全重试及错误原因 |

`success` 表示本轮执行完整，不表示退款已执行；提出必要追问也可以是一次完整处理。

### 6.2 继续追问

保留同一用户与会话，更换消息 ID：

```bash
curl -sS -H "Authorization: Bearer ${ECHOMIND_ACCESS_TOKEN:-}" \
  -X POST http://localhost:8000/chat \
  -H "Content-Type: application/json" \
  -d '{"message":"退款是原路退回吗？","user_id":"guide_user","conv_id":"guide-refund","client_request_id":"guide-refund-002"}'
```

历史背景和当前任务字段分别保存。查询与账单类共用 `commerce` 状态；换订单、明确换问题或切换业务域时会清理旧字段。订单字段齐全不等于身份或操作授权已经核验。

### 6.3 网络中断后怎样重试

原消息、原用户、原会话、原 `client_request_id` 重新提交。24 小时内已有成功或部分成功回执时，直接返回原响应，不重复写历史；同 ID 携带不同消息返回 `409`。

| 情况 | 处理 |
| --- | --- |
| `200 / success` | 完整返回，重发原 ID 会复用回执 |
| `200 / partial` | 有截断或部分协作失败，原 ID 不会自动补跑 |
| `503 / failed / retryable=true` | 可沿用原 ID 重试，恢复成功后才写入正常历史 |
| `failed / retryable=false` | 不自动重做，先确认原因和业务结果 |
| `504` | 处理超过 50 秒，沿用同一 ID 查询或重试并遵守回执结果 |
| `503` 且只有 `detail` | 可能是初始化、会话繁忙或失锁，不一定有完整聊天字段 |

同会话从读上下文到保存结果串行处理，其他会话可并行。可能修改数据的工具执行前会保存不可重放标记；若出现 `tool_outcome_unknown`，应先核验外部结果。该机制不能保证外部系统操作恰好一次。

### 6.4 技术、复合问题与转人工

可在新的消息 ID 或独立会话中分别测试：

| 输入 | 观察内容 |
| --- | --- |
| 登录一直报 HTTP 401 | 错误码实体、技术角色、错误码或知识工具 |
| 登录报错 401，还重复扣款 | 技术和账单主辅协作，合并后的状态 |
| 转人工客服 | 升级交接及 `escalated`，不会真正创建人工工单 |
| 意图为 other、分数低于 0.5 且长度大于 2 | 先澄清业务方向 |

RAG 由模型按需调用。明确需求与运行健康状态会共同影响路由，实际结果以返回字段为准。更详细的打分、澄清和升级规则见 [业务流程说明](业务流程说明.md)。

### 6.5 查工具调用记录

```bash
curl -sS -H "Authorization: Bearer ${ECHOMIND_ACCESS_TOKEN:-}" \
  'http://localhost:8000/trace/tools?limit=20'
curl -sS -H "Authorization: Bearer ${ECHOMIND_ACCESS_TOKEN:-}" \
  'http://localhost:8000/trace/tool/替换为实际request_id'
```

轨迹先读 Redis，再回退内存；已提交轨迹保留 7 天，最近列表最多 200 条。专业 Agent 失败回退时保留原尝试、`agent_fallback` 和后续调用。异常中断没完成提交的请求，可能没有完整记录。

`success` 看调用是否抛错，`result_success` 看工具自己的成功字段，缺少该字段时可以为 null。共享 RAG 失败的 fallback 仍按失败处理，不会因为附带降级说明就算查到资料。轨迹没有保存完整文档结果正文，资料内容需要单独核对。

## 7. 知识库导入、更新和检索

知识库由 [tooling/knowledge_base.py](../tooling/knowledge_base.py) 管理，collection 名称是 `knowledge_base`。development 空库可自动导入演示政策，production 空库不会自动添加，需管理员导入自己的业务资料。

### 7.1 查看片段数

```bash

```

`total_chunks` 是片段数，不是原始文档篇数。不要把一次演示输出的数字当作所有环境的固定数量。

### 7.2 按稳定文档 ID 导入

下面内容仅用于演示。实际业务应换成经过确认的资料：

```bash
curl -sS -H "Authorization: Bearer ${ECHOMIND_ACCESS_TOKEN:-}" \
  -X POST http://localhost:8000/knowledge/add \
  -H "Content-Type: application/json" \
  -d '{"documents":[
    {"document_id":"guide-login-401","title":"演示：登录401排查","content":"登录返回401时，先确认登录状态和令牌有效期。令牌失效后重新登录。不要在聊天中发送密码或完整令牌。"},
    {"document_id":"guide-refund-policy","title":"演示：退款核验","content":"本演示没有退款执行工具。退款需核验订单、金额、支付时间和渠道，不能在核验前承诺已退款或具体到账时间。"}

```

相同显式 `document_id` 会更新同一文档；未提供时按标题识别。更新会重写片段、删除多余旧片段，并使线上与评测知识检索缓存失效。同一批相同身份采用最后一份。同标题不同来源需使用不同 ID。

文档按约 500 字切片，超长句也会继续切分。片段带文档身份哈希、版本和序号，向量由 ChromaDB 默认客户端模型生成。返回的 `added_chunks` 是本次处理数，重复更新也会计数，不等于净新增。

### 7.3 文件上传

```bash
curl -sS -H "Authorization: Bearer ${ECHOMIND_ACCESS_TOKEN:-}" \
  -X POST http://localhost:8000/knowledge/upload \
  -F 'file=@data/demo_docs/troubleshooting.md'
```

也可上传 `data/demo_docs/sample_knowledge.json`。JSON 文件是数组，单项包含 `title`、`content` 和可选 `document_id`：

```json
[
  {
    "document_id":"guide-doc-001",
    "title":"文档标题",
    "content":"经过确认的业务资料"
```

仅接受 `.txt`、`.md`、`.json`，其他后缀返回 `400`，大于 10 MB 返回 `413`。文本文件按文件名确定标题，JSON 可明确指定 ID。通过 Nginx 上传时还受代理的 10M 请求体限制，multipart 有额外开销，贴近上限的文件可能先被代理拒绝。

### 7.4 单独验证检索

用 `--data-urlencode` 编码中文查询参数：

```bash
curl -sS -H "Authorization: Bearer ${ECHOMIND_ACCESS_TOKEN:-}" \
  -G -X POST http://localhost:8000/search \
  --data-urlencode 'query=登录返回401怎么办' \
  --data-urlencode 'top_k=3'
```

`query` 为 1～2000 字符，`top_k` 为 1～20，默认 5。该接口通过查询参数传值，不是 JSON Body。

```text
保留原问题，最多增加 3 个改写问题
→ 各路并行查询 → 按文档身份、标题、内容和片段序号去重
→ 结果多于 top_k 时尝试重排 → 返回 Top-K
```

响应包含 `query`、`results`、`reranked`。每条结果有标题、正文、分数、片段序号、内部文档 ID 和版本。结果不足或重排失败时，`reranked` 可以为 false。

先确认这里能召回资料，再通过 `/chat` 看模型是否调用共享知识库工具。接口 HTTP 成功但结果为空时，还需结合日志和工具统计区分空库、无结果及底层故障；不能根据 `knowledge_used` 或回复措辞倒推模型一定查过资料。

## 8. 数据分别保存在哪里

| 数据 | 位置 | 写入时机 |
| --- | --- | --- |
| 当前消息、业务字段、响应回执 | Redis | HTTP 一轮结果提交 |
| 当前会话摘要 | Redis | 后台压缩成功 |
| 聊天轨迹 | Redis | 有可用轨迹的 HTTP 结果提交 |
| `knowledge_base` | ChromaDB | 演示初始化或管理员导入 |
| `episodic` | ChromaDB | 后台压缩成功后尝试写入历史摘要 |
| `user_profile` | ChromaDB | 后台维护从近期消息提炼画像 |
| 评测基线 | `data/eval/baseline.json` | 完整且未检测到回归的报告 |
| 评测任务、路由统计、工具缓存与熔断 | 当前应用进程 | 运行中，重启会丢失这些内存状态 |

根目录 Compose 的 Redis、远端 ChromaDB、Prometheus 使用命名卷。`data/chroma/` 是本地 ChromaDB 降级目录，不能据此认为远端知识资料也都保存在这个宿主机目录。远端与本地降级数据不自动合并。

下面的数据查看命令针对根目录 Compose，使用服务名 `echomind`，不依赖固定容器名。配套前端仓库的独立部署服务名不同，应先用其 `docker compose ps` 确认。

## 10. 查看 Redis 消息、摘要、业务字段与回执

当前键名由用户和会话的结构化内容计算哈希：

| 内容 | 当前键格式 |
| --- | --- |
| 工作消息 | `wm_v2:<会话哈希>` |
| 会话摘要 | `summary_v2:<会话哈希>` |
| 业务字段 | `state_v1:<会话哈希>` |
| 请求回执 | `turn_receipt:<会话哈希>:<客户端ID哈希>` |
| 工具轨迹 | `trace:<服务端request_id>` |

旧的 `wm:user_001:session_001`、`summary:user_001:session_001` 不再是当前写入格式。下面调用项目键生成方法，直接读取真实 `REDIS_URL`，不需要手动猜哈希或把密码抄进命令：

```bash
docker compose exec -T echomind python - <<'PY'
import asyncio
import json
import os
from redis.asyncio import Redis
from memory.conversation_memory import MemoryManager

async def main():
    user_id, conv_id = "guide_user", "guide-refund"
    client_request_id = "guide-refund-001"
    client = Redis.from_url(os.environ["REDIS_URL"], decode_responses=True)
    try:
        print("ping:", await client.ping())
        key = MemoryManager._wm_key(user_id, conv_id)
        rows = await client.lrange(key, 0, -1)
        print("working key:", key, "count:", len(rows), "ttl:", await client.ttl(key))
        for raw in reversed(rows):
            row = json.loads(raw)
            print(row["role"], row["content"])
        skey = MemoryManager._summary_key(user_id, conv_id)
        state_key = MemoryManager._state_key(user_id, conv_id)
        print("summary:", await client.get(skey))
        print("state:", await client.get(state_key))
        memory = MemoryManager.__new__(MemoryManager)
        receipt_key = memory.receipt_key(user_id, conv_id, client_request_id)
        print("receipt:", await client.get(receipt_key))
        print("receipt ttl:", await client.ttl(receipt_key))
    finally:
        await client.aclose()

asyncio.run(main())
PY
```

Redis 列表最新消息在前，脚本反转后按聊天顺序输出。TTL 单位为秒，`-2` 表示该键不存在；业务状态和正常消息默认 24 小时，后台维护也可能刷新部分有效期。失败轮次没有正常消息，但仍可能有回执。

若只想扫描键名，用 `scan_iter`，不使用会一次匹配全库的 `KEYS *`：

```bash
docker compose exec -T echomind python - <<'PY'
import asyncio
import os
from redis.asyncio import Redis

async def main():
    client = Redis.from_url(os.environ["REDIS_URL"], decode_responses=True)
    try:
        for pattern in ("wm_v2:*", "summary_v2:*", "state_v1:*", "turn_receipt:*", "trace:*"):
            count = 0
            print("pattern:", pattern)
            async for key in client.scan_iter(match=pattern, count=100):
                print(key)
                count += 1
                if count >= 20:
                    break
    finally:
        await client.aclose()

asyncio.run(main())
PY
```

## 11. 验证后台压缩和画像更新

HTTP `/chat` 先原子写入用户和助手两条消息，再提交后台维护任务。压缩阈值为 15 条消息，不是 15 轮；`WORKING_MAX=20` 是工作记忆读取上限，不是硬性列表长度限制。

在空会话中，前 7 轮正常提交后是 14 条，第 8 轮后是 16 条。后台对较旧消息生成摘要，保留快照中最近 5 条；期间新写入的消息也会保留，所以最终数量不一定等于 5。

### 11.1 发起一组独立会话测试

这会真实调用模型，回复、摘要和画像都有实际耗时。查看每轮 HTTP 状态，不把失败轮次当成已经成功积累的消息：

```bash
ECHOMIND_COMPRESSION_CONV="guide-compress-$(date +%s)"
for i in 1 2 3 4 5 6 7 8; do
  curl -sS -H "Authorization: Bearer ${ECHOMIND_ACCESS_TOKEN:-}" \
    -X POST http://localhost:8000/chat \
    -H 'Content-Type: application/json' \
    -d "{\"message\":\"第${i}轮，我想了解退款需要准备哪些信息\",\"user_id\":\"guide_user\",\"conv_id\":\"${ECHOMIND_COMPRESSION_CONV}\",\"client_request_id\":\"${ECHOMIND_COMPRESSION_CONV}-${i}\"}" \
    -w '\nHTTP %{http_code}\n'
done
printf '本次会话：%s\n' "$ECHOMIND_COMPRESSION_CONV"
```

### 11.2 看日志与存储

```bash
docker compose logs --tail=100 echomind
```

留意 `工作记忆压缩完成`、`用户画像已更新`，以及摘要失败、维护延期或队列满的日志。把第 10 节脚本中的 `conv_id` 换成本次打印的会话，再读消息、摘要和状态；第 9.7 节可查同会话的 `episodic`。

当前压缩流程：

```text
读完整消息快照 → 为较旧消息生成摘要 → 合并旧摘要
→ WATCH 校验消息和摘要是否已被其他任务改动
→ Redis 提交摘要与裁剪结果 → 尝试写 ChromaDB episodic
→ 再尝试更新用户画像
```

摘要为空、截断或失败时保留原消息，不会用“摘要生成失败”占位后直接删历史。若快照为 16 条、期间又写入 2 条，提交成功会保留 `5 + 2 = 7` 条；其他压缩已改动快照时放弃覆盖，持续冲突时延期。

### 11.3 近期消息、摘要和画像的关系

| 内容 | 用途 |
| --- | --- |
| Redis 近期消息 | 模型了解最近的问答，实际提示词最多加入 8 条 |
| Redis 会话摘要 | 已压缩内容的概括，最多 800 字符 |
| Redis 业务状态 | 当前任务的订单、金额等字段和来源 |
| ChromaDB episodic | 按语义找历史摘要，优先同会话，再扩展到同用户 |
| ChromaDB user_profile | 用户维度的偏好与长期信息 |

后台任务先压缩再提炼画像，队列有界，同用户待处理任务可合并。生成摘要失败不代表当前聊天失败；Redis 压缩提交成功也不保证后续 ChromaDB 写入一定成功。画像属于模型提取结果，不是经过业务系统核验的客户档案。

## 12. Monitor 与 Prometheus

### 12.1 看运行状态

```bash
curl -sS -H "Authorization: Bearer ${ECHOMIND_ACCESS_TOKEN:-}" http://localhost:8000/monitor
curl -sS -H "Authorization: Bearer ${ECHOMIND_ACCESS_TOKEN:-}" http://localhost:8000/metrics
```

`/monitor` 包含 `agent_stats`、`tool_stats`、`active_alerts`、`suggestions`。Agent 除累计指标外，还提供近期调用数、近期成功率与延迟、惩罚及恢复状态。工具可看成功率、耗时、连续失败和 `closed/open/half_open` 熔断状态。

Monitor 默认每 10 秒采样。路由惩罚使用最近 300 秒、最多 50 次完成调用，至少 5 个样本才计算；不是对每次请求即时修改路由。

Technical、Billing 达到惩罚阈值后进入冷却，默认阈值 `0.5`、冷却 60 秒。冷却到期只允许一个请求试探恢复，成功清理旧窗口与惩罚，失败或取消重新冷却。即使每类一个实例，专业类型也可以暂时退出路由。

```dotenv
ECHOMIND_MONITOR_FALLBACK_PENALTY=0.5
ECHOMIND_MONITOR_COOLDOWN_SECONDS=60
```

工具指标用于告警和建议，没有直接加入 Agent 的路由惩罚。是否真正回退，看恢复状态和 `/chat` 的 `routing_reason` 中有无 `monitor_fallback`；告警本身不代表已经回退。运行成功率也不能当作答案准确率。

### 12.2 验证 Prometheus 抓取

打开 `http://localhost:9090`，在 Targets 中查看 `echomind-app` 是否 UP。默认采集目标是 `echomind:8000/metrics`。`PROMETHEUS_PORT=0` 只关闭独立指标端口，不关闭 API 的 `/metrics`。

若开启访问 Token，默认无认证采集会得到 `401`。仓库已有带凭据文件的配置，可复用：

```bash
mkdir -p data/tutorial
printf '%s' "${ECHOMIND_ACCESS_TOKEN:?请先设置管理员访问Token}" > data/tutorial/metrics-admin-token
chmod 600 data/tutorial/metrics-admin-token
docker compose -f docker-compose.yml \
  -f wiki/教程/examples/compose.metrics-auth.yml \
  up -d --force-recreate prometheus
```

该 Token 必须在服务端配置为 admin，凭据文件只保存在本机。配置通过 Docker secret 挂载给 Prometheus；轮换 Token 后同步更新文件并重新创建采集服务。以后管理这套 Prometheus 继续携带同样的 `-f` 参数；若有 Web 叠加配置，也保留对应文件。

更多说明见 [监控教程](教程/10-监控降权与恢复.md)。Nginx 还对 `/metrics` 有来源限制，Prometheus 按上述配置直接采集 Python 服务即可。

## 13. 提交评测、轮询任务、读取报告

### 13.1 提交内置评测

```bash
curl -i -H "Authorization: Bearer ${ECHOMIND_ACCESS_TOKEN:-}" \
  -X POST http://localhost:8000/eval/run
```

立即返回 HTTP `202` 和任务快照，不直接返回评分。主要字段示意：

```json
{
  "job_id":"复制实际任务ID",
  "status":"queued",
  "completed":0,
  "total":0,
  "result":null,
  "error":null
}
```

复制 `job_id` 查询，任务未结束时过一段时间再查，不要每次都重新提交：

```bash
curl -sS -H "Authorization: Bearer ${ECHOMIND_ACCESS_TOKEN:-}" \
  'http://localhost:8000/eval/jobs/替换为实际job_id'
```

任务状态从 `queued` 到 `running`，最终为 `completed`、`failed` 或 `cancelled`。默认最多 8 个未完成任务，串行执行，单任务上限 1800 秒；队列满返回 `429`。任务状态保存在当前进程，服务重启或旧记录被清理后查询可能为 `404`。

### 13.2 提交自己的单轮与多轮用例

下面同时测试细意图与多轮字段。参考答案和资料只给 Judge 校验，不会直接交给被测 Agent：

```bash
curl -i -H "Authorization: Bearer ${ECHOMIND_ACCESS_TOKEN:-}" \
  -X POST http://localhost:8000/eval/run \
  -H 'Content-Type: application/json' \
  -d '{
    "intent_cases":[
      {"message":"登录一直报401","expected_intent":"technical_login"}
    ],
    "dialog_cases":[
      {
        "turns":["订单号 #12345，昨天支付99元，想问退款多久到账？","退款是原路退回吗？"],
        "expected_agent":"billing",
        "expected_intent":"refund",
        "expected_entities":{"order_id":["12345"],"amount":["99元"]},
        "reference_answer":"结合已有订单信息解释处理路径，并说明仍需业务核验。",
        "evidence":"当前未接入退款执行工具，不能承诺已经退款或已核实支付记录。"
      }
    ]
  }'
```

`question` 用于单轮，`turns` 用于多轮。可指定 `expected_agent`、`expected_intent`、`required_tools`、`expected_entities`，在最后一轮做确定性检查；要求使用知识工具时设置 `required_tools`，未调用就不能通过，不会由评测器代替模型强制执行。

某类用例未传时使用默认用例，传空数组才跳过。只测意图可传 `dialog_cases: []`，只测对话可传 `intent_cases: []`；两者均空的报告为 `empty`。

### 13.3 区分任务状态和报告状态

任务 `completed` 表示评测程序结束，报告在 `result` 中。还要读取报告自身字段：

| 报告字段 | 含义 |
| --- | --- |
| `status` | `complete/partial/failed/empty`，主要表示评分是否有效完整，不表示全部用例通过 |
| `scope` | 当前为 `orchestrator` |
| `total / valid_total / evaluation_errors` | 报告项、有效项、Judge 评分失败项 |
| `passed / pass_rate` | 通过项与有效项上的通过率，不能脱离有效数看 |
| `avg_scores` | 有效评分均值和意图准确率等汇总 |
| `results` | 每项回复、实际路由、评分、确定性检查和错误明细 |
| `suite_id` | 用例与 Judge 评分条件的比较标识 |
| `regressions / regression_note` | 回归结果和是否跳过比较的原因 |
| `recommendations` | 根据评分和执行状态生成的建议 |

意图评测计算 Accuracy、Macro-F1，整个意图集在报告中是一个汇总项；每轮对话各算一个结果项。进度按意图批次和对话用例数推进，与最终报告条目数不一定相同。

对话通过需要执行状态为 `success`、确定性检查通过、四维均分至少 `0.75`。Judge 评分维度为相关性、准确性、完整性、有用性。执行失败直接记录零分；Judge 自己调用或解析失败则是空评分并记录原因，排除有效均分与通过率，不会统一补成 `0.5`。

一轮通过、一轮评分失败时，有效通过率仍可能是 100%，但报告为 `partial`，应先处理评分错误。相反，所有评分有效但都不通过时，报告也可以是 `complete`。

### 13.4 Judge 与回归基线

```dotenv
EVAL_JUDGE_MODEL=替换为可选评分模型ID
EVAL_JUDGE_MAX_TOKENS=4096
EVAL_JUDGE_TIMEOUT_S=45
```

不设置 `EVAL_JUDGE_MODEL` 则使用默认对话模型。每条评分最多两次请求，401/403 等鉴权问题直接失败；输出截断时可扩大预算，最大 8192。解析错误从 `judge_error_type`、`judge_stop_reason`、`judge_attempts` 等字段定位。

Judge 有独立 Few-shot 校准样例，处理有依据回答、诚实说明限制、笼统回答、编造操作成功和遗漏历史等情况。样例内容与版本进入 `suite_id`，只供裁判使用，不混入当前业务资料。

回归只与相同 `suite_id`、完整且无已检测回归的基线比较。指标相对下降超过 5% 会报告回归；评分失败、空报告或检测到回归时不覆盖有效基线。根目录 Compose 将基线保存到 `/app/data/eval/baseline.json`，宿主机对应 `data/eval/baseline.json`。

`suite_id` 约束用例和 Judge 评分条件，不包含所有业务提示词、知识内容和运行环境。记录实际改动和环境后再解释分数变化。

### 13.5 评测覆盖范围

评测使用独立 Orchestrator、Agent 统计、工具缓存和熔断，只提供可安全重试的共享工具。但知识库和外部连接仍共用，真实执行会消耗模型与外部服务额度。

报告覆盖编排、字段合并、工具和回答；没有经过完整 HTTP 鉴权、Redis 会话锁、整轮提交、长期记忆和后台画像。模型评分与程序回归分别验证，不能用一份高分报告替代接口可靠性检查。

## 14. 停止、更新与数据清理

### 14.1 日常操作

```bash
docker compose ps
docker compose logs --tail=100 echomind
docker compose stop
docker compose start
```

停止并移除容器、保留命名卷：

```bash
docker compose down
```

代码或依赖更新后重新构建：

```bash
docker compose up -d --build echomind
```

仅改 `.env` 时使用 `up -d --force-recreate echomind`。`docker compose restart echomind` 适合重新启动现有容器或重新读取已挂载的 MCP 文件，不会读取新的容器环境值。

若启动时叠加了 Web 或监控认证文件，后续启动、停止和重建使用同样的 Compose 文件组合。

### 14.2 数据保留和删除范围

| 数据 | 保存位置 |
| --- | --- |
| 消息、状态、摘要、回执、轨迹 | Redis 命名卷 |
| 知识、情景摘要、用户画像 | ChromaDB 命名卷 |
| 本地 ChromaDB 降级库 | `data/chroma/` |
| 评测基线 | `data/eval/` |
| Prometheus 历史指标 | Prometheus 命名卷 |
| Skills、MCP 配置 | `skills/`、`config/mcp_servers.json` |

需要完整备份时覆盖实际使用的命名卷和挂载目录，并停止相关写入保证备份一致。删除容器不会把进程内评测任务、路由统计或工具缓存保存下来。

下面会删除根目录部署的命名卷及相应数据，只在确认清空这套环境时执行：

```bash
docker compose down -v
```

它不删除 `data/eval/`、`data/chroma/` 等宿主机绑定目录；Web 配置中的 external Java 卷也不会随普通 `down -v` 自动删除。首次练习建议使用 [教程的独立环境](教程/附录-接口配置与数据字典.md#tutorial-environment)，与已有业务资料分开保存。

### 14.3 当前部署边界

会话锁可跨进程协调，但评测任务、监控统计、路由状态、缓存和熔断主要在进程内，不能据此当作完整的多副本控制面。知识导入锁也是进程内锁，多副本写入需要另行协调。

当前知识库是共享库，Token 下的用户会话隔离不等于按租户隔离所有资料。实际业务接入需要补充对应的资料权限、写操作授权和业务幂等。

## 15. 常见问题

### 15.1 健康接口正常，聊天仍失败

查看日志和响应的 `status/error_code`，核对模型 Key、Anthropic 兼容地址、模型 ID、额度、工具调用支持及超时。`/health` 不会实际调用模型。`partial` 表示内容不完整或协作有失败，不应当作完整业务成功。

```bash
docker compose logs --tail=100 echomind
```

### 15.2 修改 `.env` 没生效

确认编辑的是 Python 项目根目录配置，然后 `docker compose up -d --force-recreate echomind`。只执行 restart 不会加载新的环境值。改 Redis 密码需同时重新创建 Redis 和应用。

### 15.3 Redis 或 ChromaDB 连接失败

```bash
docker compose ps redis chromadb
docker compose logs --tail=100 redis chromadb
```

容器内使用服务名，宿主机使用 localhost 和映射端口。Redis 密码与连接 URL 保持一致，第 10 节 `ping` 脚本使用应用的实际配置。若自定义密码含 URL 特殊字符，原生 `REDIS_URL` 中还需正确编码；根目录 Compose 当前直接插入密码，设置时也要考虑这一点。

production ChromaDB 不可达会中止启动；development 回退本地后，远端客户端查询不到这些本地数据。先确认日志中的数据位置，再判断是否丢失。

### 15.4 API 返回 401 或 403

确认发送的是 EchoMind 访问 Token，且管理接口使用 admin 角色。不要发送模型 Key。启用鉴权后浏览器直接打开 Swagger 同样需要认证；使用能设置请求头的客户端。

### 15.5 聊天返回 409、503 或 504

`409` 常见于同一消息 ID 改发不同内容，新消息要换 ID。整体超时是 `504`，同会话繁忙或失锁可为 `503`，沿用原 ID 重试并查看回执结果。`retryable=false` 或结果未知的副作用操作先核验，不直接换 ID 重做。

### 15.6 知识导入成功，回答却没使用资料

先看 `total_chunks` 和 `/search` 的结果，再查该轮工具轨迹。Agent 没选择共享 RAG 工具时，本轮不检索。即使 `knowledge_used=true`，也要核对最终回复是否正确利用片段。

更新文档已清理相关检索缓存；若仍有异常，检查稳定文档 ID、实际连接库、文本内容与查询语句。不要再按照旧版“等 300 秒缓存过期”作为唯一处理办法。

### 15.7 在线向量或外部 MCP 不可用

向量检查 `/integrations/embedding` 和本次来源字段，区分未配置、local 模式、鉴权、限流和冷却。在线失败后会本地降级，不会混用两种向量空间。

MCP 检查 `/integrations/mcp` 的连接和工具列表，核对白名单、角色范围、只读注解、环境变量和容器内依赖。连接成功但调用失败时用独立调试接口查看 `success/error`。

### 15.8 用户画像或情景记忆查不到

先确认 Token 对应用户、会话 ID、已成功提交的消息数量，再看后台日志和第 10 节数据。画像会异步更新且可合并待处理任务；情景记忆需成功压缩并写入，不是每轮都有，也不保证发够固定条数后立即出现。

### 15.9 评测只返回任务 ID，或任务查询 404

任务 ID 是正常的异步响应，按 `/eval/jobs/{job_id}` 轮询，在 `result` 读报告。服务重启清空任务状态，旧记录也可被清理。`429` 表示未完成队列已满，不要无限重复提交。

Judge 失败从 `judge_error_type`、截断状态和尝试次数排查。看有效评分数后再看通过率；`complete` 不代表全通过，评分失败也不是答案得了零分。

### 15.10 Prometheus 显示目标 DOWN

先看 Targets 中的抓取错误。401/403 按第 12.2 节提供管理员凭据；连接失败检查服务名与 API 健康状态。不要把宿主机的 `localhost:8000` 填成 Prometheus 容器的采集目标。

### 15.11 端口冲突、目录写入失败或构建下载慢

确认没有同时运行根目录、前端目录两套容器，原生调试也不能占用同一个 API 端口。根目录生产镜像以 UID 1000 运行，挂载目录需允许该用户写入；按具体目录修正，不需要对整个仓库赋予所有人写权限。

首次构建要下载镜像、Python 包和 ONNX 模型。查看日志区分卡在拉取、安装还是模型下载，不能只因为构建慢就判断应用代码出错。

## 16. 推荐验证顺序

按功能逐步验证，前一步确认正常再继续：

1. 从 `.env.example` 配置，启动后看 `ps`、日志与 `/health`。
2. 通过 `/chat` 发一条带消息 ID 的请求，记录实际 `conv_id/request_id/status`。
3. 使用原 ID 重发原消息，确认复用回执；用新 ID 追问，检查字段继承。
4. 导入一份有显式 ID 的演示文档，先 `/search`，再看聊天工具轨迹。
5. 查看 Skills 和在线向量状态；要验证外部 MCP，再查连接与单独工具调用。
6. 用第 10 节脚本读消息、状态和回执；需要压缩验证时使用独立会话。
7. 查看 Monitor 与 Prometheus，启用鉴权时确认采集凭据。
8. 提交小规模评测，轮询到任务结束，再检查报告状态、有效项和具体失败原因。

需要检查程序回归时，在已准备好的 Python 环境安装测试依赖并执行：

```bash
python -m pip install -r requirements-dev.txt
python -m pytest -q
```

在根目录存储服务已启动的环境中，可执行现有集成检查：

```bash
docker compose exec -T echomind python tests/verify_request_concurrency.py
docker compose exec -T echomind python tests/verify_chat_atomic.py
```

单元、存储集成、实际模型调用和业务效果评测分别验证不同部分。本指南中的命令用于操作与排查，文档更新本身不代表重新部署、压测或跑过全部检查。
