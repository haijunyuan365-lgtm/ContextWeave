# EchoMind 定位与技术亮点

> trace 合并版说明：本页保留附件的讲解与示例；当前主链增加 Context Planner、记忆演化、经验记忆、混合检索和 OTel。运行流程、接口变化与迁移以 [合并版本使用指南](合并版本使用指南.md) 为准；文中的历史测试结果不是本次验收。

EchoMind 是一个用 Python 实现的多 Agent 客服后端，处理通用咨询、技术故障、账单售后和转人工等问题。项目围绕一轮客服对话，做了意图识别、角色分工、知识检索、工具调用、记忆和评测。

这份文档主要介绍项目的设计和实现。启动方法与接口参数见 [README](../README.md)，想顺着代码学习，可以从 [源码教程](教程/README.md) 开始。

## 项目从什么问题出发

假设用户发来一句话：

> 登录一直报 401，而且刚才付款好像扣了两次。

技术支持要处理登录故障，账单客服要确认扣款问题。接下来用户可能只补一句“订单号是……”，或者“金额是 99 元”。后端要接得住这些追问，也要知道当前缺少什么信息、能调用什么工具。

模型能理解这句话，但后续流程仍要靠程序组织：选择处理角色，带上已有信息，执行获准的工具，把结果交回模型，再保存这一轮对话。模型或工具出错、客户端重复提交时，也需要有对应的处理方式。

EchoMind 主要做的就是这部分工作。它适合用来学习 Agent 应用的后端实现，也可以作为客服业务原型继续接入企业资料和业务系统。目前已经有政策检索、错误码说明、排查计划、账单字段检查和金额比较；订单查询、实际退款和工单创建还需要接入外部系统。

## 一条消息怎样被处理

HTTP 入口是 `POST /chat`。收到请求后，先确认用户和会话，检查是否有相同请求的处理回执，再读取历史消息、摘要、用户画像和当前业务字段。

后面的流程可以这样看：

```text
读取会话上下文
    ↓
识别意图、紧急度，提取订单号、金额、错误码等信息
    ↓
合并本轮与之前的业务字段，选择处理角色
    ├─ 需求不明确：先追问
    ├─ 明确要求人工或触发紧急升级：整理交接信息
    ├─ 单一业务问题：交给对应 Agent
    └─ 同时涉及多个业务：主辅 Agent 并行处理，再合并回复
    ↓
Agent 根据需要调用知识库、角色工具或外部 MCP 工具
    ↓
保存处理结果、会话状态和请求回执，返回回复
    ↓
后台压缩历史、更新画像
```

普通 Agent 使用 Anthropic Messages 协议调用模型，编排和并行执行由 Python、`asyncio` 完成。FastAPI 提供接口，Redis 保存近期会话，ChromaDB 保存知识库、历史摘要和用户画像。配套前端与 Java 后端在其他仓库中。

系统目前有四类处理角色：

| 角色 | 负责什么 | 现有能力 |
| --- | --- | --- |
| General | 普通咨询、首轮接待、补充信息 | 检查请求上下文，提示还需提供哪些字段 |
| Technical | 登录失败、错误码、崩溃等问题 | 查询内置错误码说明，生成排查计划 |
| Billing | 扣款、退款、发票等问题 | 检查账单字段，计算金额差值 |
| Escalation | 转人工与紧急升级 | 整理意图、紧急度和已知信息，返回交接说明 |

前三类角色可以由模型选择工具。Escalation 直接通过代码生成交接内容，不再调用模型。目前没有连接人工坐席或工单队列，升级后会提示用户通过现有渠道联系人工。

## 技术上值得展开的部分

### 意图识别兼顾语义、常见表达和明确规则

客服里的“退款”“重复扣款”“开发票”都与账单有关，但后续需要的信息和处理方法不一样。因此，项目同时保留业务大类和细分意图，例如 `billing` 下的 `refund`、`invoice`、`payment_issue`。

识别过程结合三种结果：LLM 判断语义和上下文，Embedding 匹配已有表达，Pattern 处理关键词规则。默认权重是 `0.7 / 0.2 / 0.1`，LLM 与向量匹配并行执行。

融合时有一个容易忽略的细节：先按业务组汇总分数，再选组内意图。否则“技术问题”和“登录故障”可能各占一部分票，反而输给另一个单独的标签。关键词细化也只在同一个业务组内进行，避免一处关键词把整个判断带到别的领域。

向量分支可以配置硅基流动 `BAAI/bge-m3`。没有 Key 或在线调用失败时，问题和模板一起切回本地字符 n-gram 哈希向量，不会拿两种模型的向量直接比较。模板向量会缓存，并用锁防止并发重复初始化；在线失败后有冷却时间，避免每条消息都立即重试。

接口会返回各路分数和本次向量来源，便于排查分类结果。这些分数用于程序决策，实际分类效果仍要通过标注用例评测。这里的在线向量配置只影响意图识别，知识库和长期记忆使用 ChromaDB 默认的本地向量模型。

代码：[intent_recognizer.py](../core/intent_recognizer.py)、[intent_embedding.py](../core/intent_embedding.py)。

### 多 Agent 的分工落实到了输入和工具上

Technical 需要错误码、运行环境和复现信息；Billing 需要订单号、金额、时间和支付渠道。项目通过 `AgentProfile` 配置各角色的职责、处理步骤、输入输出要求和生成参数，并为它们组织不同的输入内容。

路由先处理明确的人工诉求和紧急升级，再结合意图、关键词、实体给业务领域打分。像前面的“401 + 重复扣款”，技术和账单角色都有处理依据，就可以一起执行。`RoutingDecision` 会记录主 Agent、辅助 Agent 和选择原因，方便从接口结果里看到分工。

主辅 Agent 通过 `asyncio.gather` 并行运行，完成后由 `ResponseComposer` 整理成一条回复。汇总模型调用失败时，程序仍会按顺序保留已有回答。部分角色失败会标记为 `partial`，所有角色都失败则返回 `failed`。

角色之间还有实际的工具差异。模型发出 `tool_use` 后，程序先检查工具是否在当前角色的注册表中，再校验 JSON Schema，执行后通过 `tool_result` 把结果交回模型。每个 Agent 最多进行三轮模型请求，单次调用也有超时限制。

角色的回复格式、处理步骤主要靠提示词引导；工具白名单和参数校验由程序执行。这两种约束各有用途，业务操作的权限应落在工具实现中。

代码：[agent_orchestrator.py](../agents/agent_orchestrator.py)、[agents/tools.py](../agents/tools.py)。

### 知识库由 Agent 按需查询，工具也能通过 MCP 扩展

退款政策、配送规则和排障文档放在 ChromaDB 知识库中。模型判断需要资料时，调用共享工具 `search_knowledge_base`，拿到片段后继续生成回复。

这个调用内部还会做查询改写、多子查询并行召回、去重和按需重排。改写失败就保留原问题，重排失败就使用原顺序。知识库不可用时，降级提示按失败处理，不会被包装成一条查到的政策。

知识更新也做了相应处理。同一 `document_id` 再次导入时，会更新片段、删除多余旧片段，并清理检索缓存；没有传 ID 时按标题识别文档。因此，同标题但不同来源的资料需要给不同 ID。检索结果保留标题、片段序号、文档身份和版本，方便回查。

外部工具通过标准 MCP 接入。客户端支持 Streamable HTTP 和 stdio，负责连接初始化、工具发现、列表更新和断线重连。当前默认配置 Microsoft Learn 的文档搜索与抓取，只提供给 General、Technical；其他服务可以继续在配置中添加，并指定允许使用的工具和角色。

EchoMind 也提供自己的 MCP 服务：其他客户端可以通过 `/mcp/` 查询本地知识库，或者读取知识库统计资源。

工具管理层处理缓存、超时和熔断。熔断进入半开状态时只放行一个探测请求；较早请求的迟到结果不能关闭后来触发的熔断，也不能把已经失效的旧缓存重新写回来。这些细节主要是为了处理并发调用中的状态变化。

代码：[knowledge_base.py](../tooling/knowledge_base.py)、[tool_manager.py](../tooling/tool_manager.py)、[mcp_client.py](../tooling/mcp_client.py)、[mcp_server.py](../tooling/mcp_server.py)。

### 多轮对话同时保存聊天内容和业务字段

只把历史消息拼进提示词，模型还需要每轮重新找订单号和金额。EchoMind 另外保存了一份结构化状态，包含当前业务域、已提取字段和字段来源。

用户这一轮补订单号，下一轮补金额，状态会按规则合并；检测到换订单、明确换问题或业务域变化时，会清理不该继续沿用的信息。聊天记录负责保留语境，业务字段用于明确本轮可以继承哪些数据。

存储分成两部分。Redis 保存近期消息、当前摘要和业务状态；ChromaDB 保存历史对话摘要与用户画像。读取历史时，先找同用户当前会话的相关内容，不足时再找该用户的其他会话。

消息积累后，后台任务生成摘要，保留最近几条消息。压缩期间还可能收到新消息，所以提交前会用 Redis `WATCH/MULTI` 检查快照，保留这段时间新写入的内容。摘要生成失败时保留原消息，不直接裁掉历史。压缩和画像更新使用有界任务队列，避免它们占满后台任务或拖慢聊天返回。

Redis 和 ChromaDB 之间没有跨存储事务，长期记忆写入失败时需要通过日志排查。画像内容来自模型提取，账单字段齐全也只表示信息收集到了，后续身份核验和业务授权仍要由业务系统完成。

代码：[conversation_memory.py](../memory/conversation_memory.py)、[conversation_state.py](../core/conversation_state.py)。

### 对重试和并发，按一整轮对话处理

客户端没有收到回复，可能是服务还没处理完，也可能是回复已经生成、只是网络断了。直接重新发一次，容易产生两份历史，接入写操作后还可能重复执行。

`/chat` 使用 `client_request_id` 识别同一条消息。在同一用户、会话内重试时保留这个 ID，服务可以返回已完成回执；同一 ID 换成另一条消息会返回 `409`。回执默认保留 24 小时。服务端另有 `request_id`，用来查某一次执行的工具轨迹。

同一会话的请求从读上下文到保存结果都受锁保护，其他会话可以并行。进程内按会话排队，跨进程用可续租的 Redis 锁协调，失去锁后停止继续处理。

成功或部分成功的一轮，会通过 Redis 事务一起保存用户消息、回复、业务状态、回执和脱敏轨迹。编排器返回失败结果时，保存回执及可用轨迹，不把失败轮次写进正常历史。超时或异常中断可能发生在提交之前，因此不保证都有完整记录。

对可能修改外部数据的工具，项目用 `retry_safe=False` 标记。调用前先保存一个不可自动重放的回执，同一请求内也会阻止相同操作重复调用。尝试过这类工具后，失败不会再交给兜底 Agent 自动重做。接入退款等业务时，还需要业务系统提供幂等键和执行结果查询，才能处理“请求发出去了，但结果未知”的情况。

`ChatResponse` 中的 `status`、`retryable`、`error_code` 用来告诉调用方本轮是否完整、能否重试。比如模型输出被截断会标记为 `partial`，避免把半条回复当成完整成功。HTTP 聊天请求的总处理预算是 50 秒。

代码：[api/main.py](../api/main.py)、[concurrency.py](../core/concurrency.py)。

### 经常变化的客服规则放在 Skills 中

技术客服先问哪些信息、账单客服如何说明到账时间、什么情况下提示人工，这些规则适合单独维护。项目从 `skills/` 加载 Markdown、JSON 或 TXT 文件，根据角色、关键词和启用状态，把匹配内容加入提示词，并限制总长度。

修改文件后调用 `POST /skills/reload` 就能重新加载，`GET /skills` 可以查看加载情况。当前有通用、技术和账单三类规则，汇总回复时也可以使用通用规范。

知识库保存政策和说明，Skills 记录处理习惯和流程。它们的更新频率、维护方式不同，分开后更容易调整。Skills 本身是文本规则，工具权限仍由代码控制。

代码：[skill_loader.py](../core/skill_loader.py)。

### 监控负责发现运行问题，评测负责检查回答效果

专业 Agent 一直超时，后续请求还继续发给它，服务就很难自行恢复。Monitor 会根据近期调用的成功率和延迟计算惩罚：窗口最多保留 50 次、时间范围 300 秒，至少有 5 个样本才参与计算。

惩罚会影响同类 Agent 实例的选择。Technical、Billing 进入冷却时，也会暂时退出业务候选；冷却结束后，只允许一个请求尝试恢复。探测成功清理旧状态，失败或取消就重新冷却。探测绑定具体请求，其他在途调用不能误把它释放。

`/monitor` 和 `/metrics` 还能查看工具成功率、耗时和熔断状态。不过，调用没有报错，并不能说明答案正确。回答质量需要单独评测。

评测通过 `POST /eval/run` 提交，接口返回 `202` 和任务 ID，再用 `/eval/jobs/{job_id}` 查询。意图识别计算 Accuracy、Macro-F1；对话用例可以检查目标 Agent、意图、必需工具和实体，再由 LLM Judge 评价相关性、准确性、完整性和有用性。

Judge 有单独的评分样例，包含完整回答、信息不足时说明原因、遗漏历史信息、编造操作已完成等情况，用来校准评分尺度。调用失败会留下错误和空评分，报告单独统计，避免把评分服务故障误当成回答得分。

比较回归时，用例和评分配置要能对上。项目把用例、Judge 模型、提示词、校准样例等生成 `suite_id`，只比较相同条件的有效基线。评分失败或检测到回归时，保留之前的基线。

这套对话评测直接调用编排器，并维护自己的多轮历史和业务状态。HTTP 鉴权、Redis 提交、后台画像等还要靠接口和存储测试检查。评测使用独立的路由状态、工具缓存与熔断器，但仍共享知识库和外部连接；任务进度在进程内保存，重启后需要重新提交。

代码：[performance_monitor.py](../monitor/performance_monitor.py)、[evaluator.py](../evaluation/evaluator.py)、[jobs.py](../evaluation/jobs.py)、[few_shot.py](../evaluation/few_shot.py)。

## 怎样展示这个项目

可以从一条普通技术问题开始，例如“登录返回 HTTP 401”。先看 `/chat` 返回的意图、主处理角色和路由原因，再用 `request_id` 到 `/trace/tool/{request_id}` 查看实际调用。模型是否使用了工具、工具有没有成功，都能从记录里确认。

再加入扣款诉求，观察是否出现主辅协作；分几轮补充订单号、金额，检查状态是否延续；用相同的 `client_request_id` 重试，确认回复和历史没有重复写入。这比只展示一段流畅回答，更能说明后端做了哪些工作。

仓库中已经有对应测试：[Agent 路由与工具](../tests/test_agent_orchestrator.py)、[HTTP 可靠性](../tests/test_chat_reliability.py)、[并发处理](../tests/test_concurrency.py)、[标准 MCP](../tests/test_standard_mcp.py)、[评测](../tests/test_evaluator.py)。其中包含模拟模型、fakeredis 和本地协议夹具，真实模型效果及部署容量还需要在具体环境中验证。
