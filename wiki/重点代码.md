## 1. 先找入口：哪些对象在启动时装配

**入口：[api/main.py](../api/main.py) 的 `lifespan()`、`_refresh_agent_tools()`。**

先读 `lifespan()`，再看 `/chat`，会更容易理解 `_memory`、`_orchestrator` 等变量从哪里来。它们在服务启动时创建，并在请求间复用。

| 对象 | 负责的事 | 继续阅读 |
| --- | --- | --- |
| `_orchestrator` | 意图识别、路由、角色执行、汇总 | `AgentOrchestrator` |
| `_memory` | 会话锁、上下文、回执、整轮提交、记忆维护 | `MemoryManager` |
| `_tool_manager` | 底层知识与外部工具的缓存、超时、熔断 | `MCPToolManager` |
| `_mcp_client` | 标准 MCP 连接、发现和注册远端工具 | `StandardMCPClient` |
| `_skill_manager` | 读取独立的业务规范文件 | `SkillManager` |
| `_monitor` | 收集统计，向路由回写惩罚 | `PerformanceMonitor` |
| `_profile_updater` | 有界后台队列，执行压缩和画像更新 | `ProfileUpdater` |
| `_eval_orchestrator`、`_eval_tool_manager` | 评测专用的路由状态和工具运行状态 | `EndToEndEvaluator` |

共享知识检索有两层名称：底层管理器注册 `knowledge_search`，模型看到的是 `search_knowledge_base`。后者包装查询改写、并行召回和重排。查调用关系时不要把两个名称当成同一个函数。

启动时调用 `_refresh_agent_tools()`，外部 MCP 工具目录变化后也会再次调用它，将当前工具交给各角色。评测使用独立管理器，并过滤不适合自动重试的共享工具：

```python
eval_tools = build_shared_rag_tools(_eval_tool_manager)
if _mcp_client is not None:
    eval_tools.update(_mcp_client.agent_tools(_eval_tool_manager))
_eval_orchestrator.set_shared_tools({name: spec for name, spec in eval_tools.items() if spec.retry_safe})
```

这里隔离的是路由统计、缓存与熔断等运行状态。模型服务、知识库和远端服务仍可能共用；不能因此认为评测完全不消耗线上依赖。

服务退出会依次取消评测、后台维护，关闭 MCP 连接、监控和记忆客户端。排查“退出后还有任务报错”，要看这个关闭顺序及各对象的 `close()`，而不是只看接口函数。

## 2. HTTP `/chat`：先确认身份和重复请求，再调用模型

**入口：[api/main.py](../api/main.py) 的 `access_control()`、`ChatRequest`、`chat()`；鉴权规则见 [core/access.py](../core/access.py)。**

`ChatRequest` 接收 `message`、`user_id`、`conv_id`、`client_request_id`。启用 Token 鉴权时，入口使用服务端身份覆盖请求体里的 `user_id`，避免客户端仅改一个字段就读取其他用户的会话。生产环境要求有效鉴权配置。

先分清三个 ID：

| 字段 | 表示什么 | 客户端怎样使用 |
| --- | --- | --- |
| `conv_id` | 一段持续对话 | 后续轮次带回同一个值 |
| `client_request_id` | 一条逻辑消息 | 同一条消息重试时复用，新消息换一个 |
| `request_id` | 某一次编排执行 | 从响应拿到后查询工具轨迹 |

入口生成消息 ID，并在未给会话 ID 时，根据用户和消息 ID 生成稳定的会话 ID：

```python
client_id = req.client_request_id or str(uuid.uuid4())
conv_id = req.conv_id or str(uuid.uuid5(uuid.NAMESPACE_URL, req.user_id + ":" + client_id))
started = time.monotonic()
```

因此，新建会话时若网络中断，只要仍用原 `client_request_id` 重试，也能计算出同一 `conv_id`。如果每次重试都生成新消息 ID，去重机制就无法认出它们是同一条消息。

回执保存这条消息之前提交的响应，重试时可以直接复用。读取回执发生在会话锁内、读取上下文之前：

```python
async with asyncio.timeout(50), _memory.conversation(req.user_id, conv_id):
    receipt = await _memory.get_turn_receipt(req.user_id, conv_id, client_id)
    if receipt:
        if receipt["message"] != req.message:
            raise HTTPException(409, "同一 client_request_id 不能用于不同消息")
        previous = ChatResponse(**receipt["response"])
        if previous.status != "failed" or not previous.retryable:
            return render(previous)
```

这段分支决定是否再次执行模型：

- 同一 ID 换了正文，返回 `409`。
- 先前为 `success` 或 `partial`，复用原响应。
- 先前为 `failed` 且 `retryable=false`，也复用原响应。
- 只有 `failed / retryable=true` 才继续向下重新处理。

锁内整轮有 50 秒预算，包含等锁、读上下文、识别、模型工具调用和提交。超时返回 `504`；获取会话锁失败或租约失效返回 `503`。有结构化失败响应时，`render()` 同样返回 HTTP `503`。成功与部分成功仍需继续查看响应体 `status`，不能只看 HTTP 状态。

## 3. 会话锁和整轮提交：保证读到前一轮已提交的状态

**入口：[memory/conversation_memory.py](../memory/conversation_memory.py) 的 `conversation()`、`commit_turn()`；[core/concurrency.py](../core/concurrency.py) 的 `KeyedLocks`、`redis_lease()`。**

`conversation()` 先使用进程内按键锁，再取得 Redis 租约锁。锁键来自用户与会话的组合哈希，防止分隔符造成键碰撞。同一会话从读取到提交串行处理，不同会话可以并发。

`KeyedLocks` 负责同进程 FIFO 排队与锁回收；Redis 锁负责跨进程互斥。租约默认 120 秒、每三分之一租期续租；续租失败会取消持有请求，避免失去锁后继续写入。

当前 HTTP 主链路在模型结束后调用 `commit_turn()`，没有分别写两次 `add_message()`：

```python
async with self._redis.pipeline(transaction=True) as pipe:
    if response.get("status") != "failed":
        pipe.lpush(key, raw("user", message), raw("assistant", response["response"]))
        pipe.expire(key, 86400)
        if state is not None:
            pipe.setex(self._state_key(user_id, conv_id), 86400, json.dumps(state))
    pipe.setex(self.receipt_key(user_id, conv_id, request_id), 86400,
                json.dumps({"message": message, "response": response}))
```

正常或部分完成的结果，将用户与助手消息、业务状态、响应回执放进同一 Redis 事务。失败只写回执和可用轨迹，不把失败话术加入正常历史，也不提交本次业务字段。

`LPUSH` 同时写入用户、助手两条消息后，Redis 列表头部是较新的助手消息。读取时会转换回时间顺序；压缩时则按 Redis 原始顺序保留新消息。这一点会影响后面 `LTRIM` 的理解。

回执保留 24 小时。轨迹在同一事务后续语句里存为 7 天，最近索引最多 200 个请求。事务只覆盖 Redis 写入，不能回滚模型调用、外部系统或 ChromaDB 操作。

### 可能修改数据的工具为何要先留回执

`chat()` 给编排请求设置 `before_unsafe_tool`。执行 `retry_safe=False` 的工具前，回调先通过 `commit_turn()` 写入 `tool_outcome_unknown / retryable=false` 标记。

假设未来接入提交退款工具：外部系统已收到申请，但等待最终回复时超时。预先保存的标记会阻止同一消息 ID 自动重做，要求先核验实际结果。当前项目没有真实退款执行接口，这里是接入写操作的保护路径。

本次正常结束后，最终回执会覆盖预先标记。若中途退出，标记继续存在。其有效性依赖工具正确声明 `retry_safe`，业务系统仍需自己的幂等编号和结果查询。

## 4. 上下文和业务状态：模型看背景，程序保存当前任务字段

**入口：[memory/conversation_memory.py](../memory/conversation_memory.py) 的 `get_context()`、`MemoryContext.to_prompt_text()`；[core/conversation_state.py](../core/conversation_state.py) 的 `merge_state()`。**

`get_context()` 返回近期消息、相关历史摘要、用户画像、当前摘要和结构化业务状态。入口从近期消息取最近 5 条传给意图识别；完整背景则经 `to_prompt_text()` 传给 Agent，最多包含 8 条近期消息与 3 条相关历史。

三个输入各有用途：`history` 帮助判断本轮在说哪件事，`context` 帮助角色形成回答，`conversation_state` 由程序决定哪些字段可以继承。

`AgentOrchestrator.run()` 在澄清与路由之前合并业务状态：

```python
if req.conversation_state is not None:
    from core.conversation_state import merge_state
    req.conversation_state = merge_state(req.conversation_state, req.entities,
        req.intent_group, req.message, req.request_id)
    req.entities = req.conversation_state["entities"]
```

`merge_state()` 将查询和账单归为 `commerce`，兼容同一订单的查状态、支付和退款。是否继承由领域、订单是否改变、是否明确切换任务共同决定：

```python
keep = not changed_order and not new_task and (neutral or domain == previous.get("domain"))
merged = {key: list(value) for key, value in old.items() if isinstance(value, list)} if keep else {}
origins = dict(sources) if keep else {}
```

例如这几轮均按订单相关意图处理：

```text
第 1 轮：订单号 #12345，昨天支付 99 元
  → 保存订单、日期、金额，以及各字段对应的 request_id
第 2 轮：那退款多久到？
  → 同一业务域，沿用已提供字段
第 3 轮：另一笔订单 #67890
  → 新订单 / 新任务，旧金额和日期不再继承
```

`sources` 保存字段来自哪次执行，方便追查。空提取结果不会在同一任务里直接擦掉已有值。重置状态也不删除聊天历史，因此模型背景仍可能提到旧订单；业务工具应以当前结构化字段和实际系统核验为准。

## 5. 意图识别：先看输入与缓存，再看投票

**入口：[core/intent_recognizer.py](../core/intent_recognizer.py) 的 `recognize()`、`_cache_key()`、`_vote()`；在线向量见 [core/intent_embedding.py](../core/intent_embedding.py)。**

缓存未命中时，LLM 与向量匹配并行，Pattern 本地执行：

```python
llm_task = asyncio.create_task(self._llm_recognize(message, history))
emb_task = asyncio.create_task(self._embedding_recognize(message)) if self._embedding_enabled else None
pat      = self._pattern_recognize(message)
```

正常权重是 LLM `0.7`、Embedding `0.2`、Pattern `0.1`。`_vote()` 先累计具体标签，再按 `_INTENT_GROUPS` 汇总领域：

```python
weighted_score = w * conf
scores[cat] = scores.get(cat, 0.0) + weighted_score
group = _INTENT_GROUPS.get(cat, cat)
group_scores[group] = group_scores.get(group, 0.0) + weighted_score
```

这是为了解决“technical”和“technical_login”属于同一领域却被分散计票的问题。先确定获胜领域，再选组内具体意图；Pattern 还可以按条件细化同组粗意图。

假设 LLM 是 `technical/0.8`、向量是 `technical_login/0.7`、Pattern 是 `technical_login/0.5`，技术组总分为 `0.56+0.14+0.05=0.75`。粗意图组内分高，但满足同组细化，最终为 `technical_login/0.75`。

若 Pattern 改为 `refund/0.5`，技术组为 `0.70`、账单组为 `0.05`，不能跨组细化，最终保留 `technical/0.70`。读条件时还要注意两种路径：

- LLM 失败：优先用有效非 `other` 向量结果，再用 Pattern，不走正常加权。
- LLM 正常：先判断同组细化，再判断默认 `0.5` 阈值；细化分支返回组分与 Pattern 原始置信度的较大值。

`source_scores` 是各来源原始分数，不能直接相加，也不是已校准的正确概率。实体提取与紧急度判断在融合后进行，字段提取是规则处理，不来自交易系统。

### 向量降级要看整次匹配

在线意图向量使用独立的 `IntentEmbedding`，通过 HTTP 调硅基流动 BGE-M3，已不依赖 Anthropic 客户端存在 `embeddings.create`。

`vectors()` 先为模板取快照并计算指纹，锁住在线模板初始化，按 32 条分批请求；问题与模板在同一向量空间比较。在线失败或冷却时，两边一起切换到本地 256 维字符 n-gram，不能混用一边在线、一边本地。

在线匹配总预算 8 秒，失败后冷却 60 秒；返回向量会检查数量、索引、维度、有限值和非零范数。取消任务会向上传播，不被吞成一次正常降级。

意图缓存使用完整消息和最近历史生成键；通常缓存 300 秒，已配置在线但本次降级到本地时为 60 秒。最多达到 1000 项后按插入顺序删除较早 500 项，这不是严格的“访问一次就移到最新”的 LRU。查来源看 `intent_embedding_source`，配置与冷却看 `/integrations/embedding`。

## 6. 路由和并行汇总：先看计划，再看实际结果

**入口：[agents/agent_orchestrator.py](../agents/agent_orchestrator.py) 的 `run()`、`_route_decision()`、`_domain_scores()`、`_collaboration_targets()`、`_execute()`、`run_parallel()`。**

跟读时按这个顺序走：

```text
run()
  → 必要时识别意图，合并业务字段
  → 低置信度 other 且消息长度 > 2：直接澄清
  → _route_decision()：升级或计算主辅角色
  → 单分支 _execute()，或 run_parallel()
  → 整理执行状态，记录请求轨迹
```

澄清在升级路由之前判断。进入 `_route_decision()` 后，`CRITICAL` 或人工交接意图优先选 Escalation；它当前生成确定性交接文字，不调用模型或创建工单。

普通路由先给业务类型打分，再过滤当前不可用的专业类型。General 基础 `0.1`；技术、账单对应意图各加 `0.75`；关键词与实体继续加分。主角色是可用领域中分数最高的，`routing_confidence` 上限为 `1.0`。

辅助角色优先取明确的协作信号。没有选出时才看弱信号分数：

```python
if not supporting_agents:
    supporting_agents = [
        agent_type
        for agent_type, score in ordered[1:]
        if agent_type != AgentType.GENERAL
        and score >= 0.45
        and score >= primary_score * 0.55
    ]
```

例如“登录报错 401，还重复扣款”，假设意图为 `technical_login`、只有 401 错误码实体，Technical 为 `1.31`，Billing 为 `0.18`，General 为 `0.10`。虽然账单分不到 `0.45`，明确“扣款”信号仍可使 Billing 成为辅助角色。不要只看上面这个分数兜底分支。

同一类型内，`_best_agent()` 才根据统计与惩罚选择实例；当前默认每类一个实例。类型路由与实例评分是两步，后者不能自动增加实例。

### 计划中的 Technical，不一定是最终回复者

`_execute()` 会在专业角色失败后尝试 General；若已经尝试可能产生副作用的工具，则停止自动兜底。成功兜底会保留原工具记录并插入 `agent_fallback` 事件。

并行时 `asyncio.gather(..., return_exceptions=True)` 收集分支，再由 `compose_result()` 处理：没有有效回复为 `failed`；只有一条直接用；多条尝试模型汇总，汇总失败就按顺序拼接。一个分支缺失或不完整通常形成 `partial`，但专业分支已被完整兜底时，按兜底后的最终状态计算。

| 字段 | 阅读时应怎样理解 |
| --- | --- |
| `primary_agent`、`supporting_agents` | 路由计划 |
| `agent_type` | 单分支为实际回复类型；并行结果保留主路由类型 |
| `agent_types` | 有效执行类型；全部失败时可保留计划类型 |
| `status` | 最终完整、部分完成或失败 |
| `tool_traces` | 包含工具明细及保留的兜底事件 |

排查时把计划、实际执行和状态放在一起看，不能用 `primary_agent=technical` 就断定技术分支成功。

## 7. Agent 工具循环：提示词约束与程序检查分别在哪里

**入口：[agents/agent_orchestrator.py](../agents/agent_orchestrator.py) 的 `BaseAgent._build_system_prompt()`、`_call_llm()`、`_validate_tool_input()`；工具定义见 [agents/tools.py](../agents/tools.py)。**

`AgentProfile` 描述职责、步骤、输入输出和升级条件。Technical 的角色输入包关注错误码与环境，Billing 关注订单、金额、日期与缺失字段。角色模型和生成参数也在这里指定。

自然语言契约通过提示词引导，程序并未强制把普通回复校验为固定结构。实际工具权限来自 `set_shared_tools()` 的角色过滤，以及各角色 `get_tools()` 叠加的本地工具。模型提出一个不存在于当前字典中的名称时，不会执行。

### 模型与工具怎样往返

`_call_llm()` 拼好背景、实体、角色输入包和本轮消息后，为本次调用创建局部记录：

```python
tools = self.get_tools()
tools_used: List[str] = []
tool_traces: List[Dict[str, Any]] = []
```

随后最多进行三轮模型请求。一次模型响应可能包含多个 `tool_use`，所以三轮不是最多三个工具。每次模型调用默认超时 15 秒，此外还有 `/chat` 整轮 50 秒预算。

```text
模型返回 tool_use
  → 从当前角色的 tools 字典找 AgentToolSpec
  → JSON Schema 验证参数
  → 必要时记录副作用标记
  → 执行 handler，等待异步结果
  → 使用同一个 tool_use_id 返回 tool_result
  → 再次请求模型
```

例如 `lookup_error_code({"error_code":"401"})` 只读取内置说明与排查建议，返回中明确没有检查服务器日志；Billing 的字段工具也没有查询真实订单。说明“工具调用成功”时，要说清它实际执行了哪件事。

当前校验使用 JSON Schema 校验器，不只是 Python 基础类型检查：必填字段、长度、数值范围、嵌套结构和额外字段是否允许，均由具体 schema 决定。本地工具默认拒绝额外字段；外部工具使用远端公开且经过检查的 schema。

### 副作用工具在 handler 前检查

```python
if not spec.retry_safe:
    operation = json.dumps([name, args], sort_keys=True, ensure_ascii=True)
    if operation in req.unsafe_tool_calls:
        raise ValueError("同一请求不能重复执行相同的副作用工具操作，请先核验结果")
    req.unsafe_tool_calls.add(operation)
req.tool_attempts.append({"tool_name": name, "retry_safe": spec.retry_safe})
if not spec.retry_safe and req.before_unsafe_tool is not None:
    await req.before_unsafe_tool(name)
```

同一请求里按工具名与排序后的参数识别重复操作，先登记，再通过回调持久化标记，最后才执行 handler。这一顺序决定超时之后能否安全重试。

模型最终没有有效文本时失败；文本因 `max_tokens` 截断时是 `partial`。三轮都还在请求工具、没有形成最终答复，也会失败。工具自身报错先通过 `tool_result` 交回模型，模型可能据此完整说明限制，因此工具失败不必等于整轮失败。

`AgentCallError` 携带此前工具明细，`handle()` 转成失败的 `AgentResponse`。跟异常时不要只看最后一句错误文字，要同时追这两个对象。

## 8. 底层工具管理：校验、缓存、熔断与超时的顺序

**入口：[tooling/tool_manager.py](../tooling/tool_manager.py) 的 `call()`、`CircuitBreaker`、`invalidate_cache()`。**

当前执行语句的顺序是：

```text
找到工具 → 校验参数 → 查有效缓存 → 检查熔断
→ 带超时执行 handler → 可选重排 → 更新统计与缓存
```

文件中个别旧 docstring（函数开头的说明文字）的概括顺序还没更新，跟读时以函数体为准。参数错误在请求依赖前返回，不应把健康服务计为连续失败。有效缓存位于熔断前，因此服务熔断期间仍可能返回缓存。

同步 handler 由 `asyncio.to_thread()` 执行，避免直接阻塞事件循环；异步 handler 直接等待。`wait_for` 到期会中止等待，但已经在线程中执行的同步操作不保证立即停止，不能把超时当成外部操作从未发生。

熔断就是依赖持续失败后暂时停止访问，避免继续反复等待。默认连续失败 5 次打开熔断，60 秒后只放一个半开探测。探测未结束时，其他请求失败或走 fallback（降级处理）。

### 旧请求不能关闭新一轮熔断

`call()` 取得当前 `generation`，完成后带着它调用 `record_success()` / `record_failure()`。熔断状态改变会更新代际；较早发出的慢请求不能用迟到成功覆盖新故障。

缓存也有版本检查：

```python
if use_cache and tool.cache_ttl > 0 and cache_version == self._cache_versions.get(name, 0):
    self._set_cache(name, params, data, tool.cache_ttl, cache_rerank_top_k, reranked, context)
```

例如检索 A 发出后，管理员更新资料并调用 `invalidate_cache()`。A 再返回时发现版本改变，就不能把旧结果重新填回缓存。只删字典里的现有条目，挡不住这个“先发出、后回填”的并发问题。

fallback 的返回对象保持 `ToolResult(success=False)`，即使带有说明文字也不算有效知识。本地角色小工具直接由 Agent 调用，不自动经过此管理器；不要把这里的缓存、熔断都套到每个工具上。

## 9. RAG 与资料更新：沿着两个工具名继续往下找

**入口：[agents/tools.py](../agents/tools.py) 的 `build_shared_rag_tools()`；[tooling/tool_manager.py](../tooling/tool_manager.py) 的 `search_with_rewrite()`；[tooling/knowledge_base.py](../tooling/knowledge_base.py) 的 `search()`、`add_documents()`。**

模型按需调用 `search_knowledge_base`，其 handler 再运行：

```text
search_with_rewrite("knowledge_search", query, top_k)
  → 原问题 + 最多 3 个改写问题
  → 并行 call("knowledge_search", ...)
  → KnowledgeBase.search_handler() / search_async()
  → ChromaDB 向量召回
  → 合并去重，必要时重排，再裁到 Top-K
```

`query` 必须为 1～2000 字符的非空文本，`top_k` 必须为 1～20 的整数。每路召回至少 `max(top_k, 5)`，实际条数受库内片段数限制。

合并只接收成功的底层结果：

```python
for r in results:
    if isinstance(r, ToolResult) and r.success and isinstance(r.data, list):
        for item in r.data:
            identity = ({k: item.get(k) for k in ("document_id", "title", "content", "chunk")}
                        if isinstance(item, dict) and "content" in item else item)
            key = hashlib.sha256(json.dumps(identity, sort_keys=True, ensure_ascii=False).encode()).hexdigest()
            if key not in seen:
                seen.add(key)
                merged.append(item)
```

去重身份包含文档 ID、标题、正文和片段序号，不能概括成“只按正文哈希”。底层 fallback 为失败，所以“知识库不可用”之类说明不会混入有效片段。全部没有结果时返回 `success=False / data=[]`。

`_rerank_with_status()` 只有候选数超过 `top_k` 时才尝试模型重排，成功解析并应用索引才标记 `reranked=true`；失败沿用召回顺序。`score=1-distance` 是向量距离的变换，不是答案可信概率。

`POST /search` 直接调用同一检索链路，适合分辨“资料检索不到”和“Agent 没有使用资料”。但普通聊天是否检索仍由模型决定，未按技术问题强制检索，也未对问候硬性禁用。

### 一份文档改短，旧片段怎样删除

`add_documents()` 按显式 `document_id` 或标题确定文档身份，两种类型有不同命名空间；文档身份哈希加片段序号形成稳定片段 ID，正文哈希记录版本。

```python
self._collection.upsert(ids=ids, documents=chunks, metadatas=[
    {"title": title, "document_id": document_id, "version": version,
     "chunk_index": i, "total_chunks": len(chunks)} for i in range(len(chunks))
])
stale = old_ids - set(ids)
if stale:
    self._collection.delete(ids=list(stale))
count += len(chunks)
```

同一文档从 3 片缩为 2 片时，第 0、1 片更新，多余第 2 片删除。不会再因“修改正文前 50 字导致 ID 改变”而保留旧片段。有显式 ID 时可以改标题；只用标题时，改标题就是另一份资料。

导入接口在 `finally` 里使线上与评测的 `knowledge_search` 缓存失效，即使一次导入只完成部分写入也会执行。`added_chunks` 是本次写入处理数，不是净新增数。写锁仍是进程内锁，跨副本同时维护同一文档需要额外协调。

## 10. 标准 MCP：远端工具如何进入同一执行流程

**入口：[tooling/mcp_client.py](../tooling/mcp_client.py) 的 `_serve()`、`_discover()`、`_register_catalog()`、`_call_remote()`；本地服务端见 [tooling/mcp_server.py](../tooling/mcp_server.py)。**

`MCPToolManager` 负责本地执行管理，`StandardMCPClient` 通过官方 SDK 完成协议连接。客户端支持 Streamable HTTP 与 stdio，负责初始化、分页发现、目录变化与断线重连。

`_register_catalog()` 在注册之前先筛选远端目录：

```python
if remote.name not in config.allowed_tools:
    continue
annotations = getattr(remote, "annotations", None)
if config.read_only and (annotations is None or annotations.readOnlyHint is not True or annotations.destructiveHint is True):
    continue
from jsonschema import validators
validators.validator_for(remote.inputSchema).check_schema(remote.inputSchema)
```

远端公开工具不等于当前 Agent 获得权限：还要进入 `allowed_tools`，通过只读限制，按 `config.agents` 过滤。只读模式要求明确的 `readOnlyHint=true`，并排除声明为破坏性的工具；未知注解不会直接放行。

通过筛选后，同一远端工具注册为两种对象：`Tool` 进入管理器执行，`AgentToolSpec` 供模型选择。执行结果补 `source=external_mcp`、服务名与原工具名，输出通过 `bounded_result()` 限制大小并尽量保留结构和来源。

默认 Microsoft Learn 工具开放给 General、Technical；实际配置见 [config/mcp_servers.json](../config/mcp_servers.json)。stdio 环境变量与 HTTP 认证头有显式配置，不能把所有环境变量都当成默认透传。

`/mcp/` 是 EchoMind 对外提供的 MCP 服务，暴露 `search_local_knowledge` 工具和 `echomind://knowledge/stats` 资源。前者运行基础本地检索，不经过聊天路由、查询改写与重排。查看 `/integrations/mcp` 是检查外部连接状态，与调用本地 `/mcp/` 的方向不同。

## 11. 后台记忆维护：快照之外的新消息为什么不会被裁掉

**入口：[core/concurrency.py](../core/concurrency.py) 的 `ProfileUpdater`；[memory/conversation_memory.py](../memory/conversation_memory.py) 的 `maintain()`、`_compress()`、`_update_profile()`。**

`chat()` 完成整轮提交后，非失败结果才调用 `_profile_updater.submit()`。虽然名字带 Profile，worker 实际执行 `maintain()`，先压缩再更新画像。固定 worker、有界队列，按用户合并待处理会话；队列满时跳过本次维护，不阻塞当前聊天。

当前 HTTP 主链路与旧单条写入方法要区分：

| 调用方式 | 压缩时机 |
| --- | --- |
| `/chat` → `commit_turn()` → 后台 `maintain()` | 整轮先提交，后台再检查 |
| 单独调用 `add_message()` | 方法内仍会检查阈值并等待 `_compress()` |

所以搜索到 `add_message()` 里等待摘要，不能直接得出 HTTP 也同步压缩。空会话正常每轮写两条，7 轮为 14 条，第 8 轮提交后为 16 条，达到默认 15 条阈值后由后台处理。

### 摘要生成与提交分开

`_compress()` 先用事务读取完整列表快照和旧摘要，快照不足 15 条直接返回。它将快照最近 5 条之外的消息交给模型总结；摘要为空、截断或异常就保留原始消息。

模型生成可能耗时，期间聊天仍在提交新消息。生成结束后，通过 `WATCH` 检查并计算保留条数：

```python
await pipe.watch(key, skey)
current = await pipe.lrange(key, 0, -1)
current_summary = await pipe.get(skey) or ""
if len(current) < len(snapshot) or current[-len(snapshot):] != snapshot or current_summary != old_summary:
    return  # 其他压缩任务已更新快照，不再覆盖它。
keep_count = len(current) - len(snapshot) + 5
pipe.multi()
pipe.setex(skey, 86400, new_summary)
pipe.ltrim(key, 0, keep_count - 1)
pipe.expire(key, 86400)
await pipe.execute()
```

Redis 列表最新消息在头部，因此 `current[-len(snapshot):] == snapshot` 表示旧快照仍完整位于尾部。`keep_count` 是“快照之后新来的条数 + 原计划保留的 5 条”。

```text
快照 16 条 → 模型生成摘要期间新增 2 条 → 当前 18 条
keep_count = 18 - 16 + 5 = 7
LTRIM 保留头部 7 条，包含新到的 2 条
```

旧摘要已变化、快照不再匹配就停止覆盖；发生 `WatchError` 最多重试三次，持续冲突则延期。这个条件也防止两个后台压缩任务重复覆盖同一份摘要。

Redis 摘要和裁剪提交后，才尝试写入 ChromaDB `episodic`。长期存的是摘要，旧消息全文只在 metadata 中截取部分内容；它不是完整聊天归档。两个存储没有跨库事务，ChromaDB 失败不会回滚已经完成的 Redis 压缩。

画像更新另有用户级 Redis 租约锁，ChromaDB 同步操作通过线程执行。关闭 worker 会取消在途任务并清理队列，不保证所有已排队维护都完成。

## 12. 轨迹与耗时：看哪个字段才能回答排查问题

**入口：[agents/agent_orchestrator.py](../agents/agent_orchestrator.py) 的 `_record_tool_trace()`；[api/main.py](../api/main.py) 的轨迹接口、`access_control()`；脱敏见 [core/redaction.py](../core/redaction.py)。**

工具记录先在 `_call_llm()` 内创建，通过 `AgentCallResult / AgentCallError` 向上传递，最后合并到编排结果。它们是每次调用的局部列表；共享 Agent 实例不会让两个并发用户直接共用同一份工具列表。

`_record_tool_trace()` 写进程内最近 200 条，`commit_turn()` 再将可用记录脱敏后写入 Redis。查询单条轨迹时先查 Redis，再回退到当前进程：

```python
trace = await _memory.get_trace(request_id) if _memory else None
trace = trace or _orchestrator.get_tool_trace(request_id)
```

`GET /trace/tool/{request_id}` 未找到时返回 `found=false`；`GET /trace/tools?limit=20` 按最近请求列出，不是列最近 20 次工具调用。没有用工具的请求也可能有空轨迹。中断发生在记录或提交之前时，不保证留有完整明细。

工具字段要分别理解：

| 字段 | 能说明什么 |
| --- | --- |
| `tools_used` | handler 正常返回后加入的名称，业务结果仍可能失败 |
| `success` | 该次调用流程未抛出异常 |
| `result_success` | 返回字典明确给出的业务成功标记，未提供时可能为 null |
| `cached`、`reranked` | 当前返回层传出的标记，需结合包装层实现理解 |
| `source`、`mcp_server`、`mcp_tool` | 本地或外部工具的来源 |
| `agent_fallback` 事件 | 原角色失败后交给其他角色处理 |

`knowledge_used` 当前按本地共享知识工具的成功结果计算：

```python
knowledge_used=any(t.get("tool_name") == "search_knowledge_base" and t.get("result_success") is True for t in result.tool_traces),
```

它能说明至少有一次本地检索成功，但不能证明最终回答正确引用。只调用外部 MCP 资料时它可以为 false。RAG 包装层没有逐项上传子查询缓存标记，因此外层 `cached=false` 不能证明底层从未命中缓存。

### 三种耗时不是同一范围

| 位置 | 计时范围 |
| --- | --- |
| 编排器 `OrchestratorResult.latency_ms` / 内存轨迹 | 编排阶段；HTTP 预先完成的读取和识别不在其中，并行路径重新计时 |
| `/chat` 响应体 `latency_ms` | 从入口生成 ID 后开始，包含等锁、记忆读取、识别与执行，在最终 Redis 提交前组装 |
| 响应头 `Server-Timing: chat;dur=...` | 中间件测量请求处理，包含最终提交；也用于 HTTP 延迟指标 |

复用回执时，响应体沿用原执行耗时，响应头记录这次取回执的耗时。排查接口变慢，应先看当前请求的 HTTP 计时，再分解模型、检索和存储耗时。

## 13. Skills 与 Monitor：规范注入和故障恢复分别怎样影响 Agent

### Skills 改的是本轮提示词

**入口：[core/skill_loader.py](../core/skill_loader.py) 的 `Skill.matches()`、`prompt_for()`；[agents/agent_orchestrator.py](../agents/agent_orchestrator.py) 的 `_build_system_prompt()`。**

`matches()` 先检查启用状态和角色，再匹配本轮消息关键词。没有角色限制则适用各角色；没有关键词则不要求命中关键词。匹配是大小写不敏感子串，不会自动搜索历史里的词。

`prompt_for()` 将命中文件正文拼入预算，单项默认 3200 字符、整体默认 5000 字符。模型调用前追加到 system prompt：

```python
skill_prompt = self._skill_manager.prompt_for(req.message, self.agent_type.value)
if not skill_prompt:
    return base_prompt
return f"{base_prompt}\n\n[动态 Skills]\n{skill_prompt}"
```

编辑文件后通过 `/skills/reload` 重载；`/skills` 可查加载项和解析错误。它不执行脚本、不创建工具权限，也不替代知识库事实。Composer 可以匹配通用规范，Escalation 的确定性路径不走普通 system prompt 构建。

### Monitor 用近期样本暂停专业角色

**入口：[monitor/performance_monitor.py](../monitor/performance_monitor.py) 的 `_collect()`、`_routing_penalty()`；[agents/agent_orchestrator.py](../agents/agent_orchestrator.py) 的 `AgentStats`、`_monitor_degraded()`、`_best_agent()`。**

默认每 10 秒采样。`recent()` 取最近 300 秒、最多 50 次完成记录；至少 5 个样本才计算路由惩罚。成功率低于 0.90 和平均耗时高于 3000 ms 分别增加惩罚。

例如近期成功率 `0.60`、平均 `4000 ms`，惩罚为 `0.5+0.1=0.6`；`0.85 / 4000 ms` 则为 `0.2`。默认 Technical、Billing 达 `0.5` 进入 60 秒冷却。告警、实例评分和实际暂停是三件事，不能看到告警就断定已经回退。

到期不是立刻全部放行。`handle()` 将一个请求标记为探测拥有者，`record()` 只允许该请求释放探测状态：

```python
if self.probe_running and request_id == self.probe_owner:
    self.probe_running = False
    self.probe_owner = None
    if success:
        self.samples.clear()
        self.retry_at = 0.0
        self.monitor_penalty = 0.0
    else:
        self.retry_at = time.monotonic() + max(1, _env_float("ECHOMIND_MONITOR_COOLDOWN_SECONDS", 60))
```

成功清除旧窗口和惩罚，失败或取消重新冷却。另一个较早请求即使此时完成，也不能释放当前探测。工具统计用于独立告警，没有直接混入 Agent 惩罚。执行成功率也不是回答正确率。

## 14. 评测：任务结束、评分有效、用例通过要分别判断

**入口：[api/main.py](../api/main.py) 的 `run_eval()`、`get_eval_job()`；[evaluation/jobs.py](../evaluation/jobs.py)；[evaluation/evaluator.py](../evaluation/evaluator.py)。**

`POST /eval/run` 以 `202` 返回任务快照。`EvaluationJobs` 默认最多 8 个排队或运行中的任务，串行执行，运行上限 1800 秒；任务与进度保存在进程内，重启后旧任务不可查。

`completed` 表示 runner 正常返回报告，不等于报告完整或全部通过。读报告依次看：`status`、`evaluation_errors`、`valid_total`、`pass_rate`、逐条结果及 `regressions`。

### 用例如何通过

`IntentEvaluator.evaluate()` 按最终细意图计算 Accuracy、Macro-F1、每类指标和逐条预测。API 报告包含 Accuracy、Macro-F1 与用例信息，没有直接展开 `per_class` 表。

对话用例在内存维护历史与业务状态，直接调用编排器；最后一轮可检查预期角色、意图、必需工具和实体。参考答案与核验资料交给 Judge，用于四维质量评分。校准用例单独定义在 [evaluation/few_shot.py](../evaluation/few_shot.py)，只进入 Judge 提示词。

```python
scores = (QualityScores(0.0, 0.0, 0.0, 0.0) if agent_status == "failed" else
          await self._judge.judge(question, actual_answer, context=judge_context or None))
passed = (agent_status == "success" and all(checks.values()) and
          scores.overall is not None and scores.overall >= self.PASS_THRESHOLD)
```

这段代码同时限制执行状态、确定性检查和质量均分。失败执行直接记零，不消耗一次 Judge；部分完成可以评分但不能通过。必需工具检查来自 `tools_used`，仍需结合具体工具结果判断业务成功。

### 评分失败不能补成中间分

`LLMJudge.judge()` 最多尝试两次，输出截断、JSON 不完整、缺维度、布尔值、非有限值和越界分数都有明确错误。格式错误、超时等可以重试，鉴权错误不重复尝试。解析支持从说明或围栏中提取完整对象，接受可转换的数值字符串，但最终必须有四个有效 `0～1` 分数。

重试仍失败返回缺失评分，并在结果里记录 `scores={}`、`judge_failed=true` 和原因。这类记录从均分与有效通过率分母排除：

```python
passed_count = sum(1 for r in results if r.passed)
valid_total = sum(not r.metadata.get("judge_failed", False) for r in results)
pass_rate = passed_count / valid_total if valid_total else 0.0
```

意图样本整体汇总为一条结果，对话每轮各一条。因此假设意图汇总通过，3 个对话轮次中有 1 条通过、1 条未通过、1 条评分错误：`total=4`、`valid_total=3`、`passed=2`、`pass_rate=2/3`，报告为 `partial`。不能把该比例说成“所有原始样本的准确率”。

### 只比较相同用例与评分配置的基线

`_suite_id()` 将用例、Judge 模型与服务地址、评分预算、提示词、校准样例版本和内容、通过阈值哈希。`_comparison_baseline()` 只选同套件的完整且无回归报告。

相对下降严格超过 5% 才算回归；`0.80 → 0.75` 下降 6.25%，会触发。含评分错误时跳过比较，空报告、不完整报告和退步报告不会覆盖有效基线。API 当前传入 `EVAL_BASELINE_PATH`，默认 `/app/data/eval/baseline.json`；保存采用临时文件加 `os.replace()`。

套件指纹没有包含全部 Agent 提示词、代码和知识库快照，实际对照还需记录这些版本。评测覆盖编排器行为，不经过 HTTP 鉴权、Redis 整轮提交和后台记忆维护。
