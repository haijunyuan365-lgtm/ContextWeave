# EchoMind 技术亮点

> trace 合并版说明：本页保留附件的讲解与示例；当前主链增加 Context Planner、记忆演化、经验记忆、混合检索和 OTel。运行流程、接口变化与迁移以 [合并版本使用指南](合并版本使用指南.md) 为准；文中的历史测试结果不是本次验收。

EchoMind 把客服消息交给模型理解，也用代码安排角色、执行工具、保存会话，并处理请求重复、依赖故障和评分失败。这篇主要展开这些设计的原因与实现。

部署和接口操作见 [完整使用指南](完整使用指南.md)，逐步跟一条消息走完处理过程见 [业务流程说明](业务流程说明.md)。文中的数字和输出示例用于解释代码，涉及模型的结果会明确标注假设。

## 1. 从一条复合问题看设计重点

用户可能这样提问：

> 登录一直报 401，而且刚才还重复扣款了。

这里同时有技术和账单问题。用户随后还可能补充订单号、金额，或者因为页面没收到回复而再次点击发送。除了回答内容，后端还需要处理：

- 怎样发现一句话中的两个业务方向，分别交给谁。
- 哪些资料已经收集，下一轮还能不能沿用。
- 模型想查资料或执行工具时，程序怎样检查并调用。
- 专业角色出错、工具超时或请求重试时，怎样继续或停止。
- 改过规则和模型提示词后，怎样检查回答有没有退步。

HTTP 主链路已经把这些步骤接在一起：

```text
鉴权、会话锁和回执检查
→ 读取背景、识别意图、合并任务字段
→ 选择主辅角色，执行有限轮模型与工具往返
→ 形成 success / partial / failed 结果
→ Redis 事务提交消息、状态、回执和轨迹
→ 后台压缩消息、更新画像
```

当前有三类使用 LLM 的客服角色，以及一个确定性人工交接节点。账单工具检查字段和计算差值，技术工具提供错误码说明与排查计划。真实查单、退款执行、工单创建需要继续接入业务系统。

## 2. 意图融合：粗分类和细分类怎样一起投票

“账单问题”和“申请退款”描述的是同一领域的不同层次。如果分类结果只按具体标签各算各的票，同一领域的证据可能被分散，影响后续路由。

`IntentRecognizer` 使用 LLM、Embedding 和 Pattern 三种来源。LLM 看语义与历史，Embedding 匹配模板表达，Pattern 处理明确关键词。LLM 和向量任务并行，规则匹配在本地执行。

默认权重分别是 `0.7 / 0.2 / 0.1`。正常融合先按 `intent_group` 汇总，再选择组内意图；它不是直接拿三个结果中单项分数最高的标签。

### 同一个例子里看分组和细化

假设三路结果如下：

| 来源 | 结果 | 原始分数 | 加权分数 |
| --- | --- | --- | --- |
| LLM | `technical` | `0.80` | `0.56` |
| Embedding | `technical_login` | `0.70` | `0.14` |
| Pattern | `technical_login` | `0.50` | `0.05` |

技术组总分为 `0.75`。组内粗意图 `technical` 的分数 `0.56` 高于细意图的 `0.19`，但 Pattern 给出了同组细类，满足细化条件，因此最终可以返回 `technical_login / 0.75`。

细化要求组内获胜的是粗意图、Pattern 是同组细意图、Pattern 分数至少 `0.5`，且组分数低于 `0.8`。不符合细化条件时，才继续按默认 `0.5` 阈值决定是否返回 `other`。

再换一组假设：LLM 为 `billing / 0.9`，Embedding 为 `other / 0`，Pattern 为 `technical_login / 0.5`。账单组得 `0.63`，技术组得 `0.05`。Pattern 与获胜组不同，不能把结果改成技术登录问题，最终保留 `billing / 0.63`。

### 失败与低置信度有不同处理

LLM 失败时不再正常加权，而是先用非 `other` 且有正分的向量结果，再用 Pattern，均不可用才返回 `other`。

识别器返回 `other` 后，编排器还会检查消息去首尾空格后的长度是否大于 2、置信度是否低于 `0.5`。同时满足才直接提出业务方向追问，避免在信息不足时继续调用专业角色。

输出包含最终意图、业务组、紧急度、实体、来源分数和向量来源。实体用规则提取订单号、金额、日期、HTTP 错误码；`product` 当前为空。紧急度对部分否定表达先做清理，再匹配关键词；`CRITICAL` 在未进入澄清分支时优先升级，`HIGH` 本身不会强制转人工。

这些分数是规则融合结果。要说明分类效果，需要使用标注集的 Accuracy、Macro-F1 和逐条预测，不能把 `0.75` 直接解释成已证明的 75% 正确率。

代码：[intent_recognizer.py](../core/intent_recognizer.py) 的 `recognize()`、`_vote()`、`_urgency()`。

## 3. 在线向量失败时，整次匹配一起降级

意图向量使用独立的 `IntentEmbedding` 客户端，可以通过硅基流动调用 `BAAI/bge-m3`。没有配置、在线失败或正在冷却时，使用本地 256 维字符 n-gram 哈希向量。

降级时一个关键问题是：问题向量与模板向量必须来自同一种表示。拿在线模型的问题向量与本地哈希模板比较，即使都能算出数字，结果也没有可比意义。

因此，代码把一次匹配的模板和问题一起准备：

```text
在线可用：在线模板向量 + 在线问题向量
在线失败：本地模板向量 + 本地问题向量
```

在线模板采用懒加载和缓存，通过锁避免多个请求同时初始化。模板按最多 32 条分批请求；响应会检查数量、索引、维度、有限数值和非零范数，防止不完整或异常向量参与匹配。在线匹配预算为 8 秒，失败后冷却 60 秒。

缓存也考虑了运行状态。意图缓存键包含完整消息与最近历史；在线配置存在但本次已降级时，结果缓存较短，避免恢复后长时间继续使用降级结果。接口通过 `intent_embedding_source` 显示本次实际来源，状态接口显示配置与冷却信息。

`local` 模式仍参与正常三路投票，只是向量表示改成本地形式。这里的本地向量是无在线服务时的简易匹配方法，不能把它当成训练好的语义模型。知识库与长期记忆使用 ChromaDB 默认向量模型，与这一分支分开。

`learn()` 会在进程中追加纠错模板并清缓存，但没有训练模型或持久化自动学习流程。

代码：[intent_embedding.py](../core/intent_embedding.py)、[intent_recognizer.py](../core/intent_recognizer.py)。

## 4. 主辅路由：主意图之外，继续检查另一件事

意图识别给出一个最终意图，用户一句话却可能需要多个角色处理。`AgentOrchestrator` 因此把领域打分和协作检测分开。

### 路由先选领域，再选实例

明确人工诉求和紧急请求先处理。普通请求根据意图、关键词、合并后的实体给 General、Technical、Billing 打分，再过滤无实例或暂不可用的专业类型。

最高分成为主角色。辅助角色优先来自明确的技术或账单意图、关键词；如果没有选出，再按分数兜底：其他专业领域至少 `0.45`，并达到主分数的 `55%`。General 不作为辅助角色。

在同类实例中，另按成功率、延迟与监控惩罚选择实例。当前默认每类一个实例；实例池结构支持添加同类实例，但没有自动扩容或跨进程负载调度。

### 复合问题可以复算

对“登录报错 401，还重复扣款”，假设最终意图为 `technical_login`，提取错误码 401，没有订单号和金额：

```text
Technical = 意图 0.75 + 两个关键词 0.36 + 错误码 0.20 = 1.31
Billing   = “扣款”关键词 0.18
General   = 基础分 0.10
```

Technical 为主角色，`routing_confidence` 截为 `1.0`。Billing 分数虽然低于 `0.45`，但协作检测已发现明确的扣款诉求，仍可以成为辅助角色。若只看主意图或分数兜底，就可能漏掉这一件事。

`RoutingDecision` 记录主辅角色、原因和分数，API 对应返回 `primary_agent`、`supporting_agents`、`routing_reason`、`routing_confidence`。角色选择是规则计算，不是训练出来的自学习路由。

### 并行执行和汇总的取舍

主辅角色通过 `asyncio.gather` 并行执行，再由 Composer 收集各分支的最终结果：

- 只有一个有效回复就直接使用，不额外调用汇总模型。
- 多个有效回复交给汇总模型组织主次、去重和提示冲突。
- 汇总模型出错时，按顺序拼接已有结果，保留专业内容。
- 按分支最终状态区分全部完整、部分成功和全部失败。

专业分支若已由 General 成功兜底，就按兜底后的结果判断完成状态；原专业失败仍保留在轨迹中。Composer 自己失败但确定性拼接成功时，也不必自动将结果判成整轮失败。

这种协作适合领域清楚的复合客服问题。它要等待各分支结束，还可能增加一次汇总调用，实际延迟和成本应测量后判断。

代码：[agent_orchestrator.py](../agents/agent_orchestrator.py) 的 `_route_decision()`、`_collaboration_targets()`、`_best_agent()`、`run_parallel()`。

## 5. 角色分工由提示词和工具权限共同落实

各角色在 `AgentProfile` 中定义职责、处理步骤、输入输出要求、升级条件和生成参数。Technical 的输入包带错误码与环境提示，Billing 带订单、金额、日期和缺失字段。

| 角色 | 本地工具 | 默认生成设置 |
| --- | --- | --- |
| General | 检查请求上下文、提示需补充字段 | temperature `0.3`，max_tokens `900` |
| Technical | 内置错误码说明、排查计划 | temperature `0.1`，max_tokens `1200` |
| Billing | 账单字段检查、金额差值计算 | temperature `0`，max_tokens `1100` |
| Escalation | 当前直接生成交接文字 | 确定性路径，不调用 LLM |

普通角色还可以使用共享知识库工具，以及配置允许的外部 MCP 工具。`ECHOMIND_GENERAL_MODEL`、`ECHOMIND_TECHNICAL_MODEL`、`ECHOMIND_BILLING_MODEL` 可覆盖角色模型 ID，仍使用同一 Anthropic 兼容客户端服务配置。

角色契约主要通过提示词引导，自然语言回复没有被强制校验成某种结构。程序真正执行的限制来自实际工具注册表、角色范围过滤和 JSON Schema。

例如 Billing 没有 `lookup_error_code`，模型即使提出这个名称也不能执行。知识检索 `top_k` 必须是 1～20 的整数，本地工具默认禁止额外字段；缺少必需金额的比较调用会在进入 handler 前被拒绝。

### 工具调用有明确的往返和停止条件

```text
模型提出 tool_use
→ 程序检查白名单与参数
→ 执行 handler
→ 通过 tool_result 把结果交回模型
→ 模型继续回答或提出下一轮工具请求
```

每个 Agent 最多进行三轮模型请求，每次模型调用默认超时 15 秒；HTTP 聊天另有 50 秒总预算。一轮模型响应可以包含多个工具调用，所以“三轮”不是“三个工具”的数量限制。

没有文本的最终回复按失败处理；最终文本因 token 上限被截断时标为 `partial`。工具报错后会把错误交回模型，模型仍可能完整说明限制并给出下一步，因此“工具失败”和“整轮失败”需要分开。

### 工具明细按请求保存

`tools_used`、`tool_traces` 是 `_call_llm()` 内的局部变量，通过 `AgentCallResult` 返回。模型后续异常时，`AgentCallError` 携带失败前的工具记录。

同一个 Technical 实例同时处理用户 A、B 时，两边分别有自己的记录列表。Agent 累计统计仍共享，但逐请求工具状态不会因为共享实例上的列表而混到一起。

`tools_used` 在 handler 正常返回后加入工具名；如果返回对象里的业务 `success=false`，工具名也可能存在。未知工具、参数错误则只留下失败明细，不进入工具名列表。诊断时要同时看调用状态与业务结果。

代码：[agents/tools.py](../agents/tools.py)、[agent_orchestrator.py](../agents/agent_orchestrator.py) 的 `_call_llm()`、`_validate_tool_input()`。

## 6. RAG 同时考虑检索过程和资料更新

共享工具 `search_knowledge_base` 由模型按需调用。知识查询不固定插在意图识别与路由之间；问候没有硬性禁用工具，技术问题也没有硬性强制检索。

### 一次检索怎样完成

```text
校验 query 和 top_k
→ 保留原问题，最多增加 3 个改写问题
→ 各路并行调用 knowledge_search
→ 合并并去重
→ 结果多于 top_k 时尝试 LLM 重排
→ Top-K 作为工具结果交回模型
```

每路召回数至少为 `max(top_k, 5)`，再受实际库内片段数限制。去重身份包含文档 ID、标题、内容、片段序号，避免只按正文去重时把不同文档身份混在一起。

改写失败保留原问题，重排失败保留原顺序并标记 `reranked=false`。结果数本来就不超过 `top_k` 时不调用重排模型。`reranked=true` 表示成功解析并应用了重排索引，不能单凭这个标记证明质量提高。

`POST /search` 可单独运行相同的检索链路，先用于确认资料是否能召回，再检查 Agent 是否使用。该接口仅返回 query、结果和重排状态，详细失败原因仍需结合日志和工具统计。

### 失败的降级说明不作为知识证据

底层知识工具超时、异常或熔断时可以返回带说明的 fallback，但它保持 `success=false`。合并只接收成功结果，全部查询没有有效片段就返回失败和空列表。

因此 `knowledge_used=true` 现在依据工具轨迹中的实际成功结果计算。它表示本地共享知识库至少一次检索成功，仍不能替代对最终回答的事实检查。只查外部 MCP 文档时，这个本地标记可以为 false。

RAG 包装器没有逐项转发各子查询的缓存状态，所以请求轨迹里 `cached=false` 不能用来证明底层从未命中过缓存。分析缓存效果需要结合底层统计或增加更细的埋点。

### 一份资料改版后怎样避免旧片段残留

文档身份由显式 `document_id` 或标题确定，两种身份分别加命名空间后生成哈希。片段使用“文档身份 + 序号”，正文哈希作为版本。

假设同一份政策从 3 片缩短为 2 片，再次导入会更新第 0、1 片，删除多余第 2 片。线上与评测检索缓存随导入失效，避免刚更新还一直读旧资料。同一批出现相同文档身份，采用最后一份。

有显式 ID 时，改标题仍可更新同一文档；没有 ID 则依赖标题，改标题会成为另一份资料。`added_chunks` 是本次处理数，不是净新增数。长句也会切分，上传限定 txt、md、json，单文件最大 10 MB。

导入写锁仍是进程内锁，ChromaDB 更新和删除不是多副本事务；并发维护同一文档还需要额外协调。production 空库禁止自动加载演示政策，远端不可用也不静默切换本地库。

代码：[tool_manager.py](../tooling/tool_manager.py)、[knowledge_base.py](../tooling/knowledge_base.py)、[api/main.py](../api/main.py) 的知识接口。

## 7. 工具可靠性：处理超时之外，还要处理迟到结果

知识检索和外部 MCP 工具经过 `MCPToolManager`，顺序是：

```text
参数校验 → 有效缓存 → 熔断检查 → 带超时的 handler → 更新统计和缓存
```

本地角色工具由 Agent 执行层直接调用，不能把工具管理器的所有机制都当成每个小工具自动具备的能力。

参数错误在访问服务前返回，不计入依赖熔断。缓存包含参数、调用上下文、重排参数和版本，返回时复制结果，减少调用方修改同一个缓存对象的风险。有效缓存可以在服务熔断时继续使用，因为它的检查位于熔断之前。

工具默认连续失败 5 次后熔断，60 秒后进入半开。半开只允许一个探测请求，其他调用走失败或 fallback；探测成功恢复，失败重新熔断。

### 为什么还需要状态版本

并发时，请求返回的顺序不一定等于发起顺序。例如：

```text
A 先发出，执行很慢
B、C 等后续请求失败，触发新一轮熔断
A 终于成功返回
```

如果 A 直接把状态改回正常，就会用一个旧请求的成功盖掉新故障。当前熔断器用 `generation` 标记状态代际，记录结果时核对版本；旧代请求不能关闭新一轮熔断。

缓存失效也有类似问题。某搜索 A 在资料更新前发出，管理员更新资料并清理缓存后，A 才返回旧结果。代码在写缓存前检查调用开始时的缓存版本与当前是否一致，不一致就不回填，避免清缓存后又立刻出现旧内容。

这类处理针对并发时序，单独验证“一次调用成功”很难覆盖，需要构造先发后到、失效后返回等情况。

代码：[tool_manager.py](../tooling/tool_manager.py) 的 `CircuitBreaker`、`call()`、`invalidate_cache()`。

## 8. 标准 MCP：把工具协议和本地执行管理分开

项目有两层相关实现：本地 `MCPToolManager` 管理 handler 的执行；官方 MCP SDK 客户端和服务端负责标准协议互通。两层配合，外部工具才能像已有工具一样进入 Agent 调用过程。

### 调用外部服务

`StandardMCPClient` 支持 Streamable HTTP 和 stdio，处理连接初始化、分页工具发现、工具列表变化和断线重连。

发现工具后还要按配置筛选：是否在 `allowed_tools` 中、开放给哪些 Agent、只读模式下远端是否明确声明只读且没有破坏性。参数 schema 经过检查后再注册，Agent 不能因远端公开了某工具就自动获得它。

默认 Microsoft Learn 搜索和抓取只开放给 General、Technical。认证头从指定环境变量取，stdio 子进程只传必要和显式允许的变量；连接层不自动附送整段会话或画像，但模型生成的工具参数可能包含当前问题信息。

外部结果按预算裁剪，保留有效结构，优先保留已有来源字段。轨迹记录 `source=external_mcp`、服务名、工具名，便于区分本地规则、知识库和外部资料。

### 让其他客户端查询 EchoMind

`/mcp/` 用 FastMCP 暴露 `search_local_knowledge` 工具和 `echomind://knowledge/stats` 资源。它复用本地知识库，但没有经过客服意图与路由；基础 MCP 搜索也不自动执行聊天 RAG 的查询改写和重排。

客户端目前主要使用外部 Tools，服务端提供本地 Tools 和 Resource。增加业务工具仍需配置权限、实现实际操作和验证结果，不能根据支持 MCP 就声称已经接通订单或支付系统。

代码：[mcp_client.py](../tooling/mcp_client.py)、[mcp_server.py](../tooling/mcp_server.py)、[mcp_servers.json](../config/mcp_servers.json)。

## 9. 请求一致性：同一轮对话怎样安全保存和重试

一轮聊天可能执行很多步骤，但对客户端来说只是一条消息。连接中断时，客户端不一定知道模型没执行、执行中，还是结果已提交。因此，请求 ID 和存储方式需要一起设计。

### 区分消息编号与执行编号

`client_request_id` 由客户端提供，用来表示同一条逻辑消息；`request_id` 由服务端生成，用来追踪某次执行。

客户端以相同用户、会话、消息 ID 重发：

- 已完成或部分完成，返回原回执，不再调用模型或写两份历史。
- 原失败结果允许重试，重新执行，恢复后才写正常历史。
- 相同 ID 改发另一条消息，返回 `409`。
- 原失败不允许重试，返回原结果，不自动重做。

回执保留 24 小时。去重依赖客户端复用相同消息 ID，也受用户和会话范围限制。

### 锁住的是整轮处理

进程内按会话排队，跨进程使用可续租的 Redis 租约锁。从读取上下文一直到提交结果都在锁内，不同会话仍可并发。

这样，用户连续发“订单号是……”和“金额是……”时，后一个请求不会在前一个尚未提交时就读到旧字段。租约失效会取消持有请求，避免失去处理资格后继续写入。HTTP 整轮预算 50 秒，包含等锁、读记忆、模型工具和提交。

开启 Token 鉴权后，聊天用户以服务端映射为准，覆盖请求体传入的用户标识；production 要求有效配置。它给会话隔离提供可信身份，但共享知识库仍需要另行设计资料权限。

### 消息与回执在同一个 Redis 事务中提交

`commit_turn()` 一起保存非失败轮次的用户消息、助手回复、业务状态，以及回执和可用轨迹。失败轮次只保存回执与轨迹，不污染正常聊天历史或当前业务字段。

例如，第一次模型服务故障，回执为 `failed / retryable=true`，工作消息仍为空。恢复后重试原 ID，才写入用户与助手两条消息；再重发一次，直接拿回相同响应。

事务覆盖的是这些 Redis 写入。模型调用、外部业务操作与 ChromaDB 写入不属于同一个事务；超时或异常在提交前中断，也可能没有完整记录。

### 有副作用的工具先记录，再执行

对于 `retry_safe=False` 的工具，调用前先保存 `tool_outcome_unknown`、`retryable=false` 回执。单次请求中相同工具和参数也不能重复执行；已尝试这类操作后，失败不再自动交给 General 重做。

假设以后接入提交退款工具，外部系统收到申请后，后续模型回复却超时。这个预先标记可以阻止客户端用同一 ID 再次自动提交，要求先核验结果。当前还没有实际退款执行工具，这部分是接入写操作时已有的保护机制。

保护依赖正确声明 `retry_safe`，也需要对接系统自己的业务幂等和结果查询，不能保证崩溃前后的所有外部操作恰好执行一次。

代码：[api/main.py](../api/main.py) 的 `chat()`、[concurrency.py](../core/concurrency.py)、[conversation_memory.py](../memory/conversation_memory.py) 的 `commit_turn()`。

## 10. 多轮状态与分层记忆：把当前任务和聊天背景分别保存

用户分三轮提供“订单号”“99 元”“昨天”，不应该每轮都重新问。仅保存自然语言历史，也容易在切换订单时继续使用上一笔数据。

项目将记录分成几类：

| 数据 | 存储 | 主要用途 |
| --- | --- | --- |
| 最近消息与当前摘要 | Redis | 保留聊天语境，控制输入长度 |
| 业务状态与字段来源 | Redis | 明确当前任务的订单、金额等数据 |
| `episodic` 历史摘要 | ChromaDB | 按语义找相关历史 |
| `user_profile` | ChromaDB | 保存模型提取的用户偏好与长期信息 |

`merge_state()` 将查询、账单统一到 `commerce`，同域时继承字段；换订单、明确新任务或切到不相容领域时重置。字段 `sources` 保留本次提供该值的请求 ID。

例如先说“订单号 #12345，昨天支付99元”，再问“退款多久到”，在相应识别条件下继续保留订单、金额、日期；再说“另一笔订单 #67890”时，旧金额和日期清空。清理业务状态不删除历史聊天，模型仍可能读到它们作为背景。

近期消息最多读取 20 条，Agent 背景最多使用最近 8 条与 3 条相关历史。情景检索优先当前用户、当前会话，不足再扩展同用户其他会话。当前任务字段与画像都不等于已经核验的客户或交易记录。

### 先提交结果，再做后台压缩

HTTP 通过有界后台队列维护记忆，固定 worker 数量，同用户待处理更新可合并。维护先压缩再更新画像，不要求当前聊天等待这两项完成。队列满时跳过本次任务，不能把后台处理当作每轮必定成功的步骤。

压缩阈值 15 指消息条数。空会话前 7 轮正常提交后为 14 条，第 8 轮整轮提交后为 16 条，再由后台压缩。

### 压缩时怎样保留新到的消息

后台先读取完整快照和旧摘要，为较旧消息生成摘要，再通过 `WATCH/MULTI` 检查快照并提交。`WATCH` 用于发现读取后记录是否被其他写入改动，`MULTI` 将相关更新一并提交。

```text
开始生成摘要：快照 16 条，计划保留其中最近 5 条
期间又有一轮提交：当前变成 18 条
提交压缩结果：保留新到的 2 条 + 快照最近 5 条 = 7 条
```

代码检查旧快照是否仍完整位于列表旧记录部分、摘要是否已被其他压缩修改。快照不再匹配就放弃覆盖，事务冲突时可重试或延期。这可以避免后台压缩把用户刚补充的数据裁掉。

摘要为空、截断或生成失败时保留原始消息；Redis 摘要和裁剪提交后才尝试写 `episodic`。Redis 与 ChromaDB 无跨存储事务，后者失败只记录日志。

ChromaDB 同步操作通过 `asyncio.to_thread` 执行，Redis 使用异步客户端，减少阻塞事件循环。画像更新另有用户级 Redis 锁，避免多个进程同时更新同一用户。服务关闭时取消并清理后台 worker，不能认为所有尚未完成的维护都会落盘。

代码：[conversation_state.py](../core/conversation_state.py)、[conversation_memory.py](../memory/conversation_memory.py)、[concurrency.py](../core/concurrency.py)。

## 11. Skills：让业务规范可以单独调整

退款回答要收集哪些字段、技术排查先确认什么、不能承诺哪些操作，这些规则经常需要调整。`SkillManager` 将它们放在独立文件中，支持 Markdown、TXT 和 JSON。

普通 Agent 构造 system prompt 时，按启用状态、角色和当前消息关键词筛选，受字符预算限制。Billing 的退款规则只在对应角色与关键词符合时注入，Technical 不会因为收到同一句话就自动拿到所有账单规范。

修改文件后通过 `/skills/reload` 重新扫描，`/skills` 查看成功加载与解析错误。单个文件解析失败不影响其他规则。Composer 可以使用通用规范约束汇总，Escalation 的确定性路径不经过普通提示词构建。

规则与资料的用途不同：Skills 描述处理方法，知识库存业务事实。Skills 是提示词文本，没有执行脚本，也不能替代程序中的授权和参数检查。这个拆分方便调整话术与步骤，同时保持工具执行规则明确。

代码：[skill_loader.py](../core/skill_loader.py)、[skills/](../skills)。

## 12. Monitor：用近期表现暂停专业角色，再试探恢复

如果某个专业 Agent 持续超时，下一条同类问题还一直交给它，就会重复失败。项目将运行统计写回路由，默认每 10 秒采样。

惩罚依据最近 300 秒、最多 50 次完成调用，至少 5 个样本才计算。成功率不足 `0.90`、平均耗时超过 3000 ms 时增加惩罚，总值不超过 `0.9`。

同类实例选择采用：

```text
(累计成功率 × 0.7 + 1 / (1 + 累计平均耗时秒数) × 0.3)
× (1 - monitor_penalty)
```

近期窗口用于惩罚，累计指标用于基础实例评分。这样监控判断不会一直被很久以前的大量成功样本稀释；但这仍是规则化反馈，不是模型训练。

### 一个实例也能暂停和恢复

Technical、Billing 的惩罚达到默认 `0.5` 后进入冷却，默认 60 秒。这时它们可以退出领域候选，即使每类只有一个实例也有效。

例如近期 5 次有 3 次完整成功、平均耗时 4000 ms：成功率惩罚为 `min(0.5, (0.90-0.60)×2)=0.5`，延迟惩罚为 `0.1`，总值 `0.6`，进入冷却。

到期后只放行一个请求作为恢复探测，探测绑定 `request_id`。成功清除旧窗口和惩罚；失败或取消则重新冷却。其他旧请求的完成不能误释放这次探测状态。

工具成功率、延迟、连续失败和熔断用于告警与建议，没有直接计入 Agent 惩罚。告警与实际回退需要分别看；近期成功率 0.85、4000 ms 时惩罚只有 0.2，可能告警但没有达到暂停阈值。

`/monitor` 提供统计与恢复状态，`/metrics` 暴露 Prometheus 指标。Agent 和 HTTP 延迟直方图记录单次实际耗时，HTTP 指标按状态码观察；执行正常不等于答案正确，回答质量由下一节单独检查。

代码：[performance_monitor.py](../monitor/performance_monitor.py)、[agent_orchestrator.py](../agents/agent_orchestrator.py) 的 `AgentStats`。

## 13. 评测：把答得不好、执行失败和评分失败分开

改提示词后，一条回复看起来更流畅，不代表路由、事实和多轮字段都正确。项目同时检查分类结果、确定性要求和回答质量，避免只用一个模型分数决定通过。

### 分类看标注，对话看执行与内容

意图评测比较最终细意图与标注，计算 Accuracy、各类别 Precision / Recall / F1 和 Macro-F1，并保留逐条预测。测试输入可以带历史，检查“那退款呢”这类依赖上一轮的问题。

对话评测直接调用编排器，在用例内维护历史与业务状态，复用聊天的字段合并逻辑。最后一轮可额外检查预期主角色、意图、必需工具和实体。例如：

```text
第 1 轮：订单号 #12345，昨天支付了 99 元
第 2 轮：现在想退款

最后一轮检查：
- 是否交给预期角色
- 是否识别为预期意图
- 订单号、金额和日期是否仍在状态中
- 如果要求检索，是否确实调用了指定工具
```

这里的角色和分类结果应由用例给出明确标注，不能用本段示意替代实际测试。

每轮的通过条件是：执行状态为 `success`、该轮所有确定性检查通过、四维质量均分至少 `0.75`。执行为 `failed` 时直接记零分，不再请求 Judge；`partial` 即使获得高分也不能通过。必需工具检查依据 `tools_used`，它证明发生了调用，不单独证明工具业务结果成功。

### Judge 用样例校准，也要检查自身输出

Judge 按相关性、准确性、完整性、有用性打分，每项范围 `0～1`。参考答案和核验资料可随用例提供，用来区分“符合已知政策”和“文字听起来合理”。

评分提示词包含 5 个独立校准样例，覆盖有依据的完整回答、诚实说明能力边界、空泛回答、虚构已执行操作、遗漏历史信息。样例只交给评分器，不作为被测 Agent 的输入，也不计入测试用例数。

响应解析支持多个文本块、代码围栏和嵌套分数字段，但最终仍要求四项齐全、为有限数字且在范围内。空回复、截断、非法 JSON、缺字段、布尔值或越界分数都产生明确错误，最多尝试两次；鉴权错误不反复重试。

例如 Judge 返回三个维度，代码不会把第四项补成 `0.5`。该条记录 `scores={}` 和 `judge_failed=true`，附带错误类型、尝试次数等信息，并从有效均分和通过率分母中排除。报告同时给出 `total`、`valid_total`、`evaluation_errors`，因此不能只展示排除错误后的通过率。

评分器不可用说明这次评测缺少质量结论，不能据此认定客服回答及格或不及格。

### 评测任务异步运行，状态与线上请求分开

`POST /eval/run` 返回 `202` 和任务 ID，再用 `/eval/jobs/{job_id}` 查询进度。任务串行执行，有队列容量和运行时限。任务及进度保存在当前进程，重启后不能继续查询原任务。

线上和评测使用不同的编排器、角色统计、工具缓存与熔断状态；评测也只保留用例内历史，不写入普通客户会话。这可以避免评测失败直接让线上专业角色进入冷却。但两边仍共用模型服务和底层资料，评测会消耗真实模型请求与资源。

任务 `completed` 只表示运行结束。报告还要看：

| 报告状态 | 含义 |
| --- | --- |
| `complete` | 没有评分错误，仍可能有用例未通过 |
| `partial` | 有效结果与评分错误同时存在 |
| `failed` | 有结果记录，但没有有效评测结果 |
| `empty` | 没有结果记录 |

当前范围是编排器评测，不覆盖 HTTP 鉴权、Redis 整轮提交、后台压缩等完整服务行为。这些需要各自的集成与故障测试。

### 回归比较先确认两次测的是同一套内容

代码根据用例、评分模型与服务地址、评分预算、提示词、校准样例版本和内容、通过阈值计算 `suite_id`。只有相同 ID 且完整、没有回归的历史报告，才可作为比较基线。

相对下降严格超过 `5%` 才标记回归。例如从 `0.80` 降到 `0.75`，相对下降 `6.25%`，会触发；降到 `0.77`，相对下降 `3.75%`，不会触发。

含评分错误时跳过回归比较；不完整、空报告和检测到回归的报告不会覆盖有效基线。文件保存使用临时文件加原子替换，减少中途退出造成半份文件的风险。

`suite_id` 没有包含全部 Agent 提示词、知识库快照和代码版本。正式比较仍应一起记录代码提交、配置和资料版本，多副本共同维护基线也需要额外协调。

代码：[evaluator.py](../evaluation/evaluator.py)、[few_shot.py](../evaluation/few_shot.py)、[jobs.py](../evaluation/jobs.py)、[llm_utils.py](../core/llm_utils.py)。

介绍项目时，可以优先讲清三个相互衔接的设计：怎样把复合问题交给合适的角色，怎样在失败、重试和并发时保存可信状态，怎样用有标注、有错误状态的评测检查修改。再根据听者关心的问题，展开 RAG、MCP、记忆或恢复探测。

没有测量数据时，使用“支持主辅协作”“为一次调用设置时间预算”“保留并发期间新消息”等可核对的描述。准确率提高多少、延迟降低多少、能承受多少并发，需要给出数据集、环境、对照与测量结果后再写。
